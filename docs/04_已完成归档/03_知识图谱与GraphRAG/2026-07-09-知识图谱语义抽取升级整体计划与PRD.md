## 1. 背景与问题

当前项目已经完成基础 RAG、结构化解析、SectionPathExtractor、TableFieldExtractor、ConfigBlockExtractor、GraphBuilder、候选审批和图谱入库流程。

但现有图谱存在明显问题：

```text
Document / Section 节点很多
Product / Tool / Service / Procedure / Step / ConfigItem 等业务实体很少
图谱更像“文档章节索引”，还不是“领域知识图谱”
```

当前抽取方式主要依赖规则和白名单：

```text
doc_category -> Product
section_path 精确匹配白名单 -> Tool / Service
表格结构 -> DataTable / Field
特定 Config 格式 -> ConfigItem
```

其中 `domain_catalog.json` 只承担 seed 与归一化辅助作用。它可以帮助已知产品、工具、服务稳定命名，但不能替代通用语义抽取；catalog 外或正文语义中的新实体，仍需要 LLMGraphExtractor 或新的通用规则才能进入候选。

这会导致：

```text
1. 白名单外的业务实体无法抽取
2. 安装流程、配置步骤、依赖组件、命令、错误处理等大量知识仍然只是 Section
3. 不同文档都会出现类似问题，不能靠给每个文档单独写规则解决
4. 重建图谱时存在旧 chunk link 残留、人工关系保护不足的问题
5. 仅执行规则图谱补全会改善章节和表结构可遍历性，但不会根本解决业务实体覆盖不足
```

因此，本阶段目标是把图谱构建方式从：

```text
规则白名单抽取
```

升级为：

```text
Schema 约束的 LLM 语义抽取
+ 高精度规则抽取
+ 实体归一化/消歧
+ 候选审批
+ 安全重建
+ GraphRAG 检索接入
```

## 2. 产品目标

## 2.1 总目标

构建一套面向企业技术文档的通用知识图谱抽取管线，使系统能够从不同产品文档、用户手册、配置文档、数据规范、部署文档中自动抽取领域实体和关系。

目标图谱结构从：

```text
Document
  └── Section
        └── Chunk
```

升级为：

```text
Product
  ├── Tool
  ├── Service
  ├── Module
  ├── EnvironmentComponent
  ├── Procedure
  │     └── Step
  ├── Command
  ├── ConfigItem
  ├── DataTable
  │     └── Field
  ├── Error
  │     └── Solution
  └── Evidence Chunk
```

## 2.2 核心原则

```text
1. 不为单个文档硬编码抽取逻辑
2. 具体产品、工具、服务词典只作为 seed，不作为主抽取能力
3. LLM 抽取必须受 Schema 约束
4. 所有 LLM 输出必须带 evidence_text 和 confidence
5. LLM 输出不得直接写入正式图谱，必须进入候选表
6. 人工事实、特殊关系、已审批 alias 必须可保留
7. 重建图谱必须可审计、可回滚、可对比
8. GraphRAG 检索必须基于可信图谱事实，而不是未经审核的临时结果
```


## 5. 总体架构

升级后的图谱构建流程：

```text
Document Parsing
      ↓
Chunking + Metadata
      ↓
Rule Extractors
      ↓
LLMGraphExtractor
      ↓
Candidate Normalization
      ↓
Entity Resolution / Dedup
      ↓
Candidate Review
      ↓
Safe Apply
      ↓
Graph Audit
      ↓
GraphRAG Retrieval
```

职责划分：

```text
规则抽取器：负责高精度、低成本、结构明确的事实
LLMGraphExtractor：负责通用语义理解和跨文档泛化抽取
Normalizer：负责名称归一化、别名、重复候选合并
Review：负责人工确认和批量审批
Safe Apply：负责保护人工事实并写入正式图谱
Audit：负责质量检查和重建前后对比
GraphRAG：负责在查询时使用图谱增强召回
```

## 6.3 事实来源字段

所有实体、关系、链接需要能区分来源：

```text

created_by = llm:schema_extractor

created_by = manual
created_by = seed
created_by = rule:special
```

安全重建时，只允许替换：

```text
rule:*
llm:*
```

默认保留：

```text
admin
manual
seed

```

## 6.4 Candidate 字段要求

LLM 抽取候选必须包含：

```json
{
  "candidate_type": "entity | relation | alias | field | link",
  "name": "实体名",
  "entity_type": "实体类型",
  "source_name": "关系源实体",
  "target_name": "关系目标实体",
  "relation_type": "关系类型",
  "confidence": 0.0,
  "evidence_text": "原文证据",
  "source_chunk_id": "chunk id",
  "source": "文档名",
  "section_path": "章节路径",
  "created_by": "llm:schema_extractor",
  "extractor_version": "v1",
  "prompt_version": "v1"
}
```

硬性要求：

```text
1. 没有 evidence_text 的候选不能自动通过
2. relation_type 不在 schema 中的候选不能入库
3. entity_type 不在 schema 中的候选不能入库
4. source_name / target_name 找不到实体时，需要先生成对应实体候选
5. confidence 低于阈值的候选默认不进入审批或标记为 rejected
```

## 7.5 Candidate Normalizer 候选归一化

### 目标

解决 LLM 抽取后实体重复和命名不一致问题。

### 处理内容

```text
1. 去除多余空格
2. 大小写归一化
3. 中文/英文括号归一化
4. 版本号处理
5. alias 匹配
6. domain_catalog 对齐
7. 同名不同类型冲突检测
8. 相似名称候选合并
```

### 示例

这些应该识别为同一候选或 alias：

```text
PostgreSQL
postgresql-16
Postgres
PostgreSQL数据库
```

这些需要进入冲突审核：

```text
Apache -> EnvironmentComponent
Apache数据服务 -> Service
httpd -> EnvironmentComponent
```

因为它们可能有关联，但不一定完全 same_as。

### 验收标准

```text
重复实体显著减少
同义词进入 aliases 或 same_as candidate
类型冲突进入 diagnostics，不直接合并
```

## 7.6 Entity Resolution 实体消歧

### 目标

在正式入库前解决：

```text
1. 新实体还是旧实体
2. alias 还是不同实体
3. 同名不同类型是否冲突
4. 是否需要 different_from
```

### 处理策略

```text
1. 精确同名 + 同类型：合并 evidence
2. 精确同名 + 不同类型：生成 type_conflict diagnostic
3. alias 命中：生成 alias_of 或 same_as candidate
4. 高相似度但不确定：生成 merge candidate
5. 明确不同：生成 different_from candidate
```

### 验收标准

不会因为 LLM 抽取引入大量重复节点，例如：

```text
Postgres
PostgreSQL
postgresql-16
PostgreSQL数据库
```

## 7.7 Candidate Review 审批升级

### 目标

支持 LLM 大规模候选的批量审核，而不是只能 approve-all。

### 新增命令

```powershell
.\venv\Scripts\python.exe run_graph_build.py review --batch xxx --summary
.\venv\Scripts\python.exe run_graph_build.py review --batch xxx --approve-type EnvironmentComponent
.\venv\Scripts\python.exe run_graph_build.py review --batch xxx --approve-confidence-above 0.90
.\venv\Scripts\python.exe run_graph_build.py review --batch xxx --reject-confidence-below 0.60
.\venv\Scripts\python.exe run_graph_build.py review --batch xxx --approve-source "某文档.docx"
```

### 审批策略

```text
confidence >= 0.90
+ schema 合法
+ 有 evidence_text
+ 无类型冲突
=> 可批量通过

0.70 <= confidence < 0.90
=> pending，人工审核

confidence < 0.70
=> 默认 rejected 或 ignored

无 evidence_text
=> 不允许通过

类型冲突
=> 必须人工确认
```

### 验收标准

```text
可以按 entity_type / relation_type / confidence / source 批量审批
LLM 候选不会只能 approve-all
```

## 7.8 Safe Rebuild 安全重建

### 目标

重建图谱时：

```text
不丢人工事实
不残留旧 chunk link
不重复堆积旧自动事实
可回滚
可对比
```

### 命令

```powershell
.\venv\Scripts\python.exe run_graph_build.py rebuild-safe
```

### 流程

```text
1. audit 当前图谱
2. export manual / seed / special facts
3. cleanup stale links
4. 标记旧 rule:* 和 llm:* 自动事实为 superseded
5. 执行 rule extract
6. 执行 llm extract
7. normalize candidates
8. resolve candidates
9. 生成待审 batch
10. review
11. apply approved candidates
12. restore manual / seed / special facts
13. audit 新图谱
14. 输出 before/after diff
```

### 不允许做的事

```text
1. 不直接删除 admin/manual facts
2. 不直接清空 rag_relational.db
3. 不把 pending LLM candidates 写入正式图谱
```

## 7.10 GraphRAG 检索接入

### 目标

让图谱不只是“建出来”，而是真正参与 RAG。

### 2026-07-22 过渡方案（先于完整 GraphRAG；其后第 4 轮已 PASS）

在第 4 轮「图侧 chunk 融合 A/B」之前，先落地**主干锚定检索**（详见 `已完成-主干锚定检索与关系可答/执行PRD.md`）：

```text
用户问题
  ↓
主干软命中 + 改写 LLM（口语 → canonical / anchored_queries）
  ↓
Hybrid 检索（多路 query，含 graph_rewrite；不拉图 chunk）
  ↓
回答生成（注入锚点 + 主干一跳关系摘要）
```

配置口径：

- `graph_retrieval.enabled = false`：关闭 Entity Linking → Expansion → 图 chunk 融合
- `graph_retrieval.query_rewrite_enabled = true`：仅保留主干锚定改写与回答侧关系骨架

「定位优先」= **找对实体/chunk 位置**，并把锚定结果交给回答 LLM；不是强制「先介绍后操作」文风。

完整目标流程（第 4 轮及以后再打开图 chunk）仍如下。

### 查询流程（完整目标态）

```text
用户问题
  ↓
Query Understanding
  ↓
Entity Linking
  ↓
Graph Expansion
  ↓
Evidence Chunk Retrieval
  ↓
Hybrid Retrieval Fusion
  ↓
Rerank
  ↓
Answer Generation
```

### 示例 1

用户问：

```text
StampServer 部署需要哪些环境组件？
```

系统应：

```text
1. 链接实体：StampServer
2. 图扩展：requires / depends_on / configured_by
3. 找到 Redis、PostgreSQL、Apache、Nginx、Tomcat 等 EnvironmentComponent
4. 召回对应 evidence chunks
5. 结合向量检索结果回答
```

### 示例 2

用户问：

```text
如何配置 PostgreSQL？
```

系统应：

```text
1. 链接实体：PostgreSQL
2. 找 Procedure / Step / Command / ConfigItem
3. 召回对应安装配置步骤
4. 回答时引用证据 chunk
```

### 验收标准

GraphRAG 对以下问题有明显提升：

```text
1. 某产品依赖哪些组件？
2. 某服务如何配置？
3. 某工具使用哪些配置项？
4. 某流程有哪些步骤？
5. 某错误如何解决？
6. 某数据表有哪些字段？
```

## 11. 技术风险与对策

## 风险 1：LLM 幻觉

对策：

```text
1. 强制 evidence_text
2. 严格 schema validation
3. 低置信度不入库
4. 所有 LLM 输出进入候选表
5. answer 阶段只使用 approved facts
```

## 风险 2：实体重复严重

对策：

```text
1. CandidateNormalizer
2. alias 表
3. same_as / different_from 审核
4. domain_catalog 辅助归一化
```

## 风险 3：抽取成本过高

对策：

```text
1. LLM 抽取可配置开关
2. 只对业务价值高的 chunk 调 LLM
3. 规则先过滤候选 chunk
4. prompt 压缩
5. 缓存 chunk_id + content_hash 的抽取结果
```

## 风险 4：审批量过大

对策：

```text
1. confidence 分层
2. 按类型批量审批
3. 按文档批量审批
4. 高置信候选可自动通过
5. 冲突候选才人工重点看
```

## 风险 5：重建破坏人工关系

对策：

```text
1. export manual facts
2. created_by 分层
3. rebuild-safe 不删除 manual/admin/seed
4. restore special facts
5. before/after audit diff
```
