## 一、项目概述

### 1.1 背景与问题

系统已具备对话式问答所需的多块能力：

| 能力 | 现行模块 | 作用 |
|------|----------|------|
| 歧义预检 | `QueryClarificationService` + `POST /query/clarify` | 检索前反问，产出 `entity_name` / `doc_category` |
| 追问改写 | `QueryContextualizer` | 指代补全、多查询、来源锚点 |
| 历史压缩 | `HistoryCompressor` | 超轮次时对旧对话做摘要（LRU + 后台线程） |
| Token 裁剪 | `ContextBudgetManager` | 生成前按估算 token 裁 history / 低分 chunk |
| 观测 | `QaTraceBuilder` | 阶段耗时、plan、候选落盘 |

这些能力**功能上可用**，但共享输入几乎只有松散的 `history: list[{role, content, sources?}]`，各自截断、各自猜意图，导致：

1. **多层 history 上限不一致**：前端约 60 条 → 压缩按轮数 → 预算按 token 丢旧 → `_build_messages` 再硬截 30 条。
2. **压缩与预算职责打架**：先 `compress` 再 `trim`；摘要未命中缓存时后台异步，**当次仍传全量 history、无摘要**，预算再砍一遍，行为不确定。
3. **澄清与上下文化双轨**：澄清改 filter；上下文化改 retrieval query；二者不共享 Understanding。澄清选后前端 history 常丢掉 `sources`，来源锚点失效。
4. **检索问题与回答问题脱节风险**：检索用 `standalone` / 多 query；回答仍用原始 `question`（可保留），但缺少同源的「已解析焦点」注入，长追问易漂移。
5. **重复防护与死参数**：实体保护在 contextualize / build_query_specs / planner 多处重复；clarification 残留 unused compat 参数；`rag.py` 私有依赖 clarification 下划线符号。
6. **观测不完整**：主路径 ChatView 不写 `clarification_*`；同步 `query()` 无完整 trace；`/query` 可能丢 `trace_id`。

根因不是「少一个开关」，而是缺少：

- 唯一的 **会话状态（SessionState）**
- 唯一的 **对话理解出口（UnderstandingResult）**
- 唯一的 **生成打包所有者（GenerationPack / TokenBudget）**


### 1.2 第一性原理（设计公理）

对话式 RAG 的「上下文」只回答四个问题：

| # | 问题 | 产出 |
|---|------|------|
| Q1 | 用户现在究竟在问什么？（指代、省略、是否歧义） | Understanding |
| Q2 | 该去哪里找证据？ | RetrievalPlan（queries + filters） |
| Q3 | 证据与对话记忆如何装进回答模型？ | GenerationPack（在 token 上限内） |
| Q4 | 事实边界在哪里？ | Evidence 可作事实；Dialogue 仅作理解/消歧 |

两类状态不可混用：

| 类型 | 内容示例 | 可否作为回答事实 |
|------|----------|------------------|
| **Dialogue State** | 解析后的问题、已选实体、上一轮来源锚点、滚动摘要 | **否** |
| **Evidence State** | 检索 chunk、引用编号 | **是** |

违反任一公理的方案（例如把关系文本当事实、或继续让四个模块各自解读 `history[]`）不在本 PRD 接受范围内。


### 1.3 目标

1. 建立 **SessionState → DialogueUnderstanding →（检索 | 澄清）→ GenerationPack** 的清晰流水线。
2. **一次理解**：澄清与上下文化共享判定与结果结构；禁止两套互不承认的 LLM JSON。
3. **一次打包**：历史摘要是 TokenBudget 对话槽位不足时的填充策略，不是独立「先砍一轮」的旁路。
4. 前端与后端共用同一套 **来源摘要 / Session 字段** 契约；澄清选择必须保留锚点与 filter。
5. QA Trace 完整记录 Understanding 与 Pack 决策，主路径与调试路径一致。
6. 改造过程保持现有问答可用性；分阶段交付，每阶段可独立验收与回滚。


### 1.4 非目标

| 非目标 | 说明 |
|--------|------|
| 跨会话用户偏好表 | 见《用户偏好记忆与反问继承系统-PRD》；本 PRD 只预留 Session/Understanding 挂接点 |
| 歧义规则管理后台 | 见《歧义消解规则管理系统-PRD》；本 PRD 不规定规则存储形态 |
| 知识库主数据重构 | 见《RAG 架构升级 PRD》；不改 Chroma/BM25/文档树 |
| 把图谱关系当事实答案 | 继续：context 为事实；实体/关系提示仅消歧 |
| 拆微服务 / 换向量库 / 换前端框架 | 不在范围 |
| 为每个硬编码数字单独加配置项而不收敛政策 | 禁止用配置爆炸掩盖缺少单一 Pack 政策 |


### 1.5 成功标准（总览）

| 编号 | 标准 | 度量方式 |
|------|------|----------|
| S1 | 会话内澄清选择后的下一问，source_anchor 可用率 ≥ 基线显著提升 | 固定追问用例 + trace 中 `source_anchor` 出现率 |
| S2 | 超长会话首次超限时，生成路径行为确定性（有摘要或明确降级截断，禁止「全量+无摘要」静默） | 单测 + 集成用例 |
| S3 | history 相关截断政策单一入口可描述（文档/代码一处） | 代码审查：无前端/compress/budget/build_messages 四套互斥硬编码 |
| S4 | Understanding 结果可在 trace 中完整回放 | `qa_traces` 含 mode、resolved_question、queries、filters、pack 摘要 |
| S5 | 现有追问/澄清黄金用例不回归 | pytest + 人工抽检题集 |
| S6 | 检索用改写与回答用原题的关系被显式建模（同源焦点） | 契约字段存在且单测覆盖 |


## 二、现状基线（事实摘要）

> 以下为 2026-08-11 基于代码梳理的基线，供改造对照。实施前若代码已变，以实施时再审计为准。

### 2.1 现行数据流

```text
前端 ChatView
  → POST /query/clarify（可选）
  → POST /query/stream + history(role/content[/sources])
       → QueryContextualizer.build_query_specs   # 检索侧
       → QueryPlanner / Graph / Hybrid
       → HistoryCompressor.compress              # 生成侧
       → ContextBudgetManager.trim
       → _build_messages(原 question + history + summary?)
       → 回答 LLM
```

### 2.2 关键配置与硬编码（基线）

| 项 | 位置 | 基线值 |
|----|------|--------|
| 前端 history 条数 | `ChatView.vue` | `slice(-60)` |
| 上下文化读 history | `query_contextualizer` | 最近 6 条，content 截 200 |
| 来源锚点门槛 | `build_query_specs` | dependent ∧ confidence≥0.6 ∧ heuristic_dependent |
| 生成 messages 硬截 | `rag.py` `MAX_HISTORY` | 30 |
| context_budget | config 默认 | window=32768, ratio=0.7, chars_per_token=1.3 |
| history_compression | config 默认 | min_raw_rounds=8, max_raw_rounds=20；mix 配置可覆盖 |
| 压缩未命中 | `HistoryCompressor.compress` | 后台线程；当次 `(full_history, None)` |

### 2.3 与相关 PRD 的关系

| 文档 | 关系 |
|------|------|
| 用户偏好记忆 | **下游消费**：Understanding 判定需澄清时，可先查偏好再决定是否弹卡片；偏好写入不在本 PRD |
| 歧义规则管理 | **种子源之一**：Understanding 的选项种子可来自 DB 规则或产品主干；本 PRD 要求种子经统一 Understanding 出口 |
| RAG 架构升级 | **正交**：QueryOrchestrator 未来可托管本流水线；本期不依赖主数据重构即可落地 |


## 三、目标架构

### 3.1 逻辑架构

```text
┌────────────────────────────────────────────────────────────┐
│ SessionState（会话唯一真相源，请求级或 chat_id 级）          │
│  turns[] / last_sources[] / resolved_entity / doc_category │
│  rolling_summary? / dialogue_focus?                        │
└──────────────────────────┬─────────────────────────────────┘
                           ▼
┌────────────────────────────────────────────────────────────┐
│ DialogueUnderstanding（单一理解阶段）                       │
│  输入: question + SessionState                             │
│  输出 UnderstandingResult:                                 │
│    mode: clarify | retrieve                                │
│    resolved_question / user_utterance                      │
│    retrieval_queries[] / filters                           │
│    dialogue_focus（短记忆，供生成）                         │
│    needs_source_anchor / confidence / rationale            │
└──────────────┬─────────────────────────────┬───────────────┘
         clarify│                            │retrieve
                ▼                            ▼
        反问卡片返回                  RetrievalPlan → Evidence
                                             │
                                             ▼
                               ┌─────────────────────────┐
                               │ GenerationPack          │
                               │ TokenBudget 唯一所有者   │
                               │ 槽位优先级见 §5         │
                               └─────────────────────────┘
```

### 3.2 模块映射（目标 vs 现状）

| 目标组件 | 承接现状 | 改造要点 |
|----------|----------|----------|
| SessionState | 前端 history + 请求字段 | 结构化；澄清选择写回；sources 必留 |
| DialogueUnderstanding | Clarification + Contextualizer | 合并出口；共享 underspecified/dependent |
| RetrievalPlan | `RetrievalQuery` + Planner | 只消费 Understanding，不再二次改写 |
| GenerationPack | Compressor + Budget + `_build_messages` | 合成单一 pack；压缩=槽位策略 |
| Evidence | Hybrid/Graph 结果 | 不变：唯一事实通道 |
| Trace | QaTrace | 记录 Understanding + Pack 决策 |


### 3.3 设计约束（硬性）

1. **回答 LLM 的事实依据仍只能来自检索 context（及显式联网外部来源）**。
2. `history_summary` / 实体提示 / backbone 提示 **不得**被 Prompt 写成可引用事实。
3. 用户可见回答默认仍可基于 **原始提问文案**；解析结果以 `dialogue_focus` / system 辅助理解，不强迫改写用户原话。
4. 禁止新增「第五条」并行解读 history 的服务；新逻辑必须挂到 Understanding 或 Pack。


## 四、数据契约

### 4.1 SessionState

逻辑结构（实现可为 Pydantic / TypedDict；HTTP 可渐进兼容旧 `history`）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `chat_id` | str \| null | 可选；无则请求级 |
| `turns` | Turn[] | 有序对话轮 |
| `last_sources` | SourceSummary[] | 最近一次助手回答的来源摘要（最多 N，默认 4） |
| `resolved_entity` | str \| null | 本会话已确认实体（澄清或显式） |
| `doc_category` | str \| null | 本会话已确认分类 |
| `rolling_summary` | str \| null | 旧轮滚动摘要（由 Pack/压缩策略维护） |
| `dialogue_focus` | str \| null | 最近理解焦点（短文本，供生成/检索） |

**Turn**：

| 字段 | 说明 |
|------|------|
| `role` | `user` \| `assistant` |
| `content` | 文本 |
| `sources` | 仅 assistant；可选 |
| `clarification` | 可选；该轮若经过澄清 |

**兼容**：一期可继续接收现有 `history[]`，由服务端适配器组装 SessionState；前端二期改为显式 Session 字段。


### 4.2 UnderstandingResult

| 字段 | 类型 | 说明 |
|------|------|------|
| `mode` | `clarify` \| `retrieve` | 是否需要反问 |
| `user_utterance` | str | 用户原话 |
| `resolved_question` | str | 补全指代后的独立问题（检索主 query） |
| `retrieval_queries` | RetrievalQuery[] | kind/weight/text；含 original/standalone/search/source_anchor 等 |
| `filters` | object | `entity_name` / `doc_category` / `kb_name`… |
| `dialogue_focus` | str | ≤约定长度；生成侧短记忆 |
| `is_context_dependent` | bool | |
| `confidence` | float | 0..1 |
| `clarify` | ClarificationPayload \| null | mode=clarify 时必填 |
| `rationale` | str | 短理由，供 trace |

**规则**：

- `mode=clarify` 时 **不得**进入正式检索生成（与现前端行为一致）。
- `mode=retrieve` 时 `retrieval_queries` 至少含 1 条；`resolved_question` 非空。
- 启发式对「独立问题」保留否决错误历史锚点的权力（继承现有安全设计）。


### 4.3 GenerationPack 输入/输出

**输入**：Evidence（source_docs + context 字符串）、SessionState、UnderstandingResult、agent_prompt、allow_general_knowledge、模型 context_window。

**输出**：

| 字段 | 说明 |
|------|------|
| `messages` | 最终发给回答 LLM 的 messages |
| `source_docs` | 裁剪后证据 |
| `context` | 裁剪后 context 字符串 |
| `history_for_messages` | 进入 messages 的 recent turns |
| `history_summary` | 注入 system 的摘要（可空） |
| `pack_decision` | 结构化决策：丢弃了哪些 turn/chunk、是否用了摘要、降级原因 |

**槽位优先级（唯一政策）**：

```text
1. 不可裁：system 规则骨架 + 当前 user_utterance + generation_reserve
2. Evidence：按 quality_score 从低到高删，至少保留 1 块（继承现限制并在 trace 标明超预算）
3. Dialogue：优先保留最近 K 轮原文；更旧内容优先用 rolling_summary，其次丢弃
4. 辅助：实体消歧 / backbone 提示按固定上限截断
```

**压缩策略相对现状的变更（关键）**：

| 场景 | 现状 | 目标 |
|------|------|------|
| 超限且摘要缓存命中 | 用摘要 + recent | 保持 |
| 超限且摘要未命中 | 后台异步；当次全量+无摘要 | **确定性降级**：同步短摘要（可设超时）**或**仅保留最近 K 轮并写 `pack_decision.fallback=truncate_recent`；禁止静默全量 |
| 摘要失败冷却 | 全局冷却后仍全量 | 冷却期内固定走 truncate_recent |


### 4.4 SourceSummary（前后端统一）

统一字段（与后端 `extract_source_summary` 对齐，前端禁止手写另一套 map）：

| 字段 | 必填 | 说明 |
|------|------|------|
| `file_name` / `source` | 是 | 文件标识 |
| `section_title` | 否 | |
| `page_label` | 否 | 无页码显式「无页码」 |
| `chunk_id` | 否 | 锚点增强 |
| `preview` | 否 | ≤200 字 |
| `citation_id` | 否 | 若有 |

澄清选项提交后：**不得清空** `last_sources`（除非新助手回答替换）。


## 五、功能需求详细设计

### 5.1 P0 — 契约收敛（高杠杆、低叙事膨胀）

**目标**：不先做大重构，先让行为可预测、锚点不断、打包可解释。

| ID | 需求 | 验收 |
|----|------|------|
| P0-1 | 服务端定义 SessionState / UnderstandingResult / PackDecision 数据结构（可先由现有模块拼装） | 单测序列化/字段齐全 |
| P0-2 | 澄清选择路径保留 `last_sources`；ChatView 不得在选选项后丢掉 sources | 用例：澄清→追问「继续说」→ trace 出现 source_anchor 或等价锚点 query |
| P0-3 | 合并 Generation 路径：`HistoryCompressor` + `ContextBudgetManager` + messages 组装由 `GenerationPack.pack` 唯一调用 | rag 主路径仅一处 pack 调用 |
| P0-4 | 压缩未就绪时确定性降级（见 §4.3） | 单测覆盖三种场景 |
| P0-5 | 前后端共用 SourceSummary 构建（API 可返回规范化 sources；前端只透传） | 无双份字段映射 |
| P0-6 | ChatView 主路径写入 `clarification_question` / `clarification_selected`（与 QaDebug 对齐） | trace 可过滤澄清会话 |
| P0-7 | 文档化唯一截断政策；移除或降级为「派生自政策」的重复硬截（如 `MAX_HISTORY` 改为 Pack 输出长度） | 代码审查通过 |

**明确不做（P0）**：合并 Clarification/Contextualizer 的 LLM 调用；偏好表；规则后台。


### 5.2 P1 — 理解入口合并

**目标**：一次 Understanding，两个出口（clarify / retrieve）。

| ID | 需求 | 验收 |
|----|------|------|
| P1-1 | 抽取共享判定：`underspecified` / `context_dependent` / 主干 wide-terms / 比较题跳过等，单一模块供澄清与改写使用 | rag 不再私有 import clarification 下划线函数 |
| P1-2 | `DialogueUnderstanding.analyze(...)` 统一入口；内部可编排「先判澄清，再改写」但对外一个 Result | API/RagChain 只依赖该入口 |
| P1-3 | 有 history 时废除第二套 `_simple_rewrite` 主路径；无 history 时 `resolved_question=question` 或轻量规则 | 无双路径改写分叉 |
| P1-4 | 实体保护只在 Understanding 出口执行一次；下游只消费已保护 queries | 去掉重复 protect 或改为断言 |
| P1-5 | 清理 clarification unused compat 参数（`rules_path`/`max_options`/`catalog` 等）或正式接入（若与歧义规则 PRD 合流则标注依赖） | 无死参数或文档标明延期原因 |
| P1-6 | Understanding 全量写入 qa_trace | 调试页可展示 mode/queries/filters/focus |

**与偏好 PRD 挂接（可选开关）**：若偏好服务已存在，Understanding 在 `mode` 决策前查询偏好；命中则直接 `retrieve` + filters。本 PRD 不实现偏好存储。


### 5.3 P2 — 结构化短记忆（质量增强）

**目标**：检索与生成不再依赖「6×200 聊天原文」，而依赖结构化焦点。

| ID | 需求 | 验收 |
|----|------|------|
| P2-1 | `dialogue_focus`：当前主题、已确认实体、未决问题（短字段或 ≤N 字） | 字段进入 Session 与 trace |
| P2-2 | 检索侧输入改为 `dialogue_focus + last_sources + recent turns(少量)`，替代长 history dump | 对比延迟与锚点命中 |
| P2-3 | `rolling_summary` 改为结构化或半结构化（主题/实体/结论），禁止无约束散文复述 | Prompt 与单测约束 |
| P2-4 | 用 qa_traces 的 `history_rounds` 分布验证是否值得同步摘要；不足则保持 P0 降级策略 | 数据驱动决策记录 |

**P2 前置**：P0/P1 完成且无严重回归。

## 六、Prompt 与安全约束

1. System 继续声明：历史/摘要/实体提示 **不能当事实**；仅检索 context 与标注的外部来源可引用。
2. `resolved_question` 默认 **不替换** 用户可见提问；如需在 system 注入「当前解析焦点」，使用独立小节（如 `dialogue_focus`），避免模型以为用户改口。
3. 摘要 Prompt 限制：只保留主题、已确认实体、未决问题；禁止编造知识库结论。
4. 澄清选项文案不得暗示「未选实体也已确定」。

|------|------|
| 独立问题（无指代） | 不错误挂历史来源锚点 |

| 同步摘要（若启用） | 超时上限可配；超时必须走 truncate_recent |


## 九、风险与开放问题

| 风险 | 影响 | 缓解 |
|------|------|------|
| 合并 Understanding 导致澄清过多/过少 | 体验回归 | 先共享判定函数，再合并 LLM；用固定题集对比 |
| 同步摘要阻塞首包 | 流式体验变差 | 默认 truncate_recent；摘要仅缓存命中同步使用 |
| 前端多入口（Chat / QaDebug）契约漂移 | 锚点再次丢失 | 单一 `buildChatHistoryPayload` 工具函数 |
| 与偏好/规则 PRD 并行开发冲突 | 重复造轮子 | Understanding 为唯一挂接面；存储类需求不进本 PRD |
| 长会话真实分布未知 | P2 可能过度设计 | 先用 qa_traces 统计 rounds，再开 P2 |

**开放问题（实施前需确认）**：

1. 压缩未命中时，产品更倾向 **同步短摘要** 还是 **截断最近 K 轮**？（默认建议：截断，摘要仅缓存命中。）
2. Session 是否落库（chat_storage）还是纯请求级？建议 Phase 0 请求级；若已有服务端 chat history，可只存 Session 增量字段。
3. 同步 `POST /query` 是否升级为与 stream 同级完整管线，还是正式降级为内部/兼容接口？
