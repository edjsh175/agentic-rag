## 2. 背景与问题

### 2.1 当前问题

早期图谱采用：

```
Document Chunk
      │
  LLM Extract
      │
    Entity
```

导致：

#### 1. 实体扁平化
例如：
```
PipelineBuilder
 ├─ 材质映射
 ├─ 坐标转换
 ├─ 管线点表
 ├─ Redis
 └─ 端口6379
```
所有节点处于同一层级，导致：
- 无法回答产品能力问题
- 无法理解业务结构
- 检索范围不可控

#### 2. 来源结构丢失
文档作者设计的组织结构：
```
PipelineBuilder用户手册
 3 数据管理
   3.1 材质映射
 4 工程设置
   4.1 坐标配置
```
原本包含有价值的知识分类，旧架构未予以利用。

#### 3. LLM 直接定稿分类体系
若允许 LLM **不经审核** 自由写入正式 FunctionArea（如 *数据管理*、*数据处理*、*数据配置*、*数据维护*），会造成：
- 同义节点冗余
- 分类漂移
- 图谱无节制膨胀

> **v2.1 澄清**：禁止的是「LLM 直接定稿正式功能区」，不是禁止 LLM **提议**功能区候选。主干若缺少功能区挂点，又完全禁止提议，叶子只能扁平堆叠或乱挂到 Tool——同样导致凌乱。

## 3. 总体设计原则

### 原则一：知识分层
系统中的信息分为：

| 层级 | 职责 | 可信度 |
| ---- | ---- | ----- |
| Product Backbone | 产品事实关系 | ★★★★★ (Level 0) |
| FunctionArea Registry | 产品能力分类 | ★★★★☆ (Level 1) |
| Knowledge Entity | 具体知识 (Feature/Procedure/Constraint) | ★★★☆☆ (Level 2) |
| Document Evidence | 事实出处出处 | ★★☆☆☆ (Level 3) |

### 原则二：LLM 不负责**定稿**知识体系（可提议、须确认）
- **允许 LLM**：抽取业务实体、建立实体间关系、补充属性描述；在已有 Tool/Service 下 **提议** FunctionArea 候选；为叶子给出挂载判断。
- **禁止 LLM**：创建/修改 Product；修改 Product Backbone 正式归属；**不经人工确认** 将 FunctionArea 直接写入正式注册表/正式图谱。
- **FunctionArea 正式入库路径**：一律 **候选 + 人工确认**（见 §5 Level 1、§8）。

### 原则三：来源参与建模，但不污染业务模型
文档结构（Section/Document）不是业务实体，但可以：
- 提供分类候选
- 提供检索路由
- 提供证据链条

内容在 Chunk；产品侧实体与文档侧 Section 都是指路牌，可指向同一批 Chunk，但职责不同——**不得合并成同一节点**，也**不要求**每个业务实体都有同名 Section 克隆。

### 原则四：挂载按需、禁止乱挂
- **有正确挂点**（已有正式 FunctionArea / 合法父实体，且证据支持）→ **必须挂上**。
- **没有正确挂点**（功能区尚未确认入库、上下文不足以判断归属）→ 标为 **未归属**，允许暂不挂；**禁止**为消孤点而跳级乱挂到 Tool/Product，或发明未确认的正式分类。
- **证据不足** → **拒收**该次挂载断言（实体本身是否保留见 §8.2）。

```
                               │

                               │
                            Evidence
```

## 5. 产品知识图谱设计

### Level 0：Product Backbone
- **来源**：`domain_catalog.json`、`product_relation_backbone.json`
- **特点**：人工维护，不允许自动修改，全系统最高优先级。
- **结构**：`Product ── belongs_to ──> Tool / Service`
- **说明**：主干**不强制**预置全部 FunctionArea；功能区主要通过注册表建设（§5 Level 1）。缺少挂点时走「提议候选 → 人工确认」，而不是让叶子永久扁平或乱挂。

### Level 1：FunctionArea Registry
- **定义**：表示产品能力区域（如 *数据管理*、*工程设置*、*服务部署*、*高级配置*）。
- **正式来源（候选 + 人工确认）**：
  1. 从 `Document Section` 提炼候选；和/或
  2. LLM 在抽取时 **提议** FunctionArea 候选（须 scoped 到已有 Tool/Service，如 `PipelineBuilder::数据规范`）；
  3. 经 `FunctionAreaClassifier` / 规则直匹 / 去重合并（可选自动化辅助）；
  4. **人工确认** 后写入 `data/function_area_catalog.json` 与正式图谱。
- **禁止**：LLM 或规则管线绕过确认，把新功能区直接当成正式 Level 1 定稿。

### Level 2：Feature 层 (能力实体)
- **定义**：回答 **“产品有什么能力”**（例如 *材质映射*、*数据检查*、*坐标转换*）。Feature 描述能力而非单一操作。

### Level 3：Knowledge Entity (知识实体)
- **Procedure**：回答 **“怎么做”**（例如 *创建工程流程*、*导入管线数据*）。
- **Constraint / ConfigItem**：回答 **“限制与参数”**（例如 *EPSG:4490*、*端口 10605*、*文件格式 shp*）。
- **Data Entity**：例如 *管线点表*、*管线线表*、*字段结构*。
- **Command**：例如 *启动命令*、*配置命令*。

## 6. 文档知识图谱 (Document Graph)

文档图谱不参与产品业务分类，结构为：
$$\text{Document} \longrightarrow \text{Section} \longrightarrow \text{Chunk} \longrightarrow \text{Evidence}$$

- **作用**：定位原文、引用回答、调试抽取、版本追溯。
- **Section ≠ Chunk**：Section 是目录节点；Chunk 是正文切片。一个 Section 可对应多个 Chunk。

---

## 7. 两图连接方式 (语义桥接)

1. **`Entity ── derived_from ──> Chunk`**：表示“这个知识来自哪里”。
2. **`Chunk ── mentions ──> Entity`**：表示“文本或表格提到了什么”。
3. **`Section ── suggests ──> FunctionArea`**：表示“文档结构帮助发现能力分类”（弱关联，非强归属；可作为功能区**候选**信号，不经确认不得当正式归属）。

---

## 8. LLM 抽取规范

### 8.1 输入与类型

- **LLM 输入**：包含 `当前Chunk` + `Product Backbone` + `FunctionArea Context`（已确认正式区只读列表 + 可选「可提议新候选」说明）+ `Feature Context`。
- **允许输出（业务叶子）**：`Feature`、`Procedure`、`Constraint`、`Command`、`DataTable`、`Error`、`Solution` 等 Schema 允许的叶子类型。
- **允许输出（功能区）**：`FunctionArea` **仅作为候选**（candidate / staging），不得在无确认门禁下 apply 进正式注册表。
- **禁止输出/禁止定稿**：`Product`；修改 Backbone 正式 `belongs_to`；把未确认 FunctionArea 当作已可挂载的正式父节点去「假挂载」叶子。

### 8.2 挂载决策（三种结果，必须显式）

对每个抽取出的、**需要归属**的业务实体，抽取结果必须落入且仅落入下列之一：

| 结果 | 含义 | 处理 |
| ---- | ---- | ---- |
| **挂上** | 存在已确认的正确挂点，且证据支持 | 写出 `belongs_to` / `has_procedure` / `has_table` 等合法结构边 |
| **未归属** | 当前没有正确挂点，或不应强行归属 | 实体可保留为待挂载；**不写**猜测性归属边；可同时输出 FunctionArea **候选**供人工确认 |
| **证据不足拒收** | 连「这是什么实体 / 是否该有挂载」都证据不够 | 拒收该断言（或整条候选）；禁止用噪声边凑拓扑 |

**钉死口径**：有正确挂点必须挂；没有就标未归属，禁止乱挂。
不是「所有 LLM 实体都必须挂上」，而是「该挂的挂对；不该硬挂的不要挂」。

### 8.3 挂载主路径：语义判断，而非标题字符串

- 挂载与表实体识别的**主路径**是：Chunk 正文 + section 上下文 + 已确认 FunctionArea 列表上的**语义判断**（LLM / 经确认的分类结果）。
- **实现债声明（非本 PRD 主张）**：以路径段 `endswith("表")`、被标题末尾 `：` / `:` 等标点绊倒、或其它脆弱字符串规则作为 DataTable 创建/挂载的**唯一**依据，属于实现偏离，应退役或降为弱辅助信号，不得当作架构口径。

## 9. Few-shot 规范

必须包含下列显式示例：

1. **正确拓扑**：`PipelineBuilder` $\rightarrow$ `数据管理`（已确认 FunctionArea）$\rightarrow$ `材质映射`。
2. **禁止跳级乱挂**：当已存在可用 FunctionArea 时，拒绝 `材质映射 ── belongs_to ──> PipelineBuilder`。
3. **禁止把未确认分类当正式父节点**：拒绝在未入库注册表的情况下，把 LLM 随口起的 `数据处理模块` 当成正式挂载目标；应输出 FunctionArea **候选** + 叶子 **未归属**（或待确认边），而不是假正式树。
4. **无挂点 → 未归属**：上下文表明是业务叶子，但尚无已确认 FunctionArea 可挂时，输出实体 + `mount_status=unassigned`（或等价字段），可附带 FunctionArea 候选提议。
5. **证据不足 → 拒收**：标题噪声或正文不足以支持实体/挂载时，不输出假关系。

---

## 10. 去重与实体指纹策略

实体唯一性指纹算法：
$$\text{Fingerprint} = \text{SHA256}(\text{canonical\_name} + \text{entity\_type} + \text{parent\_context})$$
允许 `Redis` (EnvironmentComponent, StampServer) 与 `Redis` (Service, PipelineBuilder) 在不同父上下文下合法共存。

FunctionArea 候选去重：同一 Tool/Service 下近义区名须合并或人工二选一后，方可确认入库，避免注册表膨胀。

---

## 11. 检索架构 (Graph RAG Routing)

1. **产品能力问题**（“PipelineBuilder 有哪些功能？”）：
   $$\text{Product} \longrightarrow \text{FunctionArea} \longrightarrow \text{Feature}$$
2. **操作流程问题**（“如何创建工程？”）：
   $$\text{Feature} \longrightarrow \text{Procedure} \longrightarrow \text{Chunk}$$
3. **参数配置问题**（“默认端口是多少？”）：
   $$\text{Constraint} \longrightarrow \text{Chunk}$$

未归属实体不进入「按功能区浏览」的主路径，但可通过证据桥（Chunk）被检索命中；确认功能区并完成挂载后，再纳入结构化路由。

---

## 12. 信任模型与验收指标

### 信任模型
- **Level 0 (Product Backbone)**：★★★★★
- **Level 1 (FunctionArea Registry，仅已确认)**：★★★★☆
- **Level 2 (Feature / Entity)**：★★★☆☆
- **Level 3 (Document Evidence)**：★★☆☆☆
- **FunctionArea / 挂载候选（未确认）**：不参与正式信任路由，仅供审批

### 验收指标
1. **图谱质量**：已确认 FunctionArea 无未治理的近义重复；**无「该挂未挂」且有明确挂点的业务实体**；无跳级乱挂边；允许统计意义上的 **未归属** 队列存在，但须可列出、可清。
2. **挂载决策完备**：抽样 LLM 候选中，需要归属的实体均显式标注为「挂上 / 未归属 / 拒收」，禁止默示孤点又不说明原因。
3. **功能区门禁**：不存在「LLM 直写正式 FunctionArea、跳过人工确认」的 apply 路径。
4. **完全可解释**：任何回答均支持 $\text{Answer} \rightarrow \text{Entity} \rightarrow \text{Chunk} \rightarrow \text{Document}$ 确定性追溯。
