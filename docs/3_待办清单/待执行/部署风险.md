---

# 一、最高优先级风险（建议立即处理）

## 1. 镜像版本管理混乱

### 当前问题

目前类似：

```bash
rag-backend:cpu-no-reranker
```

这种标签。

问题：

- 标签没有版本号
- 不知道生产运行的是哪一次构建
- 后续重新 build 会覆盖旧镜像
- 出问题难以回滚

例如：

今天：

```text
rag-backend:cpu-no-reranker
```

是版本 A。

明天：

```text
rag-backend:cpu-no-reranker
```

被重新构建成版本 B。

生产无法判断当前到底是哪一个。

---

## 建议

改成版本化：

例如：

```text
rag-backend:2026.07.14
rag-backend:2026.07.14-a3f92d
```

生产运行：

```bash
docker run ... rag-backend:2026.07.14
```

不要依赖：

```text
latest
```

---

# 2. 数据和镜像耦合风险

## 当前问题

容易混淆：

- 镜像
- 数据
- 配置
- 知识库

例如：

```
rag-backend 镜像
    |
    ├── Python代码
    ├── 依赖
    ├── rag_knowledge
```

但是：

```
/data/rag_python
    |
    ├── config.ini
    ├── chroma_db
    ├── rag_relational.db
    ├── file_index.json
```

属于运行数据。

---

## 风险

如果误操作：

```bash
docker rm
docker rmi
```

可能导致：

- 程序没了
- 知识库没了
- 图谱没了

---

## 建议

长期固定：

```
镜像：
/data/docker_images

代码：
/opt/rag

配置：
/data/rag_python/config.ini

知识库：
/data/rag_python/chroma_db

图谱：
/data/rag_python/data/rag_relational.db

原始文档：
/data/apache-tomcat-9.0.89/webapps/zsltStaticData
```

明确职责。

---

# 3. 数据库 Schema 版本风险

## 当前暴露问题

你遇到：

```text
no such column: reviewed_by
```

说明：

代码认为：

```sql
reviewed_by
```

存在。

但是数据库：

```sql
relations
entities
extraction_candidates
```

没有这个字段。

---

## 本质问题

代码版本：

↓

数据库结构版本

没有绑定。

---

## 风险

未来：

新镜像上线：

```text
代码版本 B
```

但是：

生产数据库：

```text
schema A
```

可能直接启动失败。

---

## 建议

增加：

```
schema_version
migration
```

机制。

例如：

数据库：

```
schema_version=5
```

启动：

```python
if schema_version < current:
    run migration
```

类似：

```
v1
 |
v2 增加review_status
 |
v3 增加profile_sync
```

# 4. 部署过程依赖人工操作太多

## 当前情况

大量手动：

```bash
docker run \
-v xxx \
-v xxx \
-e xxx
```

然后：

复制文件

修改配置

执行 SQL

---

## 风险

人为漏步骤。

例如：

忘记：

```bash
-v /data/rag_python/data:/app/data
```

结果：

容器启动正常。

但是：

图谱为空。

---

## 建议

写部署脚本。

例如：

```
deploy/
├── start.sh
├── stop.sh
├── backup.sh
├── rollback.sh
└── verify.sh
```

以后部署：

```bash
./start.sh
```

自动完成：

- 创建目录
- 检查配置
- 启动容器
- 健康检查

# 5. 前端 HTTPS → 后端 HTTP 风险

## 当前结构

现在：

浏览器：

```
https://192.168.10.206:8004
```

后端：

```
http://192.168.10.206:10605
```

---

## 风险

浏览器可能阻止：

```
Mixed Content
```

表现：

网页能打开。

但是：

点击查询失败。

---

## 推荐结构

改成：

```
浏览器
 |
 HTTPS
 |
Nginx:8004
 |
/api代理
 |
rag-service:10605
```

前端：

请求：

```
/api/query
```

而不是：

```
http://192.168.10.206:10605/query
```

优势：

- 无跨域
- 无 HTTPS 问题
- 后端端口不用暴露

```
docker-compose.yml
```

但是实际部署：

```bash

```

## 风险

两套配置可能逐渐漂移。

例如：

compose：

```yaml
environment:
 RERANKER=false
```

但是：

docker run：

忘记写。

---

## 建议

生产统一：

方案 A：

全部使用 compose。

方案 B：

生成固定：

```
docker-run-prod.sh
```

不要人工输入。

# 7. 配置文件管理风险

## 当前：

```
config.ini
```

里面可能包含：

- IP
- 模型地址
- 密钥
- 数据路径

---

## 风险

如果打进镜像：

泄露。

如果多人复制：

配置漂移。

---

## 建议

分三个文件：

```
config.example.ini
    ↓
开发模板

config.test.ini
    ↓
测试环境

config.prod.ini
    ↓
生产环境
```

生产配置只存在服务器。

# 9. 本地知识库误带入生产

## 当前容易犯的问题

把：

```
chroma_db
rag_relational.db
file_index.json
```

一起打包。

---

## 风险

生产出现：

```
公司文档
+
你的测试文档
```

污染。

---

## 正确方式

迁移：

代码：

复制。

规则：

复制。

知识库：

生产重新生成。

流程：

```
上传公司文档

↓

scan

↓

chunk

↓

embedding

↓

chroma

↓

graph extraction

```

# 10. 图谱 apply 流程缺少正式审批机制

## 当前

你手动：

SQL:

```sql
update extraction_candidates
set status='approved'
```

---

## 风险

绕过：

- 审计
- 校验
- 状态机

---

## 建议

增加正式命令：

例如：

```bash
graph approve \
--batch xxx
```

而不是直接改数据库。

---

# 11. 图谱和向量库生命周期没有绑定

当前：

```
Chroma
    chunk_id

SQLite
    entity_chunk_links
```

存在关联。

---

## 风险

如果：

删除 Chroma。

重新扫描。

chunk id变化。

那么：

旧图谱链接失效。

---

## 正确顺序：

重建：

```
清空旧知识库

↓

重新scan

↓

重新embedding

↓

重新extract

↓

重新apply graph

```

不能只重建其中一个。

整体评价：

你现在这套流程已经达到了**“可以部署”的水平**，但是还属于**实验环境 → 生产环境过渡阶段**。
