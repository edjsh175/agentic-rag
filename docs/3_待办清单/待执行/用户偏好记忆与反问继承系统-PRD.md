## 一、项目概述

### 1.1 项目背景

系统已具备预检索反问（Query Clarification）功能，当用户提问模糊或存在歧义（如询问“飞行物体”）时，智能体会弹出选项卡片供用户选择方向。然而当前机制存在以下问题：
* **重复打扰**：同一用户在同一会话或多次对话中多次询问相同概念时，系统每次均弹出反问卡片。
* **缺乏偏好感知**：业务人员（如特定模块的维护人员）通常只关心其负责的业务领域，反复选择相同选项降低了交互效率。

### 1.2 项目目标

构建**用户偏好记忆与反问继承系统**：
1. **自动记忆**：当用户在反问卡片中完成选项点击后，系统自动持久化该偏好记忆。
2. **跨会话自动继承**：再次提问相似或相同歧义问题时，系统自动匹配并继承历史偏好过滤条件，跳过显式反问步骤。
3. **可衰减与可重置**：偏好具备使用计数与时间衰减属性，并在前端提供重置/切换偏好的显式入口。

### 1.3 系统角色定义

| 角色 | 职责 | 使用场景 |
|------|------|----------|
| **普通用户** | 提问、点击反问卡片、显式重置偏好记忆 | 日常问答 |
| **智能体服务** | 自动记录偏好、评估记忆匹配度、执行过滤继承 | 检索前预处理 |
| **系统管理员** | 查看偏好命中率统计、清理过期偏好数据 | 运维后台 |


## 二、总体架构与数据流转

### 2.1 架构层级

```
┌─────────────────────────────────────────────────────────────────────────────────────┐
│                                用户交互层（前端）                                    │
│   对话界面 (ChatView)  │  反问卡片  │  当前偏好提示徽章 (Badge)  │  偏好重置按钮            │
└─────────────────────────────────────────────────────────────────────────────────────┘
                                         │
┌─────────────────────────────────────────────────────────────────────────────────────┐
│                             智能体核心层（Agent Core）                               │
│  ┌───────────────────────┐   ┌────────────────────────┐   ┌──────────────────────┐  │
│  │ 意图与问题哈希计算器  │ → │ 偏好匹配服务 (Memory)  │ → │ 反问决策器 (Clarify) │  │
│  └───────────────────────┘   └────────────────────────┘   └──────────────────────┘  │
│                                                                                     │
│  逻辑：存在高置信偏好 → 跳过 Clarification 卡片 → 隐式注入 Preference Filter        │
└─────────────────────────────────────────────────────────────────────────────────────┘
                                         │
┌─────────────────────────────────────────────────────────────────────────────────────┐
│                                  数据层（Storage）                                   │
│  ┌──────────────────────────────────────────────────────────────────────────────┐   │
│  │ 关系数据库 (SQLite) - 表: user_preferences                                   │   │
│  └──────────────────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 数据流转总览

| 阶段 | 触发动作 | 数据流转 |
|------|---------|----------|
| **记录** | 用户点击反问卡片的某个选项 | 用户ID + 问题摘要Hash + 选项Filter → 写入/更新 `user_preferences` 表 (hit_count + 1) |
| **继承** | 用户发起新提问 | 提问文本 → 计算哈希 → 查询 `user_preferences` → 命中高频偏好 → 隐式附加 `doc_category`/`entity_name` 过滤 |
| **重置** | 用户在前端点击“清除此领域的偏好” | 用户ID + trigger_entity → 软删除或清除该偏好条目 |


## 三、数据层详细设计

### 3.1 关系数据库表结构：`user_preferences`

| 字段名 | 类型 | 必填 | 默认值 | 说明 |
|--------|------|------|--------|------|
| `id` | VARCHAR(36) | 是 | UUID | 主键 |
| `user_id` | VARCHAR(64) | 是 | — | 用户标识（如用户名或设备ID，默认 `default_user`） |
| `trigger_entity` | VARCHAR(200) | 是 | — | 触发歧义的实体/关键词（如 `飞行物体`、`pipeline`） |
| `question_hash` | VARCHAR(64) | 是 | — | 问题的规范化 MD5/SimHash |
| `chosen_label` | VARCHAR(200) | 是 | — | 用户选择的选项文本 |
| `chosen_filter_json` | TEXT | 是 | `{}` | 用户选择的过滤参数 JSON (`doc_category`, `entity_name`) |
| `hit_count` | INT | 是 | 1 | 被成功使用/继承的累计次数 |
| `confidence_score` | FLOAT | 是 | 1.0 | 偏好置信度（随时间与显式覆盖动态计算） |
| `created_at` | TIMESTAMP | 是 | Current | 创建时间 |
| `last_used_at` | TIMESTAMP | 是 | Current | 最后一次更新/继承时间 |

### 3.2 索引设计

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_user_trigger ON user_preferences(user_id, trigger_entity);
CREATE INDEX IF NOT EXISTS idx_user_qhash ON user_preferences(user_id, question_hash);
```


## 四、功能详细设计与后端 API

### 4.1 偏好匹配与自动继承逻辑

当 `QueryClarificationService.analyze` 执行时：
1. 提取用户提问中的触发实体 `trigger_entity`。
2. 查询 `user_preferences` 表：匹配 `user_id` 与 `trigger_entity`。
3. 若存在记录且 `confidence_score >= 0.6` 且 `last_used_at` 在 30 天内：
   * 自动跳过向前端返回卡片。
   * 构造返回 `ClarificationResult(needs_clarification=False, auto_inherited=True, inherited_filter=chosen_filter_json)`。
   * 异步更新 `hit_count = hit_count + 1` 和 `last_used_at = now()`。

### 4.2 API 接口定义

#### 接口 1：记录用户偏好选择
* **HTTP 请求**：`POST /api/clarification/preference`
* **Request Body**：
```json
{
  "user_id": "user_001",
  "trigger_entity": "飞行物体",
  "question": "飞行物体怎么配置",
  "chosen_label": "运维后台配置",
  "chosen_filter": {
    "doc_category": "部署运维"
  }
}
```
* **Response**：`{"status": "ok", "message": "偏好已记录"}`

#### 接口 2：查询/清除用户偏好
* **HTTP 请求**：`DELETE /api/clarification/preference`
* **Query Params**：`user_id=user_001&trigger_entity=飞行物体`
* **Response**：`{"status": "ok", "message": "偏好已清除"}`


## 五、前端交互与页面设计

### 5.1 对话界面 (ChatView) 交互增补

1. **自动继承提示徽章 (Badge)**：
   * 当答案是通过历史偏好自动继承生成时，在答案头部显示轻量提示框：
     `已根据您的历史偏好按[部署运维]分类过滤 [切换方向]`。
2. **切换/重置偏好按钮**：
   * 点击 `[切换方向]` 时，触发删除该偏好并重新弹出歧义选项卡片。


## 六、业务流程详细说明

```
【用户发起提问】
   ↓
① 智能体解析 trigger_entity
   ↓
② 查询 user_preferences 是否存在记录？
   ├─【存在高置信偏好】 ──> 隐式注入 chosen_filter ──> 执行检索 ──> 头部附带[已继承偏好]提示
   └─【不存在/已过过期】 ──> 弹出歧义选项卡片 ──> 用户点击选项 ──> 异步写入 user_preferences ──> 执行检索
```


## 七、非功能性需求与界面规范

* **界面与内容禁用 Emoji 规则**：前端 UI 界面、对话交互卡片、系统提示文本、控制台输出及后端日志中，一律禁止使用 Emoji 表情符号（如字符画、表情图标等），必须使用纯文本标点或标准 SVG/矢量 Icon 组件。
* **性能要求**：偏好查询时延 ≤ 10ms，写入使用异步后台任务，不增加回答生成时延。
* **数据清理**：超过 90 天未使用的偏好记录，定时任务自动将 `confidence_score` 衰减，低于 0.2 时清除。


## 八、实施优先级与验收标准

* **实施周期**：第 1 周完成后端 DDL 与 API，第 2 周完成前端 Badge 交互。
* **验收标准**：
  1. 用户在对话中对“飞行物体”选择“部署运维”后，第二次提问相同问题直接生成回答，不再弹出卡片。
  2. 答案顶部清晰标注继承的方向，点击重置后恢复弹出卡片。
  3. 全界面与交互提示中无任何 Emoji 符号。
