### P0-2：`/rebuild` 同时支持 GET 和 POST，且会触发清库重建

**影响**

这是当前最危险的生产风险之一。`GET /rebuild` 被浏览器访问、预加载、爬虫、误点链接或监控探测触发时，可能直接清空 Chroma 集合和文件索引，然后重新扫描。当前锁只能防并发，不能防误触发。

**证据**

```text

rag_knowledge/api/routes.py:542:    重建知识库 —— 清空向量数据库 + 文件索引，然后全量重新扫描
rag_knowledge/api/routes.py:549:    注意：此操作不可逆，执行后所有已有问答数据将被清空
rag_knowledge/api/routes.py:552-560: RebuildCoordinator(...).run()
```

实际执行路径会清 Chroma、重置 index：

```text

rag_knowledge/services/rebuild_coordinator.py:59:self._scanner.reset_index()
rag_knowledge/repository/vector_store.py:347:store.delete_collection()
```

**建议修复**

- `/rebuild` 改成 **POST-only**。
- 增加显式确认参数，例如 `confirm=true`、`operation_id` 或管理员 token。
- 更稳妥方案：拆成 `/rebuild/plan` 与 `/rebuild/execute` 两步，先输出影响范围，再执行。
- GET 不允许有任何破坏性副作用。

### P0-3：重建流程非原子，失败后可能留下“空库 + 半残 index”

**影响**

当前流程只备份 `file_index.json`，然后先清 Chroma，再重置 index，再扫描。如果扫描、embedding、Chroma 写入或一致性校验中途失败，正式知识库已经被清掉，恢复成本高。SQLite 图谱也没有随重建做一致快照。

**证据**

```text
rag_knowledge/services/rebuild_coordinator.py:46-48: 仅备份 file_index.json
rag_knowledge/services/rebuild_coordinator.py:57: self._store.clear()
rag_knowledge/services/rebuild_coordinator.py:59: self._scanner.reset_index()
rag_knowledge/services/rebuild_coordinator.py:60: result = self._scanner.scan()
rag_knowledge/services/rebuild_coordinator.py:61: self._consistency_service.assert_consistent()
```

`reset_index()` 会直接写入空索引：

```text
rag_knowledge/services/scanner.py:156:self._index = {"version": 1, "files": {}}
rag_knowledge/services/scanner.py:157:self._save_index()
```

**建议修复**

- 重建改成两阶段提交：新建临时 Chroma collection/临时 index，扫描成功并通过一致性校验后再切换正式 collection。
- 最低限度也要在执行前同时备份 `file_index.json`、Chroma 目录、SQLite 图谱库。
- 失败时应自动回滚，不能只写 `rebuild_state.json`。

## P1：架构职责错误

### P1-1：领域事实仍写在 Retrieval Profile 里，形成多个事实源

**影响**

`retrieval_intent_profiles.json` 里存了 alias、章节族、召回词、偏好来源、同级惩罚组。这些已经不只是“检索策略”，而是领域事实。这样会导致事实同时存在于 Profile、Graph、代码规则中，后期维护会分裂：图谱里改了 alias，但 Profile 仍然可能把检索拉回旧事实。

**证据**

```text

Profile 会参与 query 扩展和质量分调整：

rag_knowledge/services/retrieval_intent.py:51-66: apply_quality_scores() 修改 quality_score
```

**建议修复**

- Profile 只保留策略参数，例如 `candidate_min_k`、是否扩大候选池、是否 rerank。
- `entity_aliases`、`section_families`、`sibling_penalty_groups`、`preferred_sources` 应迁入图谱或图谱种子数据。
- 短期做 `profile_to_graph_sync`，把这些 profile 事实转换成待审核候选，而不是直接参与检索打分。

## P2：Graph-RAG 一致性

### P2-1：职责大体有分层，但边界还不干净

**影响**

Graph Retriever、Entity Guard、Query Planner、Profile 各有职责，但 Profile 仍承担了图谱事实功能；Schema 也承担了领域词典功能。结果是 Graph-RAG 已经接起来了，但事实源没有完全统一。

**证据**

Query Planner 主要做意图分类和通用阶段词扩展，这部分职责合理。Graph Retriever 负责实体链接、图扩展、证据 chunk 加载、融合，这也合理。但 Profile 仍存 alias、section family、source preference；Schema 仍存具体产品词典。

**建议修复**

建立明确边界：

- Query Planner：只判断意图和检索参数。
- Profile：只放策略偏好，不放领域事实。
- Graph Schema：只放实体/关系类型和约束。
- Graph DB：唯一事实源，存 alias、different_from、belongs_to、has_table、has_field、defined_in。
- Graph Retriever：只消费图谱事实，不再从 Profile 读事实。

---

### P2-2：Graph Retriever 能利用图关系，但只能利用“已经进入图谱”的事实

**影响**

Graph Retriever 已经能利用 alias、different_from、belongs_to、has_table、has_field、defined_in 等关系；但如果这些事实还停留在 Profile，它就无法统一使用。也就是说 Phase C 的能力存在，但数据迁移没完成。

**证据**

关系扩展白名单：

```text
rag_knowledge/services/graph_retrieval.py:418-425:
procedure/deployment/config/definition/comparison/troubleshooting 对应不同 relation allowlist
```

方向规则支持：

```text
rag_knowledge/services/graph_retrieval.py:448-490:
belongs_to / uses_config / has_table / has_field / defined_in 的方向判断
```

图证据最后通过 chunk_id 取回：

```text
rag_knowledge/services/graph_retrieval.py:646-647:
collection.get(ids=list(context.chunk_ids), include=["documents", "metadatas"])
```

**建议修复**

做 `Profile → Graph migration/sync`：

- `entity_aliases` → `aliases`
- `section_families` → `Section` 实体 + `defined_in`
- `sibling_penalty_groups` → `different_from`
- `preferred_sources` / `fallback_sources` → 如果是事实，转成 `belongs_to` / `defined_in`；如果只是策略，保留在 Profile，但命名成 policy。
- `recall_terms` → 谨慎处理。它可能是字段名/关键词，不一定都是实体。能抽成 Field/alias 的进图谱，剩下的留作 query hint。

**影响**

Schema 里 `defined_in` 是 `Entity -> Document/Section`，但 GraphExpander 注释写成 `Entity defined_in Chunk`。虽然代码实际通过 `entity_chunk_links` 找 chunk，但这个注释会误导后续维护者把 `defined_in` 直接连到 chunk。

- 统一语义：`defined_in` 只连 Document/Section。
- chunk 证据统一走 `entity_chunk_links`。
- 把注释和质量检查都改成这个口径。

## P3：评测可信度

### P3-1：已有 dataset health check，但 stale chunk_id 仍可能被“软放过”

**影响**

现在健康检查已经能识别 chunk_id 是否存在、expected_targets 是否还能匹配，这是好设计。但如果 chunk_id 失效而 expected_targets 还能匹配，当前状态只是 warning，不一定阻断 A/B。严格 A/B 下，这会让历史 ID 失效问题被 content fallback 掩盖。

**证据**

健康检查存在：

```text
rag_knowledge/evaluation/runner.py:36-54: load() 默认调用 _check_health()
```

状态逻辑：

```text
rag_knowledge/evaluation/dataset_health.py:
status = "PASS" if invalid_questions == 0 else "BLOCK"
warnings.append("chunk ids are stale, but expected_targets still match current chunks")
```

**建议修复**

- 严格模式下，只要 `needs_chunk_id_refresh=True` 就阻断 A/B，除非显式传 `--allow-stale-ids`。
- 评测报告中单独输出 `chunk_id_health`、`target_health`，不要只看 Recall/MRR。

---

### P3-2：content fallback 会污染 recall 分母

**影响**

这是核心可信度问题。当前逻辑在 chunk_id 没命中时，如果 content fallback 命中，就把 `relevant` 改成 `matched_ids`。这等于把“检索出来的文档”反过来写成“标准答案集合”，Recall 的分母会变小，指标可能虚高。

**证据**

Fallback 改写 relevant：

```text
rag_knowledge/evaluation/runner.py:106-117:
if matched_ids:
    relevant = matched_ids
```

Recall 分母来自 `len(relevant_ids)`：

```text
rag_knowledge/evaluation/metrics.py:10-15:
return len(top_k & relevant_ids) / len(relevant_ids)
```

**建议修复**

- 不要在评测循环里把 `relevant` 替换为 `matched_ids`。
- 评测前先用 expected_targets 生成“当前库 chunk_id 映射”，刷新数据集。
- 或者评测时保留原始 `relevant_ids`，另算 `content_fallback_hit@k`，不要混入 Recall/MRR。

### P3-3：fail-on-regression 是 opt-in，不是默认防线

**影响**

`run_retrieval_ab.py` 支持回归检测，这是好的；但必须传 `--fail-on-regression` 才会失败。实际交付/CI 中如果忘了加这个参数，指标下降只会写入结果，不会阻止交付。

**证据**

```text

run_retrieval_ab.py: if regressions and args.fail_on_regression: raise SystemExit(...)
```

**建议修复**

- CI 脚本默认启用 fail-on-regression。
- 本地脚本可以保留 `--allow-regression` 作为反向参数。
- 把阈值、对比基线、数据集健康状态写进报告。

### P3-4：评测默认 `review_status=None`，与生产检索口径不一致

**影响**

生产检索默认只返回 approved；评测时不限制审核状态，会让 pending/rejected chunk 也可能参与检索。这样指标可能比真实线上表现更乐观，尤其在新资料刚入库未审核时。

**证据**

- `prod_eval`：`review_status="approved"`
- `audit_eval`：`review_status=None`

正式交付只看 `prod_eval`，`audit_eval` 用于诊断召回潜力。

1. **先处理 P0**：清理 untracked 文件；禁止 GET rebuild；重建流程加确认和原子性；评测脚本禁止默认覆盖。
