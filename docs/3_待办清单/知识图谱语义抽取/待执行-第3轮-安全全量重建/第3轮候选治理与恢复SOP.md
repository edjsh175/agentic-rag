# 第 3 轮候选治理与恢复 SOP

- **记录日期**：2026-07-16
- **适用范围**：`rebuild-safe --execute --include-llm` 执行后验收与异常处理
- **原则**：保护官方主干、保护人工事实、保护 profile_sync；低置信不阻塞 apply，但必须留痕。

## 1. 低置信候选处理

| 情况 | 处理 | 业务解释 |
|------|------|----------|
| 低置信实体 | 标记 `round3_deferred_pending` 后拒绝或保留待审 | 不让不确定实体污染正式图谱 |
| 低置信关系 | 标记 `round3_deferred_pending` 后拒绝或保留待审 | 不让弱关系带偏 GraphRAG |
| 证据不足 | 不进入 apply；记录样例 | 没有证据的事实不能支持问答 |
| 与主干邻近但不确定 | 待人工复核 | 官方产品关系附近宁可慢一点 |

## 2. 主干冲突判定

以下候选不得 apply：

1. 改写 `seed:product_backbone` 已确认的产品归属。
2. 否定或覆盖已确认的 `different_from` / 等价关系。
3. 把同名但不同类型的实体强行合并。
4. 把产品、模块、流程挂到错误上级。
5. 缺少 evidence_text 却试图覆盖已有受保护事实。

## 3. 禁止 approve-all 的业务原因

`approve-all` 的问题不是“命令危险”本身，而是它会把不同风险等级的候选混在一起放行。全库 LLM 候选里可能同时包含高置信实体、弱证据关系、旧文档残留、主干附近冲突边。业务上这等于让未经复核的内容进入知识图谱，再被 GraphRAG 用来影响问答。

本轮必须分拆审批：

1. 高置信实体优先。
2. alias 单独处理。
3. relation 按类型和置信度处理。
4. 主干冲突一律拒收。
5. 低置信候选留到人工补审。

## 4. 失败或中断后的恢复判断

| 情况 | 判断 | 动作 |
|------|------|------|
| execute 仍在运行 | 不处理半截库 | 等待完成或由人工明确停止 |
| execute 失败但有 timestamped 备份 | 可恢复 | 停进程后从本次备份恢复 |
| execute 失败且主干不完整 | 必须恢复 | 不在半截库上继续 apply |
| execute 完成但 quality BLOCK | 不进入第 4 轮 | 记录阻塞，按报告修复 |
| 只有低置信候选被拒绝 | 不阻塞 apply | 进入后续人工补审 |

## 5. 备份保护

不得覆盖：

1. `data/backups/rag_relational_pre_round3.db`
2. `data/backups/rag_relational_half_execute_aborted.db`
3. 本次 execute 生成的 timestamped 备份

恢复前必须先确认目标路径是正式库路径，并停止所有占用进程。
