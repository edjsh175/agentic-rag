## 四、Phase B：确定性规则抽取（当前阶段）

Phase B 不使用 LLM。只使用已有 Chunk 的 metadata、`section_path`、Markdown 表格和配置代码块生成可复查候选。

### Step 2：SectionPathExtractor

**目标**：从 `section_path + doc_category + source` 抽取图谱主干。

**输入字段**：

```text
chunk_id
content
source
doc_category
section_path
content_type
```

**示例一**：

```text
doc_category = StampTools
section_path = PipelineBuilder > 数据规范 > 管线点表
```

预期候选：

```text
StampTools -> Product
PipelineBuilder -> Tool
管线点表 -> DataTable

PipelineBuilder --belongs_to--> StampTools
PipelineBuilder --has_table--> 管线点表
管线点表 --defined_in--> Section/Chunk
```

**示例二**：

```text
doc_category = StampServer
section_path = 管线发布服务 > 服务配置
```

预期候选：

```text
StampServer -> Product
管线发布服务 -> Service
管线发布服务 --belongs_to--> StampServer
```

**执行任务**：

- [ ] Step 2.1：为上述两组黄金样例补失败测试。
- [ ] Step 2.2：实现或校正 `SectionPathExtractor`，仅返回候选，不写数据库。
- [ ] Step 2.3：实现 `dry_run` 输出，包括实体、关系、证据链接、诊断和统计。
- [ ] Step 2.4：从真实知识库抽取 50～100 个 Chunk。
- [ ] Step 2.5：导出 JSON，人工检查 PipelineBuilder、管线点表、管线发布服务。
- [ ] Step 2.6：修正规则误判后重复同一批 dry run，确保输出稳定。
- [ ] Step 2.7：人工确认通过后，才允许进入候选批次表；此步仍不直接写正式实体和关系。

**必须检查的风险**：

- [ ] PipelineBuilder 必须是 Tool，不能误判成 Service。
- [ ] 管线发布服务必须属于 StampServer，不能归到 StampTools。
- [ ] 文档标题和章节标题不能被错误当成业务实体。
- [ ] 所有业务实体必须带 `source_chunk_id` 和 `evidence_text`。

### Step 3：TableFieldExtractor

**目标**：从 Markdown 表格抽取字段级图谱。

示例：

```markdown
| 字段名 | 说明 |
|---|---|
| 管点编号 | 唯一识别码，全局唯一，必要字段 |
| 地面高程 | 管线点地表面的高程，单位为米，必要字段 |
```

预期候选：

```text
管线点表.管点编号 -> Field
管线点表.地面高程 -> Field

管线点表 --has_field--> 管线点表.管点编号
管线点表 --has_field--> 管线点表.地面高程
Field --evidence--> Chunk
```

**执行任务**：

- [ ] 为字段名、说明、必填、单位和值域建立表格样例测试。
- [ ] 仅在已识别 DataTable 上下文中抽 Field。
- [ ] 使用 `DataTableName.FieldName` 作用域命名，禁止跨表复用同名 Field。
- [ ] 保留字段说明、必填、单位、值域和 Chunk 证据。
- [ ] 无 DataTable 上下文时输出 `missing_table_context` 诊断。
- [ ] 对真实管线点表做小批量 dry run 并人工审查。

**完成标准**：同名字段在不同表中是不同实体；重复运行不产生重复字段或关系。

### Step 5：GraphBuilder 与候选审核流

**目标**：按固定顺序串联 Extractor，但先生成候选批次，不直接污染正式图谱。

**要求接口**：

```python
build_full(force_rebuild: bool = False)
build_incremental(chunk_ids: list[str])
dry_run(limit: int, filters: dict)
stats(batch_id: str)
export_json(batch_id: str, output: str)
```

**执行任务**：

- [ ] 固定执行顺序：SectionPathExtractor → TableFieldExtractor → ConfigBlockExtractor。
- [ ] 同一 Chunk 内共享上下文，使 Field 和 ConfigItem 能找到 owner。
- [ ] 候选按稳定 fingerprint 去重。
- [ ] 批次记录 snapshot hash、过滤条件、Chunk 数、候选数和诊断数。
- [ ] 支持 full、incremental 和 dry run。
- [ ] CLI 先于写入 API；Phase B 初期不开放 `/api/graph/build`。
- [ ] 支持候选导出、按 ID 批准/拒绝、拒绝原因和 approve-all。
- [ ] apply 前检查 pending 候选、关系端点、类型冲突和 evidence。
- [ ] 整批事务化应用，失败时全部回滚。
- [ ] apply 可安全重试，不重复实体、关系、字段和证据链接。

**验收命令**：

```powershell

.\venv\Scripts\python.exe run_graph_build.py export --batch <batch_id> --output data/graph-candidates.json

.\venv\Scripts\python.exe run_graph_build.py quality --batch <batch_id>
```

## 六、Phase D：LLM 抽取与大规模自动构建（最后实施）

LLM 只用于确定性规则难以覆盖的复杂关系：

```text
alias_of
different_from
requires
causes
solved_by
produces
consumes
```

### D1. 候选输出约束

- [ ] 使用固定 JSON Schema。
- [ ] 每条候选必须包含 `evidence_text`。
- [ ] 每条候选必须包含 `source_chunk_id`。
- [ ] 每条候选必须包含 `confidence`。
- [ ] 默认 `review_status = pending`。
- [ ] 本地校验实体类型、关系方向、证据原文和置信度。
- [ ] 无效 JSON、超时或证据不匹配只记录诊断，不中断批次。

### D2. 审核和上线约束

- [ ] LLM 候选不得自动写入正式图谱。
- [ ] 人工审核后才能 apply。
- [ ] 相同 chunk_hash 使用缓存，避免重复调用模型。
- [ ] 记录模型、Prompt 版本和抽取时间。
- [ ] 支持按模型或 Prompt 版本回滚候选批次。

### D3. 大规模构建门禁

- [ ] 先在黄金集评估 precision、recall 和证据正确率。
- [ ] 达到验收阈值后扩大到单产品。
- [ ] 单产品通过后才允许全知识库构建。
- [ ] 正式图谱仍以审核通过的数据为准。
