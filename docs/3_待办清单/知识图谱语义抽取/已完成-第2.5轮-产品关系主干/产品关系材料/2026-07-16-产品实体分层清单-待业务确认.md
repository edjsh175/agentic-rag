## 1. 本轮口径

### 1.1 实体纳入范围

本轮采用“功能实体 + 技术实体”口径，纳入：

- 产品、产品体系、客户端、服务端、工具集和管理平台。
- 工具、子工具、可复用处理能力和明确命名的输出类型。
- 服务、服务模块、服务对应的 `.so` 文件和服务提供的明确功能。
- 数据类别、数据资源类型、图层类型、交换格式和纹理格式。
- 渲染模式、渲染接口、图形 API、客户端形态和明确命名的渲染能力。
- 行业应用、应用子场景、二次开发能力、协议标准、运维模块和运行组件。

本轮不纳入：

- 安装命令、文件路径、端口号、配置键、配置示例值。
- 界面按钮、表单字段、管线数据库字段、EPSG 逐个编码值。
- 文档中的操作步骤、一次性故障处理动作和硬件推荐数值。

### 1.4 分层原则

- 每个实体只设置一个“主分类层”，跨层用途通过备注表达，避免重复造实体。
- 同一名称表示不同对象时分开登记。例如 `3DTiles` 数据格式与 `3DTiles服务` 不是同一实体。
- 同一 `.so` 在不同材料中使用不同服务名称时，先登记别名候选，不直接认定为同一产品。
- 用户手册正文标题优先于目录标题，目录名称保留为别名候选。
- 工具层使用 `StampTools用户手册` 的六个章节名作为一级工具规范名；其它名称、内部名和拼写变体不覆盖手册规范名。
- 渲染体系采用业务已确认的三分法：`ActiveX`、`StampUE`、`WebGL`。C++ API、WebRTC、DirectX、Vulkan、OpenGL 等只作为接口、传输方式或底层技术实体。
- 白皮书明确的官方核心结构仍是五层：工具集、系统数据、系统服务、客户端、业务应用。
- 二次开发、运维管理、运行部署属于材料中明确存在的支撑层，不宣称其属于白皮书官方五层。
- 标准规范与安全保障属于横向维度，不强行作为上下游链条中的一层。

## 7. 客户端与渲染层

### 7.1 三类渲染体系（业务确认）

渲染体系一级主干只保留以下三项。它们是产品/客户端体系，不与图形 API、开发接口或网络传输协议并列。

| 规范名 | 实体子类型 | 核心定位 | 原始材料依据 | 结论 |
|---|---|---|---|---|
| ActiveX | RenderingSystem | StampGIS 的 Windows 插件式客户端/渲染体系 | StampServer 手册明确称“ActiveX版本”“ActiveX插件”“StampGIS ActiveX界面”；PPT 第 36 页标注 StampGIS (ActiveX) | 业务确认的一级渲染体系；手册可直接佐证 |
| StampUE | RenderingSystem | 面向 UE 数据、Shader 和游戏引擎效果的 StampUE 前端/渲染体系 | StampTools 手册在 UEModelBuilder 章明确出现 StampUE、UE图层数据、Shader 重新生成及“StampUE前端” | 业务确认的一级渲染体系；手册可直接佐证 |
| WebGL | RenderingSystem | 浏览器免插件客户端/渲染体系 | 两本手册明确出现 StampWebGL、WebGL2 和 Cesium 浏览；白皮书明确称 WebGL 免插件前端渲染引擎 | 业务确认的一级渲染体系；手册和白皮书可直接佐证 |

### 7.2 ActiveX 与 StampUE 的共性和差异

| 对比维度 | ActiveX | StampUE | 当前判断 |
|---|---|---|---|
| 体系角色 | StampGIS 客户端及渲染体系 | StampGIS 客户端及渲染体系 | 两者同属渲染主干，不是工具、服务或单一图形 API |
| 客户端形态 | 手册明确为 ActiveX 版本、ActiveX 插件，界面资源使用 CEGUI | 手册明确称 StampUE 前端，围绕 UE 图层数据和 Shader 工作 | 两者不是同一个前端运行形态，不能合并为一个实体 |
| 数据与服务底座 | 使用 StampGIS 数据、服务和 StampManager 配置；手册明确三维数据库读写优化服务目前只支持 ActiveX | 使用 UEModelBuilder 编译发布的 UE 图层数据；是否覆盖 ActiveX 的全部服务能力，材料未明确 | 都属于同一 StampGIS 产品架构，但具体服务兼容范围不能凭相似性复制 |
| UE 资源兼容点 | UEModelBuilder 章多次说明 `lib_ax` 对 UE 蓝图节点、事件、颜色、旋转和材质操作的支持 | UEModelBuilder 章明确说明 StampUE 版本变化可能要求重新生成 Shader，且可由 StampUE 前端执行 | 同一章同时出现 `lib_ax` 与 StampUE，说明两套运行侧与 UE 数据链存在共同接口点；但材料未直接写明 `lib_ax = ActiveX`，该映射暂不固化 |
| 界面与交互 | CEGUI 是 ActiveX 插件必须资源；StampGIS ActiveX 界面支持 CEGUI | UE 蓝图、材质、粒子、灯光、Shader 等是手册明确的数据和效果链 | ActiveX 偏传统插件客户端集成；StampUE 偏 UE 内容和游戏引擎效果链 |
| 已明确的专有能力 | 支持椭球和正球；三维数据库读写优化服务当前仅支持 ActiveX，并配合 `generate_edit_active.dll` | 可对 UE 图层数据重新生成 Shader；前端可执行 Shader 生成 | 专有能力必须分别挂接，不能因为同属渲染体系而互相继承 |
| 尚未证实的内容 | C++ API、DirectX、OpenGL、DX9/DX11 与 ActiveX 的逐项归属未被材料直接写明 | WebRTC、Vulkan、云端渲染与 StampUE 的逐项归属未被材料直接写明 | 这些先作为技术叶子或候选关系，不做一级体系，也不强绑到某一分支 |

因此，图谱中应保留两类关系：一类表达 ActiveX 与 StampUE 都属于 StampGIS 渲染体系；另一类分别表达其专有客户端形态、数据链和能力。不能把二者建成别名，也不能把 ActiveX 的编辑能力自动复制给 StampUE。

| 等保安全 | 系统安全配置要求 | StampServer手册 | 属于部署安全，不作为产品服务 |

## 13. 冲突与待业务确认项

1. `数据安全服务` 在 PPT 中分别对应 `se_security.so` 和 `se_security_config.so`；StampServer 手册改为 `Port服务 -> se_port.so` 表达图层权限入口，三者不可自动合并。
2. `基础数据服务 -> se_sde.so` 与手册 `Apache数据服务 -> se_sde.so` 是否只是新旧名称，需要业务确认。
3. `基础搜索服务` / `三维搜索服务`、`基础分析服务` / `三维分析服务` 是否作为正式别名，需要业务确认。
4. Oracle 版本的 `se_db_query.so`、`se_publish_tool.so`、`se_city_plan.so` 与当前手册 `_pg` / 新模块名是版本变体还是独立服务，需要业务确认。
5. 工具层已确认以 StampTools 手册为准，因此一级主工具固定为六类；`Vector Builder`、`Visual Editor` 不进入当前工具主干，仅保留为 PPT 历史候选名称。
6. `TerrarainBuilder`、`PiplineBuilder` 与手册拼写不一致，不登记为规范名或正式别名；`ObliqueBuilder`、`PointCloudBuilder`、`ue_model_tools` 仅作名称对照，待出现正式材料后再决定是否写入 `aliases`。
7. “点云数据处理工具”按手册作为一个一级主工具，其 LAS 点云处理和 PLY / GLB 高斯处理拆为能力叶子，不拆成两个主工具。
8. 渲染体系已确认只分 `ActiveX`、`StampUE`、`WebGL`；`C++ API`、`WebRTC`、`DirectX`、`Vulkan`、`OpenGL`、`DX9/DX11` 不再作为同级渲染体系。
9. `lib_ax` 在 UEModelBuilder 章中承担 UE 蓝图解释和材质等操作，但原始材料没有直接写明 `lib_ax = ActiveX`，暂不建立等同或实现关系。
10. `云渲染三维基础平台`、`WebRTC`、`StampWebRTC` 与 `StampUE` 的正式归属关系需确认；当前仅把 WebRTC 作为传输技术叶子候选。
11. 架构截图使用“应急安防管理”，白皮书使用“应急管理”并另列“公共安全”，需确认正式应用名称和上下位关系。
12. `三维管线管理` 与 `地下基础设施管理` 可能是子应用和上位领域关系，暂不合并。
13. `BIM模型`、`BIM图层`、`BIM应用` 分属数据、资源和应用三个层面，后续图谱不得合并为同一实体。
14. `3DTiles`、`3DTiles服务`、`3DTiles服务配置` 分别是格式/标准、业务服务和运维模块，后续图谱不得用同一个无类型实体承载。
15. I3S 章节开头存在沿用 3DTiles 描述的疑似文案错误，但后文明确是 I3S 服务且当前仅支持管线数据，按 I3S 服务登记并保留问题。
16. `Mesh转换服务` 的 LoadModule 示例被注释，应确认是可选模块、停用模块还是仅文档示例问题。
17. `Stamp2`、`PS2`、`Cityplan`、`StampManager2` 是 PPT 中的历史产品/系统名称，需补充当前正式名称和产品身份。

## 14. 与当前 seed 的差距

当前 `data/product_relation_backbone.json` 为 40 个实体、40 条关系，主要问题不是少量关系错误，而是实体分层和粒度不足：

| 当前 seed 内容 | 原始材料实际内容 | 修订方向 |
|---|---|---|
| 5 个工具能力名 | 6 类手册一级主工具、4 个 TerrainBuilder 子工具、UE导出插件及多项处理能力 | 以手册六类工具搭主干，再挂子工具、插件和功能叶子 |
| 6 类数据 | 30 余类数据、20 余类图层/资源、数十种格式 | 分开 DataType、LayerType、DataFormat |
| 11 个概念服务 | 手册 29 类部署服务及对应 `.so`，另有历史版本 | 以手册服务名为主，`.so` 作为技术叶子 |
| WebGL、WebRTC | 一级渲染体系应为 ActiveX、StampUE、WebGL；WebRTC、图形 API 和客户端形态应下沉为技术叶子 | 按三大体系重建主干，禁止 WebRTC 与三大体系并列 |
| 7 个一级应用 | 白皮书和 PPT 明确大量行业子场景 | 一级应用与子场景分开 |
| 无二次开发、运维、运行层 | 材料中有完整 SDK、协议、StampManager 和基础设施内容 | 增加支撑层和横向标签 |

因此，本文件确认前不应直接在现有 40 实体上继续补关系，否则会形成“抽象主干过粗、真实叶子无处归属”的结构。
