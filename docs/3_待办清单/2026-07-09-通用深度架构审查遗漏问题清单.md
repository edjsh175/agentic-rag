# 通用深度架构审查遗漏问题清单（2026-07-09）

## 1. 审查背景

本文件记录在既有严格代码审查问题清单之外，按照 `docs/prompt/审查提示词.md` 进行二次“通用深度架构审查”后新增或被强化确认的问题。

本轮审查目标不是判断代码是否能运行，也不是重复已有 P0–P4 问题，而是主动查找以下隐患：

- 职责错位
- 单一事实源分裂
- 规则补丁膨胀
- 数据污染与错误写入
- 评测失真
- 临时方案固化
- 模块边界混乱
- 隐性耦合
- 操作安全边界缺失
- 长期不可维护设计

## 2. 总体结论

当前项目已经不是简单功能型 RAG，而是逐步进入“平台化 RAG / 知识治理系统”阶段。现有主链路包括文档解析、结构化切块、Chroma 向量索引、BM25、Reranker、Graph-RAG、Prompt 引用约束、评测与一致性检测。

二次审查发现：当前最大新增风险不是模型效果，而是治理层和操作边界尚未平台化。特别是：

1. 管理接口和生产数据之间缺少权限边界。
2. 聊天记录持久化路径依赖未校验的浏览器指纹，存在路径穿越风险。
3. doc_category、review_status、Graph schema、前端 TS 类型、文件索引、chunk metadata 之间仍存在事实源分裂。
4. 博客发布 / 同步 / 扫描 / 入库链路缺少事务状态模型。
5. Evaluation 与生产检索口径仍存在分叉。
6. 当前可以继续开发，但必须优先处理 P0/P1，否则后续 Graph Agent、多知识库和自动知识构建会放大维护风险。

## 13. 最高优先级新增问题

### P0-新增-1：管理接口缺少鉴权和操作确认

**证据位置：**

- `rag_knowledge/api/routes.py`
- `/admin/chunks/*`
- `/admin/knowledge_graph/*`
- `/review/status`
- `/config/embedding-model`
- `/blog/posts/{filename}` DELETE
- `/blog/publish/{filename}`

**影响：**

任何能访问服务的人都可能修改审核状态、删除图谱实体、删除博客文件、触发向量模型切换或重建。若服务绑定 `0.0.0.0` 且 CORS 为 `*`，风险更高。

**推荐修复：**

- 增加 Admin Token / Role Middleware。
- 所有 `/admin/*`、`/config/*`、`/rebuild`、`DELETE`、`batch-review` 进入保护路由。
- 危险操作要求 `confirm=true`、`reason`、`operator`。
- 增加 audit log。

**是否阻塞继续开发：**

阻塞生产部署，不阻塞本地功能开发。

---

### P0-新增-2：ChatStorage 使用未校验 fingerprint 作为文件名

**证据位置：**

`rag_knowledge/services/chat_storage.py`

```python
return self._root / f"{fingerprint}.json"
```

**影响：**

`x-device-fingerprint` 来自请求 Header，若未限制字符，可造成路径穿越、覆盖或删除非预期 JSON 文件。

**推荐修复：**

- fingerprint 只允许 `[a-zA-Z0-9_-]`。
- 限制长度，例如 64。
- `resolve()` 后校验必须位于 `data/chats` 下。
- 对非法 fingerprint 返回 400。

**是否阻塞继续开发：**

阻塞公网部署。

---

### P1-新增-1：doc_category 和 review_status 双端/多层维护

**证据位置：**

- `rag_knowledge/services/chunk_admin.py`
- `web/src/types/index.ts`
- `file_index.json`
- chunk metadata
- `doc_category_map.json`
- Graph DB

**影响：**

新增分类、新增状态、重命名状态时容易出现前后端不一致、索引不一致、评测口径不一致。

**推荐修复：**

- 建立统一 schema registry。
- 前端类型由 OpenAPI/schema 生成。
- 增加 metadata consistency check。

**是否阻塞继续开发：**

不完全阻塞，但在新增产品线前必须处理。

---

### P1-新增-2：博客发布链路缺少事务与回滚

**证据位置：**

`rag_knowledge/api/routes.py` 的 `/blog/publish/{filename}`：

流程包括：

1. 读取爬取文件。
2. 调用外部 addRag API。
3. 写入已发布目录。
4. 删除原文件。
5. 扫描入库。
6. 重建 BM25。
7. 清缓存。

**影响：**

任一步失败都可能留下半完成状态：外部已发布但本地未入库，文件已移动但扫描失败，BM25 失败但 metadata 已改变。

**推荐修复：**

- 引入 `BlogPublishTransaction`。
- 记录状态：`created -> external_synced -> local_written -> indexed -> completed`。
- 支持恢复和回滚。

**是否阻塞继续开发：**

不阻塞，但阻塞稳定上线。

---

### P1-新增-3：Evaluation 与生产检索口径仍有分叉

**证据位置：**

`rag_knowledge/evaluation/runner.py`

评测使用：

```python
review_status=None
```

生产通常使用：

```text
review_status='approved'
```

**影响：**

评测结果可能高于真实用户体验。

**推荐修复：**

- 增加 `production_mode=True`。
- 默认 A/B 使用 approved-only。
- all-status 作为诊断指标单独输出。

**是否阻塞继续开发：**

阻塞将评测作为上线门禁。

## 14. 建议修复顺序

1. **先处理 P0：**
   - Admin 鉴权与危险操作确认。
   - ChatStorage fingerprint 安全校验。
   - `/rebuild` POST-only 与 confirm。
   - `run_eval_full.py` 禁止默认覆盖正式评测集。

2. **再处理 P1：**
   - schema registry：统一 doc_category、review_status、KB 名称、Graph 实体类型。
   - 分类规则迁移出代码。
   - Evaluation production mode。
   - Blog publish transaction。

3. **然后处理 P2：**
   - 拆 routes.py。
   - 抽 VectorStore 公开只读 API，减少 `_collection` 依赖。
   - 抽 PromptBuilder / CitationValidator / QueryPlanner。

4. **最后处理 P3：**
   - OpenAPI 生成前端类型。
   - 配置模块化。
   - 增加更多反例测试。

## 16. 最终判断

本轮新增审查问题中，真正需要优先关注的是：

