## 1. 背景与决策

当前系统已经具备 DOCX 结构化解析、语义切块、Chroma、BM25、Hybrid Retrieval、Reranker、邻居扩展、GraphRAG、Chunk 审核和引用约束等能力。

现有检索评测在单点问题上取得较高 Hit@K，但实际问答仍频繁出现以下现象：

1. 回答只包含零星、简短片段。
2. 流程类问题只能回答几个步骤标题，缺少完整参数和操作命令。
3. 原文存在的信息被回答为“知识库中未查询到”。
4. 回答使用“完整流程”等确定性表述，但实际遗漏大量步骤。
5. 知识图谱重建后实体仍以 Document、Section 为主，Procedure、Step、Command、ConfigItem 等业务实体偏少。

经对恢复后的正式 Chroma 快照、原始 DOCX 解析结果、过滤结果、检索上下文、API 最终回答和引用呈现进行检查，确认当前主要矛盾不是 Rerank 参数，也不是知识图谱 Prompt，而是 **Chunk 基石存在有效内容误删、结构误判、粒度失衡和证据不完整**。

因此作出以下产品决策：

> 在本 PRD 的 P0 验收门槛通过前，当前知识图谱全量 LLM 抽取结果只作为诊断快照，不作为最终图谱质量基线；暂停对当前批次进行最终推广或以其评价 GraphRAG 上限。先完成 Chunk 基石治理、受控重建和多证据评测，再重新执行全量图谱抽取。

### 架构决策（2026-07-15，v1.2 修订；v1.2.1 澄清）

不再把“解析结果直接切成 Chunk”作为长期主链路。系统中心也不是完整 Document AST。

**证据源与工作模型分离：** 原始文档及其指纹、Raw Block（及页/段落位置）是不可替代的证据源；版本化 Canonical Element / Tree Lite 是写路径上唯一的结构化工作模型；Chroma / BM25 / Graph / Citation 均为由其投影出的检索与引用视图。解析器升级导致结构变化时，必须能对照同一原文 + Raw Block 解释差异，而不是把某次 Canonical 快照当成永恒真相。

#### 四条架构约束

1. **原始文档 / Raw Block = 证据源**；**版本化 Canonical Element（含稳定 element_id、parser_version、source_snapshot_hash）= 写路径唯一的结构化工作模型**。Chroma / BM25 / Graph / Citation 均为投影，不得各自另立事实源，也不得在丢掉 Raw 引用后仍声称可审计。
2. **EvidencePack = 读路径唯一 LLM 输入契约**；可先落结构与管理视图，再加重校验。
3. **Tree Lite（Section Spine）优先于完整 AST**：`Document → Section → Ordered Elements → Chunk`；Chunk 是检索视图。
4. **Structure Graph / Domain Graph 分离**：骨架图服务扩上下文，业务图服务产品/配置/依赖；证据同时绑定 `section_id` 与 `chunk_id`，并最终可回溯 Raw Block。

#### 目标链路

```text
Write:
  Raw Doc
    -> Document Intelligence（格式解析、结构识别、候选校验）
    -> Canonical Elements
    -> Section Spine / Tree Lite
    -> Chunk Builder（technical_manual 等策略）
    -> Vector / BM25 / Domain Graph / Citation（投影）

Read:
  Query -> Plan -> Candidates -> EvidencePack -> Answer (+ light verify)
```

Round 0B 的过滤与标题规则保留为结构校验和降级保护，不继续以逐文档补规则的方式扩张。

#### 本 PRD 明确不做（后置）

1. 完整版式 AST / 复杂 figure 语义平台。
2. 独立 Ontology 服务或 Document Registry / 多版本生命周期平台。
3. Intent Router 重做、重型 Answer NLI、多租户权限。
4. 以更换 Embedding / LLM 或盲调 TopK 掩盖语料问题。

### 与知识图谱 PRD 的接口

1. **本 PRD 未完成 Round 0G 前**：图谱全量 LLM 结果仅作诊断，不评价 GraphRAG 上限。
2. **Round 0C 起**：新抽取的实体/关系证据必须能挂 `section_id` + `chunk_id`（及原始块引用）。
3. **Structure / Domain 分离**：在图谱侧后续轮次落实；本 PRD 只保证证据锚点可挂载。
4. **Chunk ID 变化后**：不得迁移旧证据 ID；须在新库上重新抽取与评测。

## 2. 目标与非目标

### 2.1 产品目标

1. 保证中文技术文档中的有效正文、命令、路径、配置项、参数和中英文混合内容不被错误过滤。
2. 保证标题层级来源可信，避免正文、命令、端口和配置值被误判为 Section。
3. 让每个普通文本 Chunk 具备足够完整的局部语义，能够独立支撑一个事实、步骤或短流程。
4. 保留文档、章节、节内顺序、前后邻接、表格和图片证据，使检索和图谱抽取可以恢复连续上下文。
5. 建立覆盖单点事实、多步骤流程、跨 Chunk 证据和证据冲突的评测集。
6. 使用回答正确性、完整性、引用蕴含和图谱抽取质量决定策略是否上线，而不是只看 Hit@K。

### 2.2 非目标

1. 本轮不迁移 Chroma 或关系数据库。
2. 本轮不以更换 Embedding 或 LLM 模型作为首要解法。
3. 本轮不先行盲调 `chunk_size`、`top_k` 或 Rerank 阈值。
4. 本轮不重构与解析、Chunk、检索上下文和评测无关的模块。
5. 本轮不允许为单份手册硬编码特例；规则必须基于可泛化的结构、字符和版式特征。
6. 本轮不把 `domain_catalog.json` 作为问题来源。该文件内容正常，其职责是实体种子和归一化辅助，不负责修复 Chunk 质量。
7. 本轮不建设完整 Document AST、独立 Ontology 服务、Document Registry / 多版本平台、Intent Router 重做或重型 Answer NLI。
8. 本轮不以 Hit@K 单独作为上线或 GraphRAG 上限依据。

## 4. 根因与影响

### 4.1 P0：中文技术正文被低信息过滤器误删

### 现状

`FileLoader._is_low_information()` 会将较长、同时包含 ASCII 和非 ASCII 字符、且空格较少的文本判为低信息内容。

中文技术文档天然包含以下组合：

```text
中文 + PCIE/WebGL/Redis/Cesium
中文 + /etc/... 文件路径
中文 + systemctl/vim/chmod 命令
中文 + EPSG/端口/配置键
中文 + JPG/WebP/CRN/DDS
```

这类内容不应仅因中英文混排而被视为乱码或噪声。

### 实测影响

| 文档 | 过滤前 | 最终保留 | 被过滤 | 过滤比例 |
|---|---:|---:|---:|---:|
| StampServer | 519 | 357 | 162 | 31.21% |
| StampTools | 200 | 150 | 50 | 25.00% |
| StampWebRTC | 117 | 50 | 67 | 57.26% |

WebRTC 关键段落对比：

| Section | 原始长度 | 当前结果 |
|---|---:|---|
| WebRTC 内网部署 | 105 | 整段删除 |
| Turnserver 配置 | 1369 | 只残留 328 字尾段 |
| 信令服务修改 | 412 | 整段删除 |
| TCP 外网部署 | 1266 | 整段删除 |
| TCP 信令服务修改 | 478 | 整段删除 |
| 应用外网部署 | 141 | 整段删除 |
| 运行渲染服务器 | 61 | 整段删除 |

### 影响

1. 被删除内容无法被向量检索、BM25、Reranker 或 GraphRAG 恢复。
2. LLM 无法抽取被删除的 Tool、Service、Procedure、Step、Command、ConfigItem。
3. 原文存在的信息被错误回答为“未查询到”。
4. 同一配置只保留尾部，导致参数、前置条件和结论分离。

---

### 4.2 P0：DOCX 标题兜底规则过于激进

### 现状

结构化解析在无法从 Word 样式确认标题时，会使用字号和粗体进行兜底判断。短段落只要存在 12pt 及以上字号，就可能被识别为标题。

12pt 在中文 Word 中经常是普通正文字号，不能独立作为标题依据。

### 已发现的错误 Section

```text
reboot
enabled=1
vim /etc/sysctl.conf
/boot/efi：分区大小一般是200M
HTTPS端口："HttpsPort": 443,
89：8450
```

### 影响

1. 每个误标题都会立即切断前后正文。
2. 命令、配置值和端口进入 `section_path`，污染结构语义。
3. 图谱规则和 LLM 会把命令、配置项误当成 Section。
4. Procedure、Step、Command 与所属对象关系被破坏。

---

### 4.3 P0：语义切块只能拆分，不能合并短 Section

### 现状

结构解析器先按标题输出元素，Semantic Chunker 再逐元素处理。Semantic Chunker 可以将长元素拆小，但不会将相邻短元素合并。

因此，即使将 `chunk_size` 从 500 增大到 800 或 1000，也不会自动合并已经被解析器切开的 20～100 字 Section。

### 影响

1. 大量 Chunk 只有标题和一句话。
2. 流程步骤散落在多个 Chunk 中。
3. Reranker 容易选中标题匹配度高但信息量低的片段。
4. 图谱抽取只能在单个碎片中寻找证据，跨块关系召回率下降。

---

### 4.4 P0：正文、表格和图片的粒度严重不一致

### 现状

1. 普通正文中位数只有 80～116 字。
2. DOCX 表格允许整块保留到 3000 字以上。
3. 表格使用 Markdown 原文参与向量嵌入，`searchable_text` 主要用于 BM25。
4. 表格和正文没有统一的父级上下文注入策略。

### 影响

1. 文本 Chunk 过短，表格 Chunk 过长，候选评分不可直接比较。
2. 大表格可能挤占上下文预算。
3. 表格中的字段含义容易与所属章节、产品和操作对象脱离。
4. 图谱抽取面对大表时容易漏行、漏列或错误归属。

---

### 4.5 P0：图片型步骤基本没有进入知识库

### 现状

当前本地和生产配置均关闭 `extract_embedded_images`。

三份主要 DOCX 包含：

| 文档 | 内嵌媒体数量 |
|---|---:|
| StampServer | 191 |
| StampTools | 123 |
| StampWebRTC | 201 |
| 合计 | 515 |

即使打开现有开关，每份文档默认也只处理前 5 张图片，图片描述作为独立 Chunk 追加，缺少可靠的 Section 挂接。

### 影响

1. “如下图”“具体如下”“点击某按钮”等步骤只有引导句，没有实际内容。
2. 安装向导、网络拓扑、菜单位置和表单字段缺失。
3. 图谱无法提取截图中的工具、操作步骤和配置关系。

---

### 4.6 P1：PDF 和旧 DOC 缺少结构恢复

### 现状

1. 结构化解析主路径只覆盖 TXT、Markdown 和 DOCX。
2. PDF 主要依赖按页文本抽取，没有稳定恢复标题、章节、表格和布局。
3. 当前 PDF 的 `section_path` 为空。
4. 旧 DOC 退回纯文本处理，结构和格式证据不足。

### 实测

当前主要 PDF：

```text
155 个 Chunk
100% section_path 为空
```

### 影响

1. PDF 召回只能依赖正文词面和向量相似度。
2. 无法进行章节过滤、节内邻接和结构化图谱归属。
3. 表格行列和跨页段落可能错序。
4. 中文扫描 PDF 和截图页面完全缺失。

---

### 4.7 P1：Chunk 顺序与邻接元数据不足

### 现状

当前主要依赖：

```text
source
section_index
chunk_in_section
element_order
```

但在 PDF、旧格式和同 Section 多块场景中，顺序元数据不稳定或重复。当前邻居扩展主要按相邻 `section_index` 查找，并排除相同 `section_index`，无法稳定补回同一 Section 被拆开的兄弟 Chunk。

### 影响

1. 长 Section 的后续命令和说明无法稳定拼回。
2. 同 Section 的表格与正文可能互相不可达。
3. 图谱跨 Chunk 抽取缺少可靠窗口。
4. 重建后 Chunk ID 变化使基于 ID 的评测集失效。

---

### 4.8 P1：检索参数只能缓解，不能修复缺失内容

### 已确认行为

中文流程类问题能够触发：

```text
top_k=8
candidate_k=24
rerank=true
expand_neighbors=true
8 条检索查询
```

因此 Query Planner 和邻居扩展不是当前 P0 根因。

但仍存在以下限制：

1. 普通问题生产默认 `top_k=4`。
2. 生产配置默认关闭 Reranker，本地默认开启，环境口径不一致。
3. 最终 TopK 仍不足以覆盖整章流程。
4. 扩大 TopK 会同时增加无关短片段和表格噪声。
5. Reranker 无法召回已经被过滤器删除的内容。

---

### 4.9 P1：回答完整性和证据冲突缺少治理

### 现状

回答 Prompt 要求仅基于 Context，但当前没有结构化检查：

1. 问题要求“完整流程”时，证据是否覆盖全部章节。
2. 回答是否使用了“完整、全部、仅、必须”等强断言。
3. 同一参数在不同证据中是否冲突。

### 已发现冲突

同一文档中：

```text
端口表：TLS 端口 5439
Turnserver 配置正文：tls-listening-port=5349
```

由于包含 `5349` 的正文大部分被过滤，模型只看到 `5439` 时无法发现冲突。

### 影响

1. 残缺答案被描述为完整答案。
2. 冲突配置未提示用户核对原文。
3. 引用存在但不代表答案覆盖充分。

---

### 4.10 P1：引用过滤放大用户看到的碎片感

### 现状

内部可能检索 8 个 Chunk，但 API 最终只返回答案中明确使用 `[n]` 引用的来源。

WebRTC 用例中：

```text
内部上下文：8 个 Chunk
页面可见来源：3 个 Chunk
```

### 影响

1. 用户无法看到未引用但参与过判断的候选证据。
2. 用户更容易认为系统只检索到几个短片段。
3. 缺少“已检索但未采用”和“证据不足”的透明度。

---

### 4.11 P1：现有评测无法评价完整答案

### 现状

当前标准评测集共 36 题：

1. 每题只有 1 个 relevant Chunk。
2. 没有需要 2～6 个证据块才能回答的问题。
3. 没有完整 `ground_truth`。
4. 没有 `expected_answer`。
5. 主要评价是否命中某个 Chunk ID。

### 影响

1. Hit@5 高不等于答案完整。
2. 一个标题片段命中即可得分。
3. 重建后 Chunk ID 变化会造成假失败。
4. 当前评测无法发现“原文存在、入库后消失”。
5. 当前评测无法评价错误的“完整答案”声明。

---

### 4.12 P1：当前 Chunk 质量直接限制知识图谱上限

### 现状

LLM 图谱抽取以单个 Chunk 为输入，证据必须来自当前 Chunk 或其 `section_path`。

### 影响

1. 被过滤内容中的实体和关系完全不可见。
2. 跨 Chunk 的 `Procedure -> has_step -> Step` 关系无法稳定抽取。
3. 命令和配置值被误识别为 Section。
4. 图片中的 UI 操作和网络拓扑无法抽取。
5. 当前 Section-heavy 现象既来自语义抽取边界，也来自 Chunk 输入本身偏向 Section 标题。

### 图谱轮次约束

1. 已完成的产品关系主干继续保留，不受本 PRD 影响。
2. 当前规则和 LLM 重建产物可用于诊断，不直接作为最终验收基线。
3. P0 Chunk 门槛通过后，必须重新生成 Chunk ID、图谱候选和证据链接。
4. 旧 Chunk 证据链接不得直接迁移到新 Chunk。

---

### 4.13 P2：运维和可观测性问题

1. 图谱进程退出后可能留下过期 PID 文件，容易误判任务仍在运行。
2. Chroma 遥测持续输出 `capture()` 参数错误，污染诊断日志但不影响当前检索结果。
3. 部分文档在语义模型不可用时会降级为固定切块，日志有记录，但管理界面缺少明确的降级状态。
4. 同内容 PDF 的路径、文件索引和 Chroma `source` 可能因文件移动或重复文件产生不一致，影响引用定位。
5. Chunk 统计目前关注均值、数量和命中次数，缺少短块率、内容过滤率、空章节率、结构覆盖率和图片覆盖率。

## 6. 功能需求

### 6.1 FR-01：建立只读 Chunk 健康审计

新增可重复运行的只读审计能力，输入原始文档、解析中间结果和 Chroma 快照，输出 JSON 与 Markdown 报告。

报告至少包括：

1. 文档级 Chunk 数、长度分位数和短块率。
2. `section_path` 空值率和标题深度分布。
3. 文本、表格、代码、图片/OCR 的数量和长度分布。
4. 解析前、过滤前、过滤后、入库后的内容数量与字符覆盖率。
5. 被过滤内容样本及触发规则。
6. 疑似命令/路径/端口被识别为标题的样本。
7. 重复顺序键、缺失顺序键和断裂邻接链。
8. 每份文档媒体数量、已处理数量和挂接成功率。
9. PDF 页面、标题、表格和 OCR 覆盖率。
10. 同一参数多值冲突候选。

约束：

1. 审计默认不修改 Chroma、`file_index` 或关系数据库。
2. 正式库审计使用项目根目录 `venv`。
3. 报告记录语料快照哈希、解析配置和代码版本。

#### 6.1.1 全链路解析留痕契约

解析链路必须能够从任一 Final Chunk 反向追溯到原始文档块，也必须能够从任一原始文档块查询其最终去向。留痕不是调试日志，而是 Chunk 质量审计、误删定位、重建对账和图谱证据追溯的正式数据契约。

统一处理链路：

```text
Source Document
    ↓
Raw Block
    ↓
Canonical Element
    ↓
Structure Validation
    ↓
Merge / Split Transformation
    ↓
Content Decision
    ↓
Final Chunk
```

##### 统一标识

所有阶段记录必须包含：

```text
run_id                 单次解析或审计运行 ID
source_document_id     文档稳定身份，不使用文件名代替
source_snapshot_hash   本次读取的原始文件哈希
parser_version         解析器版本
config_fingerprint     有效配置指纹
created_at             阶段记录生成时间
```

同一次运行内，所有中间对象使用稳定的阶段 ID，并通过 `input_ids`、`output_ids` 建立血缘，不允许只依赖数组位置进行关联。

##### 阶段必填字段

| 阶段 | 必填字段 | 说明 |
|---|---|---|
| Raw Block | `raw_block_id`、`block_index`、`block_type`、`raw_text`、`page_or_part`、`parent_container`、`style_snapshot`、`media_refs` | 保存文档原始顺序以及段落、表格、图片、分页位置和 Word 样式，不做标题推断 |
| Canonical Element | `element_id`、`source_raw_block_ids`、`element_type`、`content_markdown`、`searchable_text`、`element_order`、`candidate_section_path`、`content_type` | 将不同格式统一为规范元素，但保留来源 Raw Block |
| Structure Validation | `validation_id`、`element_id`、`structure_action`、`issue_codes`、`heading_source`、`heading_confidence`、`resolved_section_path` | 记录标题判定、层级修正、疑似误标题、空章节和命令标题等结构检查 |
| Merge / Split | `transformation_id`、`action`、`input_ids`、`output_ids`、`boundary_type`、`reason_code`、`char_range`、`target_size` | 记录合并来源、拆分边界、前后关系以及为什么进行转换 |
| Content Decision | `decision_id`、`target_id`、`action`、`reason_code`、`confidence`、`quality_metrics`、`quarantine_ref` | `action` 仅允许 `keep`、`quarantine`、`reject`；任何非保留结果必须可查询原文 |
| Final Chunk | `chunk_id`、`source_element_ids`、`source_raw_block_ids`、`section_id`、`section_path`、`chunk_index_global`、`chunk_index_in_section`、`prev_chunk_id`、`next_chunk_id`、`content_type`、`chunking_method`、`parser_version` | 作为 Chroma、BM25、引用和图谱证据共同使用的最终对象 |

##### Raw Block 契约

`Raw Block` 只表示源文件中的客观块，不在这一阶段判断标题或垃圾内容。

```json
{
  "raw_block_id": "rb_<stable-id>",
  "block_index": 42,
  "block_type": "paragraph|table|image|page_break|code",
  "raw_text": "",
  "page_or_part": "word/document.xml",
  "parent_container": "document_body",
  "style_snapshot": {
    "style_name": "Normal",
    "outline_level": null,
    "font_size_pt": 12,
    "bold": false,
    "numbering": null,
    "alignment": "left"
  },
  "media_refs": []
}
```

要求：

1. `block_index` 严格反映原始阅读顺序。
2. 表格、图片不得在 Raw Block 阶段丢弃。
3. DOCX 图片记录 relationship ID；PDF 内容记录页码和版面区域。
4. `style_snapshot` 保存判定所需的原始证据，不能只保存最终标题等级。

##### Canonical Element 契约

`Canonical Element` 负责统一 DOCX、PDF、Markdown、TXT 和旧 DOC 的中间表示。

```json
{
  "element_id": "el_<stable-id>",
  "source_raw_block_ids": ["rb_42", "rb_43"],
  "element_type": "text|table|image_text|code",
  "element_order": 18,
  "candidate_section_path": ["操作系统安装", "Rocky安装"],
  "content_markdown": "",
  "searchable_text": "",
  "content_type": "text"
}
```

要求：

1. 一个 Element 可以来自多个连续 Raw Block，但必须保留完整来源列表。
2. `content_markdown` 用于展示和引用，`searchable_text` 用于检索，两者不得互相覆盖。
3. Element 不得因后续过滤而从审计产物中消失。

##### Structure Validation 契约

结构校验必须输出判定而不是直接覆盖原始信息。

```text
structure_action = accept | downgrade_heading | promote_heading | flag
heading_source   = style | outline | numbering | heuristic | none
```

`issue_codes` 至少包括：

```text
SUSPECT_COMMAND_HEADING
SUSPECT_PATH_HEADING
SUSPECT_PORT_HEADING
SUSPECT_CONFIG_HEADING
EMPTY_SECTION_TITLE
HEADING_LEVEL_JUMP
BODY_FONT_AS_HEADING
MISSING_SECTION_PATH
```

要求：

1. 保存候选路径和最终路径，不能只保留修正结果。
2. 启发式标题必须记录置信度和命中的信号。
3. `heading_confidence` 低于门槛时进入审计，不得静默创建深层 Section。

##### Merge / Split 血缘契约

所有合并和拆分必须形成可逆向查询的转换记录。

```json
{
  "transformation_id": "tx_<stable-id>",
  "action": "merge|split|passthrough",
  "input_ids": ["el_18", "el_19"],
  "output_ids": ["unit_7"],
  "boundary_type": "section|paragraph|sentence|table|token_limit",
  "reason_code": "MERGE_SHORT_SIBLING_SECTIONS",
  "char_range": [0, 486],
  "target_size": 500
}
```

`reason_code` 至少覆盖：

```text
MERGE_SHORT_SIBLING_SECTIONS
MERGE_LEAD_IN_WITH_COMMAND
MERGE_CAPTION_WITH_TABLE
SPLIT_TOKEN_LIMIT
SPLIT_TABLE_ROW_GROUP
KEEP_STRONG_SECTION_BOUNDARY
KEEP_CODE_BLOCK_ATOMIC
KEEP_TABLE_ATOMIC
```

要求：

1. 合并只能使用顺序连续、边界兼容的输入。
2. 拆分必须记录每个输出对应的原文字符范围或表格行范围。
3. `prev/next` 在 Final Chunk 生成后重新计算，不能沿用已失效的中间索引。
4. 任一 Final Chunk 必须能够还原其 `merged_from` 和 `split_from` 血缘。

##### Content Decision 契约

内容质量检查不得再使用无原因的布尔删除。

```json
{
  "decision_id": "cd_<stable-id>",
  "target_id": "unit_7",
  "action": "keep|quarantine|reject",
  "reason_code": "VALID_MIXED_TECHNICAL_TEXT",
  "confidence": 0.98,
  "quality_metrics": {
    "replacement_char_ratio": 0.0,
    "control_char_ratio": 0.0,
    "symbol_ratio": 0.08,
    "mixed_script": true
  },
  "quarantine_ref": null
}
```

要求：

1. `mixed_script=true` 不能独立触发 `reject`。
2. `quarantine` 和 `reject` 都必须保留原文、来源和判定指标。
3. `reject` 只用于具有明确损坏证据的内容；不确定内容进入 `quarantine`。
4. 正式重建前必须输出各 `reason_code` 的数量、字符数和人工抽样结果。

##### Final Chunk 追溯契约

Final Chunk 除检索 metadata 外，必须具备以下追溯字段：

```json
{
  "chunk_id": "",
  "source_document_id": "",
  "source_snapshot_hash": "",
  "source_raw_block_ids": [],
  "source_element_ids": [],
  "transformation_ids": [],
  "content_decision_id": "",
  "section_id": "",
  "section_path": "",
  "chunk_index_global": 0,
  "chunk_index_in_section": 0,
  "prev_chunk_id": null,
  "next_chunk_id": null,
  "parser_version": "",
  "config_fingerprint": ""
}
```

不要求将全部 Raw Block 和转换记录塞入 Chroma metadata。Chroma 只保存检索和反向查找所需的 ID；完整血缘保存在本次运行的审计产物中，避免向量库 metadata 膨胀。

##### 审计产物

每次审计或重建生成独立目录：

```text
data/chunk_audit/<run_id>/
  manifest.json
  raw_blocks.jsonl
  canonical_elements.jsonl
  structure_decisions.jsonl
  transformations.jsonl
  content_decisions.jsonl
  final_chunk_lineage.jsonl
  quarantine.jsonl
  summary.json
  summary.md
```

`manifest.json` 至少记录：

```text
run_id
started_at / completed_at
source_snapshot_hashes
parser_version
config_fingerprint
embedding_model
document_count
stage_counts
stage_character_counts
```

数据安全要求：

1. 审计目录沿用正式语料访问权限，不得上传到外部服务。
2. `raw_blocks.jsonl` 和 `quarantine.jsonl` 可能包含敏感原文，不进入前端普通用户接口。
3. 审计产物默认不提交版本库；只提交脱敏黄金样本和汇总报告。
4. 受控重建报告保存对应 `run_id`，使 Chroma 快照和审计血缘一一对应。

##### 留痕不变量

实现必须满足：

1. **无静默删除**：每个 Raw Block 都能查询到 `kept`、`quarantined`、`rejected` 或 `non_content` 去向。
2. **双向追溯**：Raw Block 能查 Final Chunk，Final Chunk 能查 Raw Block。
3. **顺序稳定**：相同文件、配置和代码版本重复解析时，阶段顺序和血缘一致。
4. **统计守恒**：每阶段输入、输出、合并、拆分、隔离和拒绝数量能够对账。
5. **证据不可伪造**：任何图谱实体、关系或回答引用都能回到 Final Chunk，再回到原始块。
6. **失败可见**：阶段异常、降级解析和缺失媒体必须进入 `issue_codes` 和汇总报告。

### 6.2 FR-02：重写低信息过滤策略

### 必须要求

1. 不得仅因中文和 ASCII 混排判为垃圾。
2. 命令、路径、配置键值、端口、URL、产品名和格式名默认保留。
3. 垃圾判断优先依据：
   - Unicode 替换字符比例；

   - 不可见字符比例；
   - 重复乱码模式；
   - 极端符号比例；
   - 解码失败证据。
4. 每条拒绝必须返回机器可读 `reason_code`。
5. 审计报告能够按规则统计误杀样本。

### 回归样本

必须纳入本次已误删内容：

1. 分区与文件系统选择。
2. PCIE/M.2、CPU、GPU 和内存说明。
3. Redis、Cesium、WebGL、WebRTC 配置。
4. EPSG 与空间参考参数。
5. `systemctl`、`vim`、`chmod`、启动脚本。
6. Turnserver、信令服务和 TCP/UDP 部署。

### 6.3 FR-03：收紧标题识别

### 标题信号优先级

1. Word Heading 样式。
2. Word outline level。
3. 明确编号结构，如 `1.`、`1.2`、`（1）`。
4. 多信号组合：字号显著高于正文基线、加粗、段前段后间距、短文本。

### 禁止规则

以下模式不得仅凭字号或加粗认定为标题：

1. Shell/PowerShell 命令。
2. 文件路径和 URL。
3. `key=value`、JSON、INI 配置。
4. 单独端口号或端口映射。
5. 以冒号结尾的正文引导句。
6. 参数值、单位和值域。

### 输出

每个标题记录：

```text
heading_source=style|outline|numbering|heuristic
heading_confidence=0..1
```

低置信度标题进入审计报告，不直接生成新的深层 Section。

### 6.4 FR-04：Tree Lite（Section Spine）与结构化 Chunk Builder

在格式解析与最终 Chunk 输出之间建立可持久化、可审计的 **Tree Lite**，而不是完整版式 AST。现有 Raw Block、Canonical Element、Section Path 和血缘字段是其迁移基础；合并与邻接以实现稿 `已完成-第0B轮-并行准备与预研/第0C轮设计与留痕/round0c_merge_adjacency_design.md` 为准，留痕以 `已完成-第0B轮-并行准备与预研/第0C轮设计与留痕/lineage_manifest_contract.md` 为准。

### Tree Lite 最小模型

```text
Document
  └── Section（可嵌套；稳定 section_id + section_path）
        └── Ordered Elements（text / list / step / code / config / table / image_ref）
              └── Chunk（检索视图；覆盖 element ids + prev/next）
```

每个 Section / Element 必须包含稳定 id、parent id、文档顺序、原始块引用、类型、标题判定来源、解析版本；版式解析可用时再补充页码和坐标。Final Chunk 必须记录其覆盖的 Section 与 Element，而不是只记录字符串拼接结果。

Round 0C 不要求完整 Paragraph/Figure 语义树；图片与复杂 PDF 版式在 Round 0E 接入同一 Section Spine。

### Chunk Builder

1. Chunk Builder 从 Section 下有序 Element 生成 Chunk，并在生成时保留标题、说明、步骤、命令、代码、表格的父级上下文。
2. 首批实现 `technical_manual` 策略：章节完整、步骤完整、命令/配置与解释完整；通用文档走保守 `section_based` 策略。
3. 后续策略以可配置策略名扩展：`api_doc`、`table_doc`、`faq`、`paper`。不得以全库统一 `chunk_size` 代替策略选择；Round 0D 只做最小可用，不挡 0C/0G。
4. 图谱抽取输入为 Section 或其 Chunk 视图；实体、关系证据必须记录 `section_id`、`chunk_id` 和原始块引用。
5. LLM 只参与低置信度标题、元素类型或边界的批量裁决（可选，不挡主线）；规则和原始结构事实优先，LLM 不可直接改写原文或单独决定高风险证据。

### 合并原则

1. 同一父级下的短叶子 Section 可以按文档顺序合并。
2. 标题与正文必须共同保留。
3. “执行以下命令”必须与后续命令放在同一 Chunk 或建立强邻接。
4. 步骤编号连续时优先保持在同一流程窗口。
5. 不跨越明确的一级/二级章节边界。
6. 表格、代码块可以独立成块，但必须携带父级上下文。

### 建议目标

普通中文技术正文：

```text
目标区间：300～800 字符
软上限：1200 字符
```

以下内容允许低于 300 字符：

1. 独立定义。
2. 单一配置项。
3. 原子命令及其解释。
4. 表格标题与表格关联块。
5. 无法安全合并的章节边界。

---

### 6.5 FR-05：完善 Chunk 身份、顺序和邻接

每个最终 Chunk 至少包含：

```text
chunk_id
source_document_id
section_id
section_path
chunk_index_global
chunk_index_in_section
prev_chunk_id
next_chunk_id
content_type
chunking_method
parser_version
source_snapshot_hash
```

### 邻居扩展要求

1. 优先补齐同 Section 的前后兄弟 Chunk。
2. 再扩展相邻 Section。
3. 表格与其前后说明建立显式关联。
4. 图片/OCR 与锚定段落建立显式关联。
5. 不依赖可重复或缺失的默认 `section_index=0`。

---

### 6.6 FR-06：表格分块与上下文治理

1. 大表按表头重复的行组切分，不允许无条件保留超长整表。
2. 每个表格 Chunk 保留表名、父级章节和重复表头。
3. 向量嵌入使用去除 Markdown 噪声后的可检索文本。
4. 原始 Markdown 表格继续作为引用展示内容。
5. 表格行不得与字段说明、单位和值域脱离。
6. 表格 Chunk 进入图谱抽取前提供表头和所属对象。

---

### 6.7 FR-07：图片、OCR 和版式证据

### DOCX

1. 不再限制为每份文档前 5 张图片。
2. 跳过装饰图、Logo 和重复图片。
3. 对截图执行 OCR，必要时使用视觉模型生成结构化描述。
4. 根据 DOCX relationship 和文档顺序挂接到最近的标题、段落或表格。
5. 图片证据保留媒体哈希和锚定位置。

### PDF

1. 支持版面感知的标题、段落和表格恢复。
2. 扫描页执行 OCR。
3. 保留页码、版面区域和阅读顺序。
4. 跨页段落不得无条件断开。

### 图片结构化输出

```text
image_id
source
page_or_element
anchor_section_id
ocr_text
visual_summary
media_hash
```

### 6.8 FR-08：回答完整性与冲突治理

### 完整性

1. 识别“完整、全部、有哪些步骤、分别说明”等问题意图。
2. 在回答前检查检索证据是否覆盖目标章节和步骤。
3. 证据不足时不得使用“完整流程”“全部如下”等强断言。
4. 部分回答必须明确列出缺失的具体部分。

### 冲突

1. 对同一配置键、端口、路径、默认值提取候选值。
2. 多个高相关证据值不一致时，回答必须展示冲突和来源。
3. 不得静默选择一个值。
4. 冲突样本进入人工语料治理清单。

---

### 6.9 FR-09：引用与证据链呈现

回答结果应区分：

1. **已引用证据**：直接支撑答案事实。
2. **相关但未采用证据**：参与检索但未被回答引用。
3. **证据缺口**：原问题要求但当前未覆盖的章节或步骤。
4. **冲突证据**：同一事实存在不同值。

默认用户界面仍以已引用证据为主，但调试和管理视图必须能够查看完整检索上下文和淘汰原因。

2. 乱码、控制字符和替换字符能够拒绝。
3. 12pt 正文不自动成为标题。
4. 命令、路径、端口和配置值不成为标题。
5. 小 Section 合并不跨越强章节边界。
6. 同 Section Chunk 可以按顺序恢复。
7. 表格拆分重复表头并保留父级上下文。
8. 图片锚点和 OCR 去重正确。
9. 每个 Raw Block 都有明确去向且不存在静默删除。
10. Final Chunk 可以反查全部 Raw Block、Element 和转换记录。
11. 合并记录保留所有输入 ID，拆分记录保留字符或表格行范围。
12. 相同输入、配置和版本重复解析时，顺序与血缘结果稳定。

### 9.2 语料回归测试

必须使用三份真实手册的脱敏片段覆盖：

1. Rocky 分区和 SSH 配置。
2. WebRTC UDP/TCP 外网部署。
3. Turnserver 和信令服务配置。
4. StampTools 管线配置。
5. 图片引导型步骤。

### 9.3 端到端测试

1. 单点命令答案正确并引用。
2. WebRTC 外网部署能够区分 UDP 和 TCP，并覆盖关键步骤。
3. Rocky 安装回答不能在证据缺失时宣称完整。
4. `5439/5349` 冲突能够被发现并提示核对。
5. 图谱实体、关系和证据链接使用新 Chunk。

## 10. 上线、回滚与数据安全

### 10.1 上线原则

1. 先在隔离路径生成新知识库，不覆盖旧库。
2. 新旧库使用同一评测集做 A/B。
3. 只有 P0 指标全部通过才允许切换。
4. Embedding 未变化时也必须因 Chunk 变化执行重建。
5. Chunk ID 变化后必须重新生成评测和图谱证据链接。

### 10.2 回滚材料

1. 原 Chroma 目录备份。
2. 原 `file_index` 备份。
3. 原关系数据库备份。
4. 原解析和 Chunk 配置快照。
5. 新旧库文档数、Chunk 数和哈希对照。

### 10.3 禁止操作

1. 不得用系统 Python 或 `.venv` 打开正式 Chroma。
2. 不得手动拼接清库流程。
3. 不得在后端、评估或图谱进程运行时重建正式库。
4. 不得将旧 Chunk ID 强行映射为新证据。
5. 不得仅凭 Hit@K 提升判定上线。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 合并后 Chunk 过长 | 召回精度下降 | 使用结构边界和软上限，不做无条件拼接 |
| 标题规则过严 | 标题层级丢失 | 保留低置信度候选并进入审计 |
| OCR 噪声 | 污染检索 | 媒体去重、置信度阈值、OCR 与视觉摘要分字段 |
| TopK 增大引入噪声 | 回答偏题 | 先修 Chunk，再用多证据评测调参 |
| 重建改变 Chunk ID | 评测和图谱失效 | 使用稳定 source/section anchor 重建资产 |
| 原文自身冲突 | 回答不确定 | 冲突检测并展示来源，不静默裁决 |
| 新图谱与旧图谱差异大 | 审核成本上升 | 小批量试点、候选审批、分批 apply |

## 13. Go / No-Go 门禁

| `procedure` | 23.33% | 44.37% |

### 短块门禁（进入 0G）

二者取一，**禁止**在隔离实测前预写临时百分比：

1. **达标路径**：隔离库普通文本短块率达到 **§8.2**（`<100` ≤5%，`<200` ≤15%，`>1200` ≤5%）。
2. **临时路径**：隔离库实测后，将**唯一**一组临时阈值（`<100` / `<200` / `>1200`）写入 Go 清单并冻结；同时记录实测值、对照旧库/未合并基线的对比表。临时阈值仅用于开 0G 重建；**允许知识图谱全量抽取前必须达到 §8.2**。

未完成（1）或（2）冻结 → **不得**进入 0G。

### FR-10 门禁（整体 + category）

评分须使用与基线相同的 gold（或显式声明的继承集），并输出 category 分表。

#### A. 整体（进入 0G / 图谱全量）

1. `pass_rate` 与 `mean_completeness` 均须**高于**上表整体基线。
2. 具体最低值（`pass_rate_min`、`completeness_min`）在隔离库实测后与短块临时阈值（若有）**一并写入 Go 清单冻结**；冻结前不得开 0G。
3. 图谱全量前：重建后复核仍须 ≥ 已冻结的整体最低值，且短块已达 §8.2。

#### B. Category 下限（结构强制；数值随隔离实测冻结）

| category | 进入 Round 0G | 允许知识图谱全量 / 0F 后约束 |
|---|---|---|
| `procedure` | **必须考核**。`pass_rate` 与 `mean_completeness` 均须高于基线（23.33% / 44.37%）；具体 `procedure_pass_min` / `procedure_completeness_min` 隔离实测后写入 Go 清单冻结 | 重建后仍须 ≥ 冻结下限 |
| `fact` / `table` / `cross_section` | 均不得低于各自基线（允许持平） | 同左 |
| `conflict` | 若 0F（FR-08）尚未接线：本项可记为「待 0F」，但不得宣称冲突能力已验收 | **0F 接线后强制**：样本适用时 `pass_rate` 不得仍为 0%；具体下限隔离或 0F 回归后冻结。无适用样本须书面注明并跳过 |
| `ocr` | **与 0E / 纳入范围绑定**（见下） | 同左 |
| `none` | 不作为短块改善的替代指标；接线拒答策略后应高于基线或单独验收 | 图谱全量前建议完成拒答回归 |

#### C. `ocr` 与纳入范围（可判定）

1. 对**纳入本次重建范围**的文档：若 gold 含该文档的 `ocr` / 图片锚点题，则这些题计入 0G 门禁；未达冻结的 `ocr` 下限（或仍为 0% 且样本适用）→ **No-Go**，且不得用 0E「风险接受」绕过。
2. 对**未纳入范围**的文档：相关题标记 `out_of_scope`，移出本次 0G 评分；文档本身可豁免 0E，但不得当作主路径通过证据。
3. Go 清单须附：纳入文档列表、`ocr` 题去留表、0E 达标/豁免原因。
