# Chunk 基石治理长期通用架构整改 PRD

- **版本**：v1.0.0
- **日期**：2026-07-15
- **状态**：待实施（P0）
- **适用范围**：文档解析、内容质量决策、标题识别、Profile/Chunk Builder、审计、评测和交付脚本

---

## 1. 背景与问题判断

Round 0A/0B 已在当前真实语料上完成基线、过滤回归和标题 Precision 核验，现有生产代码没有按三份手册文件名、WebRTC 关键词或具体章节编写特判。

但当前实现仍是“对当前样本有效的阶段性方案”，不具备长期通用架构所需的策略隔离、统一决策、不可变审计和可复现评测能力。主要问题如下：

1. 低信息过滤在 `FileLoader` 中对所有文本格式统一生效，隐含中文技术文档假设；短事实、多语言内容和部分合法符号可能被拒绝。
2. 标题 fallback 使用固定字符数、字号和命令词表，缺少 Word outline、来源类型和置信度；封面 fallback 在部分路径上被静默丢弃。
3. 审计服务复制生产过滤规则，生产决策与审计 reason code 可能漂移。
4. 审计重跑会覆盖人工候选标签，人工证据与生成候选未分离。
5. FR-10 评测计算了证据锚点召回，但锚点结果不参与 `passed`；评测器规则、阈值和拒答文案未版本化。
6. 黄金集、评测报告和 Spike 脚本存在旧目录、绝对路径和固定样本快照，默认命令不能稳定复跑。
7. 短块门禁只对结果长度负责，尚未统一区分 `ordinary_body`、命令、步骤、接口、表格、记录等原子内容角色。

本 PRD 的核心判断是：**问题不是再添加更多手册例外，而是把内容质量、结构判定、Profile 策略和评测门禁收敛为可配置、可追溯、可复用的通用机制。**

---

## 2. 目标与非目标

### 2.1 目标

1. 建立按 `document_profile` 和 `content_role` 选择的内容质量与 Chunk 策略。
2. 生产路径、审计路径和评测路径共享同一份结构化决策结果。
3. 禁止有效内容静默删除；不确定内容进入 quarantine，并保留原文、来源和 reason code。
4. 标题判定可解释、可回溯，记录来源、置信度、候选证据和最终 Section。
5. 人工标注、黄金集、评测报告和运行配置均可版本化、可复跑、不可被生成步骤覆盖。
6. FR-10 同时评价回答内容、来源锚点和冲突/拒答行为，不允许只靠关键词命中通过。
7. 为后续 technical_manual、procedure、api_doc、table_doc、record_list、section_based 等 Profile 提供统一接口。

### 2.2 非目标

1. 本轮不更换 Embedding、LLM、Reranker 或 Chroma。
2. 本轮不建设完整 Document AST、独立 Ontology 或多版本文档平台。
3. 本轮不通过放宽 TopK、增加 Prompt 或删除短块来掩盖内容治理问题。
4. 图片、OCR、PDF、PPTX、HTML、旧 DOC 和媒体适配器可复用本契约，但不要求本轮全部完成。

## 3. 设计原则

1. **证据源与工作模型分离**：Raw Block/Canonical Element 是证据源；Profile Builder 和 Final Chunk 是可重建投影。
2. **策略选择优先于格式判断**：文件扩展名不能直接等同于文档类型；没有显式 Profile 时使用 `section_based`。
3. **原子语义不可被通用规则吞并**：命令、步骤、接口、表格、记录、代码等内容不得为了短块率跨边界合并。
4. **不确定即隔离**：`quarantine` 优先于静默 `reject`；所有 `reject` 都必须有机器可读 reason code。
5. **生产只产生一次决策**：审计和评测消费生产决策，不重新猜测生产行为。
6. **数据产物不可变**：生成候选、人工标签、评测结果和运行清单分层保存，不互相覆盖。
7. **门禁必须与证据绑定**：来源锚点、Section、Chunk 和 Raw Block 的链路缺失时不得宣称通过。

## 4. 目标架构

```text
Raw Document
  -> Parser Adapter
  -> Canonical Elements
  -> Structure / Content Decisions
  -> Profile Builder
  -> Common Finalizer
  -> Vector / BM25 / Graph / Citation projections
  -> Audit + Evaluation
```

### 4.1 Parser Adapter

Parser Adapter 只负责格式解析和结构原始信号，不负责最终 Chunk 合并：

- 输出 `CanonicalDocumentElement`；
- 提供 `element_type`、`content_role`、`raw_block_id`、来源位置、样式/编号/表格关系；
- 不直接删除低信息内容；
- 无法确定结构时输出候选和置信度。

### 4.2 Policy Registry

建立按 Profile 注册的不可变策略：

```text
ContentQualityPolicy
HeadingPolicy
ChunkPolicy
EvaluationPolicy
```

策略参数只能在 Profile 级配置，不允许为单个文件写临时覆盖。每份策略生成稳定的 `policy_id`，写入文件索引、审计报告和 Final Chunk。

### 4.3 Unified Decision

所有内容质量和结构判断使用统一结果：

```json
{
  "decision_id": "cd_<stable-id>",
  "target_id": "el_<id>",
  "action": "keep|quarantine|reject",
  "reason_code": "VALID_MIXED_TECHNICAL_TEXT",
  "confidence": 0.98,
  "content_role": "ordinary_body",
  "metrics": {},
  "source_raw_block_ids": [],
  "policy_id": "policy_<stable-id>"
}
```

生产、审计和评测均消费该结果；不得在审计侧复制生产判断。

### 4.4 Common Finalizer

Common Finalizer 统一完成：

- 超长拆分和原子边界保护；
- Section/Chunk 稳定 ID；
- `prev_chunk_id` / `next_chunk_id` 重算；
- `source_raw_block_ids`、`source_element_ids`、`transformation_ids` 血缘；
- `searchable_text` 生成；
- `document_profile`、`chunk_policy_id`、`content_role`、`related_element_ids` 写入元数据。

## 5. 功能需求

### FR-01：Profile 与策略选择

1. 支持 `section_based`、`technical_manual`、`procedure`、`api_doc`、`table_doc`、`record_list`。
2. 优先级：上传者显式选择 > 文件索引继承 > Profile 映射文件 > `section_based` 默认值。
3. 禁止生产代码根据文件名、产品名、WebRTC 等关键词自动选择 Profile。
4. Profile、策略和选择来源必须记录在运行清单中。

### FR-02：内容质量决策

1. 将当前低信息判断从布尔函数升级为可解释决策。
2. 当前阈值（如 compact 长度、目录比例、可读字符比例）只能作为兼容默认值，不得散落在代码中。
3. 语言和字符集规则不得将“未列出的 Unicode 脚本”直接等同于乱码。
4. `ordinary_body`、`command`、`code`、`table`、`step`、`api_request`、`api_response`、`record` 等角色使用不同保护规则。
5. 不确定内容进入 quarantine；拒绝结果必须保留原始文本、来源位置和 reason code。
6. 过滤前后数量、字符数、角色数量必须可对账。

### FR-03：标题与 Section 判定

1. 标题判定至少综合 Word Heading Style、outline level、编号结构、段落样式、字号、加粗、上下文和分隔线。
2. 输出 `heading_source`、`heading_confidence`、候选信号和最终层级。
3. 命令、路径、端口、配置、SQL、PowerShell、代码等不得仅凭字号或加粗成为标题。
4. 封面、版本、组织信息不得静默删除；无法成为 Section 时必须保留为 `non_content` 或正文候选。
5. 低置信度标题进入审计，不得静默创建深层 Section。

### FR-04：Profile Builder 与原子边界

1. `section_based` 不跨兄弟 Section 合并。
2. `technical_manual` 允许同层短叶子有限合并，但不跨强 Section 边界。
3. `procedure` 以步骤为硬边界，命令与说明/结果保持关联。
4. `api_doc` 以 Endpoint 为硬边界，不能跨接口合并。
5. `table_doc` 显式维护表名、字段、单位、值域和表格关系。
6. `record_list` 不跨 Record 合并；续行和说明归属原 Record。
7. 表格、代码、命令、接口请求/响应等原子角色不得被普通正文 Builder 吞并。

### FR-05：审计与生产一致性

1. 审计只能消费生产的 Decision、Transformation 和 Final Chunk lineage。
2. 审计报告必须包含 `policy_id`、`decision_id`、`run_id` 和 `corpus_snapshot_hash`。
3. 审计不得实现第二套低信息过滤、标题识别或对象统计规则。
4. 生产和审计决策不一致时，审计必须失败并报告差异，而不是继续生成“通过”报告。

### FR-06：人工标注与黄金集

1. 生成候选和人工标注分离保存。
2. 候选文件只能追加新版本，不得覆盖已有标签。
3. 每条标注必须有稳定 ID、标注人/时间、输入快照、规则版本和标签版本。
4. 黄金集必须与来源快照、Profile、评测器版本绑定。
5. 重新生成候选不能改变已冻结的黄金标签；若样本内容变化，必须产生新数据集版本。

### FR-07：FR-10 评测门禁

1. `evidence_anchor_recall` 必须参与 `passed` 判定，不能只作为报告展示指标。
2. 来源绑定问题必须同时检查 required facts、来源、Section/Chunk 锚点和禁止断言。
3. `conflict`、`none`、`partial` 和 `full` 使用可版本化的 `EvaluationPolicy`。
4. 关键词命中不得覆盖否定、冲突和来源不一致语境。
5. 评测结果必须记录 evaluator version、gold version、corpus snapshot、retrieval 配置和模型配置。
6. retrieval proxy 只能标注为 retrieval baseline，不得冒充最终 LLM 回答质量。

### FR-08：路径与复现

1. 所有脚本和 README 使用仓库根目录解析路径，不得依赖当前工作目录。
2. 统一使用 `docs/3_待办清单/切块基石治理/` 作为产物根目录。
3. 禁止提交绝对本机路径到黄金集、基线报告和 manifest。
4. 默认命令必须在干净工作目录中完成 `--help`、输入检查和只读基线运行。
5. 目录迁移必须同步更新脚本、文档相对链接和报告中的路径字段。

### FR-09：运行留痕

每次审计、重建或评测必须生成：

```text
run_id
started_at / completed_at
source_snapshot_hashes
parser_version
policy_id / config_fingerprint
evaluator_version
document_profile_counts
stage_counts
stage_character_counts
issue_counts_by_reason
```

## 6. 迁移与实施阶段

### Phase 1：契约冻结

- 冻结 `ContentDecision`、`HeadingDecision`、`EvaluationRunManifest`；
- 冻结 Profile、Content Role、reason code 枚举；
- 为现有 Chunk metadata 增加兼容读取和默认值。

### Phase 2：生产路径收口

- 接入 Policy Registry；
- 将过滤和标题判断改为 Decision 输出；
- 接入 Profile Builder/Common Finalizer；
- 禁止静默丢弃和跨原子角色合并。

### Phase 3：审计与评测收口

- 审计直接消费生产决策；
- 人工标签改为不可变 overlay；
- FR-10 增加来源门禁和 evaluator manifest；
- 重新生成 Round 0A/0B、FR-10 和各 Profile 黄金基线。

### Phase 4：脚本与数据迁移

- 修复默认路径、相对链接和报告路径字段；
- 为历史产物增加 `legacy` 标记，不覆盖旧快照；
- 生成全目录 Profile 覆盖清单；
- 对无法支持的文件记录明确排除 reason code。

### Phase 5：受控验收

- 隔离目录运行全部 Profile；
- 完成完整 pytest、前端检查和仓库卫生检查；
- 未通过 P0 门禁不得写正式 Chroma 或推广全量图谱。

## 8. 测试要求

### 8.1 单元测试

1. 短事实、短配置、短命令、多语言文本不会被通用规则静默删除。
2. 乱码、目录、纯链接和明确损坏内容仍能按 reason code 拒绝或隔离。
3. Word style、outline、编号和分隔线的标题来源可区分。
4. 命令、路径、端口、配置、SQL、PowerShell 和代码不会仅凭字号成为标题。
5. 封面 fallback 保留为可追溯内容，不产生无依据 Section。
6. 各 Profile 不跨 Endpoint、步骤、表或 Record 合并。
7. 表格、代码、命令、接口请求/响应保留父级上下文。
8. 审计输出与生产 Decision 完全一致。
9. 重跑候选不会覆盖人工标签。
10. 无来源锚点的回答不能通过来源绑定题。

### 8.2 真实语料回归

每个 Profile 至少包含：

- 2 份真实代表文档；
- 1 份边界混合文档；
- 1 份结构异常文档；
- 1 组短块、长块、原子块和跨边界黄金样本。

### 8.3 交付前检查

```powershell
.\venv\Scripts\python.exe -m pytest
cd web; npm run check
.\venv\Scripts\python.exe scripts/check_repo_hygiene.py
```

正式库和评估进程运行期间不得执行受控重建；隔离审计必须先通过，再进入 Go 清单。

## 9. Go / No-Go

### Go 条件

1. FR-01 至 FR-09 契约和实现均已冻结；
2. 所有文件均有 Profile，或有明确排除 reason code；
3. 有效内容误删为 0，所有 reject/quarantine 可追溯；
4. 原子语义边界和表格/命令上下文验收通过；
5. 审计与生产 Decision 一致；
6. FR-10 来源锚点门禁和 evaluator manifest 已接线；
7. 默认脚本和 README 命令可在干净目录复跑；
8. 隔离库、完整测试和仓库卫生检查通过。

### No-Go 条件

1. 仍存在静默删除或无 reason code 的拒绝；
2. 生产和审计维护两套过滤/标题规则；
3. 评测 pass 不检查来源锚点；
4. 生成候选会覆盖人工标签；
5. Profile 依赖文件名、产品名或关键词自动猜测；
6. 基线无法绑定源快照、配置和评测器版本；
7. 任一 Profile 跨原子语义边界合并；
8. 未通过隔离验收即写正式 Chroma 或推广全量图谱。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 新策略放宽过滤后噪声上升 | 检索噪声增加 | 先 quarantine，按 reason code 审核，不直接扩大 reject |
| Profile 边界改变 Chunk ID | 旧评测和图谱血缘失效 | 使用 source snapshot/section anchor，完成受控重建 |
| 审计改为消费生产决策后发现历史报告不一致 | 基线不可直接比较 | 标记 evaluator/policy version，保留历史快照 |
| 多窗口同时修改核心文件 | 合并冲突或策略分叉 | 先冻结契约和文件 owner，统一通过隔离分支合并 |
| 真实文档结构不足以判定 Profile | 误选策略 | 默认 section_based，并输出人工确认队列，不自动猜测 |

---

## 12. 结论

Round 0A/0B 的阶段性结果可以保留，但不得继续把“当前样本门禁通过”当成“通用架构完成”。本 PRD 要求把内容质量、标题识别、Profile Builder、审计、人工标注和 FR-10 评测统一到同一套可配置、可追溯、可复现的契约中，再进入正式库重建和全量图谱推广。
