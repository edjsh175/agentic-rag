## 2. 背景与问题

### 2.1 当前问题

早期图谱采用：

```
Document Chunk
      │
  LLM Extract
      │
    Entity
```

导致：

#### 1. 实体扁平化
例如：
```
PipelineBuilder
 ├─ 材质映射
 ├─ 坐标转换
 ├─ 管线点表
 ├─ Redis
 └─ 端口6379
```
所有节点处于同一层级，导致：
- 无法回答产品能力问题
- 无法理解业务结构
- 检索范围不可控

#### 2. 来源结构丢失
文档作者设计的组织结构：
```
PipelineBuilder用户手册
 3 数据管理
   3.1 材质映射
 4 工程设置
   4.1 坐标配置
```
原本包含有价值的知识分类，旧架构未予以利用。

#### 3. LLM 定义世界
LLM 自由生成分类节点（如 *数据管理*、*数据处理*、*数据配置*、*数据维护*），造成：
- 同义节点冗余
- 分类漂移
- 图谱无节制膨胀

---

## 3. 总体设计原则

### 原则一：知识分层
系统中的信息分为：

| 层级 | 职责 | 可信度 |
| ---- | ---- | ----- |
| Product Backbone | 产品事实关系 | ★★★★★ (Level 0) |
| FunctionArea Registry | 产品能力分类 | ★★★★☆ (Level 1) |
| Knowledge Entity | 具体知识 (Feature/Procedure/Constraint) | ★★★☆☆ (Level 2) |
| Document Evidence | 事实出处出处 | ★★☆☆☆ (Level 3) |

### 原则二：LLM 不负责定义知识体系
- **允许 LLM**：抽取实体、建立实体间关系、补充属性描述。
- **禁止 LLM**：创建 Product、修改 Product Backbone 归属、创建 FunctionArea。

### 原则三：来源参与建模，但不污染业务模型
文档结构（Section/Document）不是业务实体，但可以：
- 提供分类候选
- 提供检索路由
- 提供证据链条

---

## 4. 总体架构：双图 + 语义桥接架构

```
                    产品知识图谱 (Product Graph)
                  
                        Product Backbone
                               │
                     FunctionArea Registry
                               │
                            Feature
                               │
               ┌───────────────┴───────────────┐
           Procedure                       Constraint
               │
      Command/Data/Table



                               ▲
                               │  semantic bridge (derived_from / mentions / suggests)
                               │



                    文档知识图谱 (Document Graph)

                            Document
                               │
                            Section
                               │
                             Chunk
                               │
                            Evidence
```

## 5. 产品知识图谱设计

### Level 0：Product Backbone
- **来源**：`domain_catalog.json`、`product_relation_backbone.json`
- **特点**：人工维护，不允许自动修改，全系统最高优先级。
- **结构**：`Product ── belongs_to ──> Tool / Service`

### Level 1：FunctionArea Registry
- **定义**：表示产品能力区域（如 *数据管理*、*工程设置*、*服务部署*、*高级配置*）。
- **来源**：从 `Document Section` 提炼为 Candidate，经 `FunctionAreaClassifier`（规则直匹 $\rightarrow$ LLM 语义分类 $\rightarrow$ 保守 Section 退避），人工确认后写入 `data/function_area_catalog.json` 注册表。

### Level 2：Feature 层 (能力实体)
- **定义**：回答 **“产品有什么能力”**（例如 *材质映射*、*数据检查*、*坐标转换*）。Feature 描述能力而非单一操作。

### Level 3：Knowledge Entity (知识实体)
- **Procedure**：回答 **“怎么做”**（例如 *创建工程流程*、*导入管线数据*）。
- **Constraint / ConfigItem**：回答 **“限制与参数”**（例如 *EPSG:4490*、*端口 10605*、*文件格式 shp*）。
- **Data Entity**：例如 *管线点表*、*管线线表*、*字段结构*。
- **Command**：例如 *启动命令*、*配置命令*。

---

## 6. 文档知识图谱 (Document Graph)

文档图谱不参与产品业务分类，结构为：
$$\text{Document} \longrightarrow \text{Section} \longrightarrow \text{Chunk} \longrightarrow \text{Evidence}$$

- **作用**：定位原文、引用回答、调试抽取、版本追溯。

---

## 7. 两图连接方式 (语义桥接)

1. **`Entity ── derived_from ──> Chunk`**：表示“这个知识来自哪里”。
2. **`Chunk ── mentions ──> Entity`**：表示“文本或表格提到了什么”。
3. **`Section ── suggests ──> FunctionArea`**：表示“文档结构帮助发现能力分类”（弱关联，非强归属）。

---

## 8. LLM 抽取规范

- **LLM 输入**：包含 `当前Chunk` + `Product Backbone` + `FunctionArea Context (只读)` + `Feature Context`。
- **LLM 允许输出实体类型**：`Feature`、`Procedure`、`Constraint`、`Command`、`DataTable`、`Error`、`Solution`。
- **LLM 禁止输出实体类型**：`Product`、`Tool`、`FunctionArea`。

---

## 9. Few-shot 规范

必须包含三类显式示例：
1. **正确拓扑**：`PipelineBuilder` $\rightarrow$ `数据管理` $\rightarrow$ `材质映射`。
2. **禁止跳级**：拒绝 `材质映射 ── belongs_to ──> PipelineBuilder`。
3. **禁止创造分类**：拒绝 LLM 自行创建 `数据处理模块` 等未注册节点，强制引用已有上下文。

---

## 10. 去重与实体指纹策略

实体唯一性指纹算法：
$$\text{Fingerprint} = \text{SHA256}(\text{canonical\_name} + \text{entity\_type} + \text{parent\_context})$$
允许 `Redis` (EnvironmentComponent, StampServer) 与 `Redis` (Service, PipelineBuilder) 在不同父上下文下合法共存。

---

## 11. 检索架构 (Graph RAG Routing)

1. **产品能力问题**（“PipelineBuilder 有哪些功能？”）：
   $$\text{Product} \longrightarrow \text{FunctionArea} \longrightarrow \text{Feature}$$
2. **操作流程问题**（“如何创建工程？”）：
   $$\text{Feature} \longrightarrow \text{Procedure} \longrightarrow \text{Chunk}$$
3. **参数配置问题**（“默认端口是多少？”）：
   $$\text{Constraint} \longrightarrow \text{Chunk}$$

---

## 12. 信任模型与验收指标

### 信任模型
- **Level 0 (Product Backbone)**：★★★★★
- **Level 1 (FunctionArea Registry)**：★★★★☆
- **Level 2 (Feature / Entity)**：★★★☆☆
- **Level 3 (Document Evidence)**：★★☆☆☆

### 验收指标
1. **图谱质量**：零重复 `FunctionArea`，无孤立业务实体，无跳级冗余边，Feature 查询不误召回参数节点。
2. **完全可解释**：任何回答均支持 $\text{Answer} \rightarrow \text{Entity} \rightarrow \text{Chunk} \rightarrow \text{Document}$ 确定性追溯。
