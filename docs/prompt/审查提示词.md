请对当前项目/分支/PR 做一次“通用深度架构审查”，不要只检查代码是否能跑、测试是否通过，也不要只围绕我已经指出的问题审查。

你的目标是主动发现我没有提出来的隐患，包括但不限于：职责错位、事实源分裂、规则补丁膨胀、数据污染、评测失真、临时方案固化、模块边界混乱、长期不可维护设计。

请按以下维度逐层审查。

---

## 1. 架构分层审查

请先还原当前项目的主要架构分层，并判断每个新增或修改模块实际属于哪一层：

* 输入/解析层
* 数据清洗层
* 存储层
* 索引层
* 知识事实层
* 查询理解层
* 检索策略层
* 召回融合层
* 重排层
* 生成层
* 评测层
* 运维/治理层
* 临时补丁层

然后检查：

* 是否有模块承担了不属于自己的职责？
* 是否有“中间层”正在变成长期架构债？
* 是否有业务知识被写进了策略层、配置层、测试层或临时规则里？
* 是否有运行策略被误写进了知识库、图谱、数据库或事实层？
* 是否有本该下沉到统一 schema / 数据库 / 知识图谱 / 索引 / 配置中心的内容，被散落在代码里？

请输出：

| 模块/文件 | 当前职责 | 实际承担的额外职责 | 是否职责错位 | 建议归属 |
| ----- | ---- | --------- | ------ | ---- |

---

## 2. 单一事实源审查

请主动寻找项目中是否存在“同一事实被多个地方维护”的情况。

重点检查：

* 同一个实体、概念、字段、关系、别名、分类、状态、来源、规则，是否同时存在于多个文件或模块？
* 某些事实是否同时存在于代码、配置、测试数据、数据库、索引、文档、图谱、profile、脚本中？
* 如果多个地方都有，哪个才是权威源？
* 是否缺少同步、迁移、校验、去重、回滚机制？
* 是否存在“删掉某个补丁后系统就失去某类知识”的情况？

请输出：

| 事实/规则/状态 | 出现位置 | 当前权威源 | 问题 | 建议权威源 | 迁移方式 |
| -------- | ---- | ----- | -- | ----- | ---- |

---

## 3. 规则补丁与架构债审查

请检查当前实现中是否出现 case-specific patch。

重点寻找：

* 为了解决某个具体问题而硬编码的实体名、关键词、来源、章节、路径、字段、特殊判断
* 看似配置化，但实质是把领域知识塞进规则补丁
* 看似测试辅助，但实际影响线上逻辑
* 看似中间层，但长期会越来越重
* 看似简单 if/else，但未来会扩散成规则泥潭

请判断每个规则：

* 是稳定领域事实？
* 是检索/运行策略？
* 是临时 workaround？
* 是测试专用逻辑？
* 应该保留、下沉、迁移、删除，还是抽象成通用机制？

请输出：

| 规则/补丁 | 解决的问题 | 本质类型 | 长期风险 | 建议处理 |
| ----- | ----- | ---- | ---- | ---- |

---

## 4. 数据污染风险审查

请重点检查所有可能写入数据的位置。

包括但不限于：

* 正式数据库
* 向量库
* 关系库
* 图谱库
* 缓存
* 索引
* 评测集
* 配置文件
* 运行结果文件
* 备份文件
* Git 工作区
* 测试临时目录

检查：

* 是否有脚本默认覆盖输入文件？
* 是否有命令默认写正式环境？
* 是否有测试可能污染真实数据？
* 是否有 untracked 临时文件、debug 脚本、agent 工具文件可能被误提交？
* 是否有 dry-run / apply 区分？
* 是否有 backup / rollback？
* 是否有幂等保护？
* 是否有写入前校验？
* 是否有写入后健康检查？

请输出：

| 写入点 | 写入内容 | 风险等级 | 是否默认写入 | 是否可回滚 | 建议 |
| --- | ---- | ---- | ------ | ----- | -- |

---

## 5. 评测可信度审查

请不要只看测试是否通过，要判断评测是否可信。

重点检查：

* 测试是否验证了真实目标，而不是验证实现细节？
* 评测集是否绑定过期 ID、路径、缓存或旧结构？
* 是否存在指标虚高或虚低？
* fallback 是否污染指标分母或命中判断？
* 是否有回归阈值？
* 是否有数据健康检查？
* 是否有 golden set？
* 是否有 hardcases？
* 是否有 integration test 与 unit test 的边界？
* 是否有测试隔离？
* 是否有测试只覆盖正例、不覆盖误伤和中性场景？

请输出：

| 测试/评测 | 当前验证内容 | 可信度问题 | 缺少的反例/边界 | 建议 |
| ----- | ------ | ----- | -------- | -- |

## 6. 可演化性审查

请判断当前设计在规模扩大后是否还能维护。

假设以下情况发生：

* 数据量扩大 10 倍
* 实体/规则数量扩大 10 倍
* 新增多个产品线
* 新增多个知识库
* 多人协作维护
* 需要频繁重建索引
* 需要持续评测和回归

请检查：

* 当前模块是否会变成瓶颈？
* 当前配置是否会膨胀？
* 当前规则是否会互相冲突？
* 当前数据结构是否支持演化？
* 是否缺少版本、审计、迁移、回滚、失效检测？
* 是否存在无法解释的隐式行为？

请输出：

| 设计点 | 当前做法 | 规模化后的问题 | 建议演化方向 |
| --- | ---- | ------- | ------ |

## 10. 输出格式要求

最后请按下面格式输出审查结论：

### A. 总体结论

用 5 到 10 行总结当前项目/分支状态。

### B. 当前架构分层图

用文本图画出当前架构。

### C. 最高优先级问题

按 P0/P1/P2/P3 分级：

* P0：会导致数据污染、错误写入、严重架构错误、不可逆后果
* P1：会导致长期架构债、事实源分裂、评测失真、明显维护风险
* P2：会导致局部混乱、重复逻辑、边界不清
* P3：普通代码质量、命名、文档、测试补充

每个问题必须包含：

* 问题描述
* 证据位置
* 影响
* 推荐修复
* 是否阻塞继续开发

### D. 哪些内容应该迁移或下沉

主动列出：

| 当前所在位置 | 内容 | 应该迁移到哪里 | 为什么 |
| ------ | -- | ------- | --- |

### E. 哪些内容应该保留在当前层

| 内容 | 当前层 | 为什么不应迁移 |
| -- | --- | ------- |

### F. 是否建议继续开发

* 可以继续，但先处理 P0/P1
