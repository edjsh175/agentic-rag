# 当前系统架构基线（2026-08-20）

> **状态**：当前有效架构基线。本文描述当前代码和运行 Trace 已确认的职责边界，不是新的实施计划。
>
> **代码优先**：具体行为以 [routes.py](../../../rag_knowledge/api/routes.py)、[rag.py](../../../rag_knowledge/services/rag.py)、[agent_orchestration/runtime.py](../../../rag_knowledge/services/agent_orchestration/runtime.py) 及配置文件为准；本文用于统一架构口径。旧的“当前/现状”架构快照已归入历史目录，不得覆盖本文。

## 1. 一句话定义

当前系统是：

> **公共语义门禁 + 两种执行引擎（固定 Linear / 自主 Agent）+ 共享检索子系统 + 共享证据生成收口；主 LLM 与 helper LLM 属于横切的运行时资源层。**

Agent 不是另一套固定 RAG 流水线，而是一个能够按需编排知识库检索、图谱探索、证据复用、澄清和外部搜索的工具执行层。

## 2. 总体数据流

```text
用户请求
  │
  ▼
/query 或 /query/stream
  │
  ├─ 空问题 / 敏感 / greeting 短路
  ├─ COM Phase 0 门禁
  └─ DialogueUnderstanding（入口澄清检查）
       │
       ├─ 需要澄清 → 返回澄清卡片
       │
       └─ 不需要澄清 → 按 mode 硬分流
             │
             ├─ linear → 固定检索流水线
             │
             └─ agent  → Stage 1 + Agent Tool Loop
                              │
                              ▼
                    Evidence / Context
                              │
                              ▼
                       GenerationPack
                              │
                              ▼
                          Answer LLM
                              │
                              ▼
                        AnswerFinalizer
                   Grounding / 引用 / Claim Guard
                              │
                              ▼
                           最终回答
```

`mode=agent` 和 `mode=linear` 是用户可见的硬分流入口。两条执行链在 Evidence/Context 之后重新汇合，最终都经过生成、Grounding 和引用输出。

## 3. 公共入口与语义门禁

公共请求层当前依次处理：

1. 空问题、敏感内容和 greeting 的确定性短路；
2. COM Phase 0 等业务前置拒答；
3. `DialogueUnderstanding.analyze(run_clarify=True)` 的入口澄清检查；
4. 未触发澄清时，根据 `mode` 进入 Linear 或 Agent。

`run_clarify=True` 的真实语义不是“只判断是否反问”：

```text
QueryClarificationService
  ├─ needs_clarification → 返回 clarify
  └─ 不需要澄清 → 继续完成本轮 retrieval understanding
```

因此，普通问题在入口已完成一次 Understanding 后，分支内部仍可能通过 `run_clarify=False` 再执行一次检索理解。该行为是当前事实，尤其在有历史对话时可能重复触发上下文化；是否合并为单一 Understanding 结果，列为后续治理事项，不在本文假设已经修复。

入口澄清和 Agent `clarify` Tool 也不是同一层：

- 入口澄清是请求进入执行引擎前的公共门禁；
- Agent `clarify` 是 Tool Loop 中由 Agent 根据当前 Observation 主动决定的暂停动作。

二者都能产生澄清，但触发时机和控制者不同。

### 3.1 问答主链的 LLM 角色：目标口径与当前接线

你的“两种对话模型”理解是合理的目标架构：

- **主 LLM**：Agent 的工具决策与最终总结回答；Linear 的最终回答；
- **helper LLM**：Linear 的意图判断、上下文化/查询改写，以及可选的安全网；
- Embedding、Reranker 不属于对话 LLM；Vision、图谱抽取属于其他业务支路，不计入普通文本问答主链。

但截至 2026-08-20，代码接线并没有完全实现这个目标。当前真实调用关系如下：

| 场景 | 目标口径 | 当前代码实际调用 |
|---|---|---|
| Agent 工具决策 | 主 LLM | **helper LLM**；`AgentLoop._decide_via_llm()` 根据 helper 是否配置，明确选择 `role="helper_llm"` |
| Agent 最终回答与 grounded retry | 主 LLM | 主 LLM |
| Linear 意图判断 | helper LLM | **主 LLM**；`QueryPlanner._classify_via_llm()` 调用 `role="llm"` |
| Linear 历史上下文化/查询改写 | helper LLM | **主 LLM**；`QueryContextualizer._contextualize_via_llm()` 调用 `role="llm"` |
| Linear 澄清预检 | helper LLM | **主 LLM**；`QueryClarificationService` 调用 `role="llm"` |
| Graph Query / Backbone 改写 | helper LLM | **主 LLM**；`GraphQueryRewriter` 两条 LLM 路径都调用 `role="llm"` |
| 知识库路由 | helper LLM | helper LLM；`RagChain._route_query()` 调用 `role="helper_llm"` |
| 回答 Grounding 审查 | helper LLM | 固定调用 `helper_llm`；Reviewer 不可用或协议非法时 fail closed |
| 历史摘要 | 条件式 helper LLM | 条件触发，但当前 `HistoryCompressor` 调用的是 `role="llm"` |

所以，**如果问“应该是什么架构”，你的口径是对的；如果问“当前代码实际上怎么跑”，当前代码是模型角色接线漂移，不能按你的目标口径直接描述。** 我之前的文档没有指出这层漂移，并把组件/模型角色混写，是我的错误。

这不是“系统有很多主 LLM”的结论：正常问答的模型角色仍可收敛为主 LLM + helper LLM。问题在于若干 helper 任务现在错误地路由到了主 LLM，而 Agent 决策又反向路由到了 helper LLM。

## 4. Linear：固定检索流水线

Linear 模式是确定性的“一次理解 → 规划 → 检索 → 后处理 → 回答”：

```text
RetrievalScope
  ↓
DialogueUnderstanding（run_clarify=False）
  ↓
Retrieval Query Specs
  ↓
Query Planner
  ↓
Graph Plan（可选）
  ├─ Backbone Rewrite
  ├─ Graph Link / Expand
  └─ Graph Query Rewrite（条件启用）
  ↓
多路检索
  ├─ Vector
  ├─ BM25 / SDK BM25（按配置）
  └─ Multi-query RRF
  ↓
Scope Admission
  ↓
Reranker / Retrieval Quality / Anchor Filter / Compression（按配置）
  ↓
GenerationPack → Answer LLM → AnswerFinalizer
```

Linear 的 `RetrievalScope` 在请求开始时计算证据准入边界，包括根实体、可准入实体、来源路径和排除重绑定等约束；它不执行 Agent 式的多轮工具决策。

## 5. Agent：Stage 1 + Tool Loop

Agent 的固定部分只有三段：

```text
Stage 1：Semantic Understanding / Identity
  ↓
Stage 2：Agent Tool Loop（Decide → Act → Observe）
  ↓
Stage 3：Evidence → Answer → Grounding → Publish
```

### 5.1 Stage 1

`_run_agent_turn()` 先调用检索理解，构造 `SemanticTaskContext` 和 `IdentityScope`，再创建 `ConversationContext`、`ExplorationGrantResolver` 与 `EvidencePool`。Stage 1 不属于 Tool Loop，也不存在一个当前固定的 `understand` Tool。

### 5.2 Stage 2 工具表

| Tool | 作用 | 是否固定调用 |
|---|---|:---:|
| `retrieve_kb` | 执行知识库检索并写入 EvidencePool | 否 |
| `reuse_evidence` | 复用上一轮仍有效的引用证据 | 否 |
| `link_entities` | 图谱实体定位、消歧与关系探索 | 否 |
| `clarify` | Agent 主动发起澄清并暂停 | 否 |
| `environment.read_status` | 读取当前服务状态 | 否 |
| `web_search` | 外部网页检索；仅在显式开启联网时注册 | 否 |

Agent 每次工具调用都经过 Harness：工具权限和参数校验、探索授权、步骤/检索预算、Evidence Gate、复用限制和 Cycle Detection。Harness 约束 Agent 的行动边界，但不把工具编排成固定顺序。

当前默认运行口径为 `max_steps=8`、`retrieve` 上限为 8；实际值仍遵循环境变量 > 配置文件 > 代码默认值的配置优先级。

## 6. `retrieve_kb` 是一个完整检索子系统

从 Agent 视角看，`retrieve_kb` 是一个 Tool；从资源和控制流视角看，它包含完整的检索子系统：

```text
retrieve_kb
  ├─ ExplorationGrant 授权
  ├─ Query 合并
  ├─ Query Planner
  ├─ Graph Plan
  │   ├─ Backbone Anchor
  │   ├─ Graph Link
  │   ├─ Graph Expand
  │   └─ Graph Query Rewrite（条件）
  ├─ Retrieval
  │   ├─ Vector
  │   ├─ BM25
  │   ├─ SDK BM25（条件）
  │   └─ Multi-query RRF
  ├─ Scope Admission
  ├─ Reranker
  ├─ Retrieval Quality
  ├─ Anchor Filter
  └─ Context Compression（条件）
       ↓
   EvidenceGroup → EvidencePool → Agent Observation
```

Agent 第二次及后续调用 `retrieve_kb` 时，复用本轮 `ConversationContext` 中已有的 Understanding，不重新执行 Stage 1；但每次 Tool Call 仍会重新进行 Query Planning、Graph Plan、Retrieval 和后处理。

## 7. 图谱的两个角色

图谱既可以被 Agent 显式调用，也可以作为检索子系统的内部能力：

- `link_entities` 是 Agent 自主选择的显式工具，用于实体定位、关系探索和上下文补充；
- `retrieve_kb` 内部的 Graph Plan 仍可能执行实体链接、图扩展、图查询改写和图文融合，即使 Agent 没有先调用 `link_entities`。

因此，`link_entities` Tool 不是系统使用图谱的唯一入口，也不能把“先 `link_entities`、再 `retrieve_kb`”当成 Agent 的固定顺序。

## 8. Scope 与证据边界

两种模式的范围语义不同：

| 模式 | 主要范围对象 | 语义 |
|---|---|---|
| Linear | `RetrievalScope` → `EvidenceScope` | 请求开始时计算一套证据准入边界 |
| Agent V1.6 | `SemanticTask` → `IdentityScope` + 每次 `ExplorationGrant` | 身份锁定与检索范围分离；每次探索单独授权 |

Agent 的 `IdentityScope` 只回答“当前用户说的是谁”，不等于“后续只能检索谁”。Agent 选择 `target_entity` 后，由 `ExplorationGrantResolver` 判断本次探索是否有权执行。

## 9. 共享生成与发布收口

两条执行链最终都进入：

```text
Evidence
  ↓
GenerationPack
  ├─ 历史压缩（长历史且 cache miss 时可后台生成 summary）
  └─ Token Budget 裁剪
  ↓
Answer LLM
  ↓
AnswerFinalizer
  ├─ strict_kb：Helper LLM 审查同一冻结 Evidence Snapshot
  ├─ REVISE 时允许一次 Atomic Claim grounded retry，并由 Helper 二审
  └─ 二审不通过或 Reviewer 异常 → 阻断发布
```

History Compression 不是每次回答固定调用的模型步骤；短历史直接继续，长历史命中缓存时复用 summary，长历史 cache miss 时当前请求先按策略截断并安排后台 summary。它属于条件式模型调用，不是第三种对话模型角色；当前代码把它接到了主 `llm` endpoint。

Agent 侧在最终回答前先冻结 Evidence Snapshot；Main 与 Helper Reviewer 使用同一快照。Evidence Gate 负责回答前的证据可用性，答案内容是否受支持只由 Helper LLM Reviewer 判断。

## 10. GPU 服务属于横切资源层

GPU Monitor 当前是问答主链的旁路资源能力：

```text
RAG Server 启动
  ↓
gpu-agent（可选）
  ↓
nvidia-smi → GPU 指标
  ↓
GpuMonitor → /gpu API / 最终模型 VRAM Guard
```

当前已确认的边界：

- `_apply_vram_guard()` 只在最终 Answer Model 生成前检查模型显存并执行 fallback；
- GPU Monitor 当前不决定 Agent / Linear 分流，也不统一调度所有 Tool 内部 LLM；
- `environment.read_status` 当前只返回 server、kb_name、graph_enabled，不向 Agent 暴露 GPU 指标。

因此 GPU Monitor 应视为 `L-1 Runtime Resource Layer`，不应与 Agent/Linear 业务控制流混为同一层。

## 11. 当前 Trace 对架构的验证

2026-08-20 11:27 的 Trace：[73f6b29736264393b7ffa3415d2079d9.json](../../../data/qa_traces/20260820/73f6b29736264393b7ffa3415d2079d9.json)。问题为“webgl webrtc是不是不同技术路线”，实际路径是：

```text
Step 1：retrieve_kb → 6 chunks
Step 2：Agent 改写 query 后再次 retrieve_kb → 6 chunks
Step 3：准备重复 retrieve_kb → Cycle Detection → 停止循环
最终：基于当前 Evidence 生成回答
```

该 Trace 没有先调用 `link_entities`，但检索计划内部仍出现 WebGL、WebRTC、graph query 和 graph rewrite。这证明当前 Agent 是按 Observation 自主选择 Tool，且 `retrieve_kb` 内部图谱能力与显式 `link_entities` 是两条不同的使用路径。

## 12. 后续治理观察点

以下是当前架构已暴露、但不应在本文中假设已经解决的事项：

1. 入口 `run_clarify=True` 与分支内 `run_clarify=False` 可能重复执行 Understanding，需决定是否引入本轮 Understanding 复用。
2. 公共入口澄清与 Agent `clarify` Tool 需要继续明确触发条件和责任边界。
3. `retrieve_kb` 的 Tool 预算、内部检索成本和 Agent 循环预算需要分层观测，不能只按 Tool 数量估算资源。
4. GPU 信息是否进入 Agent 的环境工具、以及是否参与更多模型/工具调度，仍属于后续资源治理设计。
5. Linear stream / non-stream 对 `direct_chat` 的处理存在代码路径差异，需单独补回归验证。

这些事项是架构治理入口，不代表本文已经提出或批准具体实现方案。
