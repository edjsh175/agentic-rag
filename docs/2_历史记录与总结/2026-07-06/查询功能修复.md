# RAG 查询功能修复与检索增强方案总结

本篇文档针对用户提问部分名词及流程型问题时，系统召回候选充足却由于 LLM 规则限制导致“拒答”的现象进行了深入排查，并提出了意图驱动的检索增强（Query Planner）方案。

---

## 1. 问题现象与排查结论

### 1.1 问题表现
- **输入**：`"如何使用DOMBuilder工具进行发布？"`
- **输出**：`"当前知识库中未查询到相关内容。"`
- **现象**：前端未显示任何来源引用文档。

### 1.2 排查结论
该问题**不是**检索缺失或向量库/BM25 索引未命中，而是由于：
1. **成功召回但生成受拒**：检索层实际从 Chroma 和 BM25 分别召回了 12 个相关 chunk，并通过 RRF Fusion 融合出了 4 个高相关候选来源。
2. **上下文过载/不足以完全回答**：由于 `top_k` 默认限制为 4，且知识库里关于操作步骤的内容被结构化切分，4 个 chunk 只覆盖了“工程设置”，缺乏后续的“编译与发布”步骤。
3. **拒答触发零引用删除**：LLM 判定无法完整回答，遵循严格系统 Prompt 的限制输出 `"当前知识库中未查询到相关内容。"`，因未在正文中使用 `[1]` 等编号引用，后续的零引用过滤方法 `_filter_cited_sources()` 将 4 个候选来源全部过滤掉，最终在前端呈现为“没搜到任何内容”的假象。

*(对比：“DOMBuilder工程设置”因为可以直接对应到单点定义的 Chunk，所以能被正确回答并引用来源。)*

---

## 2. 核心根因分析

1. **关键词泛化导致候选集稀释**
   - `"发布"` 一词在 `StampTools`/`StampServer` 中被大量使用，导致混入了许多无关内容（如 `StampServer 影像发布服务配置` 等），排挤了真正需要的 `DOMBuilder` 步骤。
2. **固定 `top_k=4` 不够容纳“多步骤流程”**
   - `DOMBuilder` 的发布流程散落在多个小节中（`3.2.1 工程设置`、`3.2.2 数据设置`、`3.2.3 编译级别`、`3.2.4 数据编译`）。只召回 4 个 chunk 极易漏掉后半部分，使大模型无法形成闭环回答。
3. **Query 改写未对产品手册章节进行展开**
   - `QueryContextualizer` 改写后的 query 依然停留在泛泛的 `"DOMBuilder 发布"` 层面，没有被精准扩展为更具体的手册章节名，导致检索效率降低。
4. **严格的零引用过滤导致假阴性表现**
   - 只要 LLM 给出拒答语，所有检索到的文档来源都将被过滤，剥夺了用户通过“相关来源”自助排查的机会。

---

## 3. 意图驱动的检索增强方案（Query Planner）

为解决通用流程型/操作型/部署型问题，引入 **Query Planner**，实行“意图驱动检索”。

### 3.1 职责划分

| 组件 | 核心职责 | 输出物 |
| :--- | :--- | :--- |
| **QueryContextualizer** | 处理历史追问（指代消解、关联前文改写） | `standalone_query` |
| **QueryPlanner** | 识别问题意图（意图分类、检索参数规划、阶段词扩展） | `RetrievalPlan` |

---

### 3.2 方案分阶段实施计划

#### 第一阶段：Query Planner + 阶段词扩展 + 动态 top_k
*在不重建知识库的前提下，通过优化检索策略解决 60% 左右的流程问题拒答。*

- **意图分类**：通过 LLM（辅助模型 `gemma3:4b`）判断意图；如 LLM 不可用，自动降级为预设的正则表达式关键词匹配（匹配“如何/怎么/步骤/流程”等）。
- **阶段词扩展**：当识别为 `procedure`（流程）或 `deployment`（部署）时，提取核心词并与通用阶段词（如 `配置`、`安装`、`编译`、`启动` 等）结合，进行多路并发召回。
- **参数动态规划**：根据意图类型，动态调整 `top_k`、候选池 `candidate_k` 以及是否强制启用重排序（Rerank）。
  
| 意图 (Intent) | 规划 top_k | 规划 candidate_k | 启用 Rerank |
| :--- | :---: | :---: | :---: |
| **definition** (单点定义) | 4 | 12 | 按原配置 |
| **config** (配置属性) | 4 | 12 | 按原配置 |
| **procedure** (操作流程) | 8 | 24 | **True** |
| **deployment** (部署搭建) | 8 | 24 | **True** |
| **troubleshooting** (排错诊断) | 6 | 18 | **True** |
| **comparison** (概念对比) | 6 | 18 | **True** |

#### 第二阶段：邻近 Chunk 扩展
*解决流程步骤被切片策略切碎到相邻 Chunk 的问题。*
- **实现原理**：利用 `unstructured_loader` 切片时已包含的 `source` 和 `section_index` 元数据。
- **扩展策略**：在流程/部署意图下，对向量检索命中的核心 Chunk，自动向前后扩展相邻的 Chunk（如 `section_index ± 2`），去重后一并送入 LLM 组装上下文。

#### 第三阶段：回答层优化（“部分命中部分回答”）
*消除“检索到了但前端显示没搜到”的差体验。*
- **提示词改造**：微调 `_SYSTEM_PROMPT`，使 LLM 在遇到部分命中时先回答已知依据，并优雅说明缺失部分，例如：
  > “以上为知识库中已查到的部分内容。关于[未覆盖的方面]，当前知识库中未查询到相关内容。”
  
#### 第四阶段：评估集覆盖
- 自动提取标题实体，生成流程型问题的模板化评估集，建立流程检索和回答的 Baseline。

## 4. 第一阶段详细改动清单

### 4.1 新增文件：`rag_knowledge/services/query_planner.py`
实现 QueryPlanner 业务逻辑和数据结构：
```python
from dataclasses import dataclass

@dataclass
class RetrievalPlan:
    """检索计划：由 QueryPlanner 生成，指导后续检索与排序参数"""
    intent: str            # 意图类型
    queries: list[str]     # 扩展后的检索查询列表
    top_k: int             # 动态 top_k
    candidate_k: int       # 候选池大小
    enable_rerank: bool    # 是否启用 Rerank
    expand_neighbors: bool # 是否启用邻近扩展
    confidence: float      # 置信度
```

### 4.2 修改文件

1. **`rag_knowledge/services/rag.py`**
   - 实例化 `QueryPlanner`。
   - 在 `query()` / `aquery()` / `stream_query()` 入口方法中，根据 QueryPlanner 生成的 `RetrievalPlan` 动态调整检索入参。
2. **`rag_knowledge/config.py` 与 `config.ini`**
   - 增加 `[query_planner]` 配置段，允许细粒度调节各意图类型的 `top_k` 和 `candidate_k`。

## 5. 待探讨问题 (Open Questions)

2. **意图分类准确性**：`gemma3:4b` 分类器在 6 类意图中的稳定性。如果分类错误，是否需要增大启发式降级规则的权重？
3. **跨阶段集成**：是否建议第一阶段和第三阶段（回答层 Prompt 修改）同时实施，以确保直接向用户输出时有显著体验提升？
