## 1. 背景

当前系统的 SSE 流式架构仍然存在，但知识库问答在 strict grounding 模式下存在明显“黑盒化”问题。

当前表现大致为：

```text
用户提交问题
→ 显示少量状态提示
→ 中间长时间无正文/无详细决策
→ 最后一次性吐出定稿答案
```

实际后台却可能发生：

```text
Main 判断是否澄清
Main 选择工具
Scope/Grant 拒绝
Main 改变策略
retrieve_kb
Evidence 增加
Finalization 判断 PARTIAL
Main 决定补检
第二次检索 NO_PROGRESS
Main 进入 Answer Generation
Candidate V1
Helper Reviewer REVISE
Atomic Claim Rewrite
Candidate V2
Helper Reviewer PASS
Publish
```

这些关键过程多数未被完整展示。

用户希望的目标不是仅恢复一个“思考框”，而是：

> **把整个 Agent 执行生命周期透明展示出来，包括错误、拒绝、重试、证据不足、Reviewer 拒绝、重写和最终通过。**

## 2. 当前实现事实（As-Is）

### 2.1 前端已经具备 thinking 接收能力

当前前端存在：

```text
web/src/api/index.ts
→ onThinking

web/src/views/ChatView.vue
→ targetMsg.thinking
→ AgentThinkingBlock
```

因此问题不是前端完全没有展示能力。

### 2.2 Agent Controller 的 thinking 在 strict_request 下被过滤

当前后端存在：

```python
if strict_request and event.get("type") == "thinking":
    continue
```

因此 Agent Runtime 已经生成的 `decision.thought` 在严格知识库请求下不会转发给前端。

### 2.3 Answer Generator `<think>` 只存 Trace，不发 SSE

当前 strict grounding 下：

```text
<think>...</think>
→ thinking_parts
→ QA Trace
```

但：

```text
thinking event
→ 不发送
```

### 2.4 最终正文采用 Buffer → Finalize → Publish

当前知识问答正文：

```text
Main 生成 Candidate
→ 后台缓存
→ AnswerFinalizer / Grounding Review
→ 最终完整答案一次性发出
```

这一点是正确方向，不应因为恢复透明执行过程而退回未经审核的逐 Token 正文发布。

### 2.5 `thinking` 事件语义混杂

当前同一个 `thinking` 概念可能承载：

```text
Agent Controller thought
Answer Generator <think>
模型内部自由推理文本
```

这导致 strict grounding 只能粗暴地整体屏蔽。

## 3. 第一性原则裁决

### 3.1 最终答案正确性与执行过程透明性是两件事

必须拆开：

```text
Answer Publication Safety
≠
Execution Visibility
```

最终答案仍然：

```text
Generate
→ Review
→ Rewrite if needed
→ Review
→ Publish
```

执行过程则：

```text
Understanding
Decision
Guard
Tool
Observation
Evidence Delta
Gate Result
Reviewer Result
Rewrite
Publication
```

均可实时展示。

### 3.2 strict grounding 只控制“正式答案发布”

strict grounding 不再被用来决定：

```text
Agent 决策能不能显示
工具调用能不能显示
Evidence Gap 能不能显示
Reviewer 拒绝能不能显示
Rewrite 能不能显示
```

它只控制：

> **未经审核的 Candidate 能否成为正式 Final Answer。**

### 3.3 错误过程不需要隐藏

允许用户看到：

```text
Main 判断错误
Guard 拒绝
Scope 拒绝
检索无结果
Finalization PARTIAL
Reviewer REVISE
Candidate 被拒
Main 重写
Reviewer 二审
```

系统无需伪装成“始终一次成功”。

### 3.4 产品透明性必须同时包含“结构化执行事实”和“模型真实推理流”

不能再把下面两者混为一谈：

```text
结构化事件 = 系统发生了什么
Raw Reasoning = 模型当时在怎么推理
```

V1.2 要求两条通道并存：

```text
Execution Event Channel
→ understanding / decision / guard / tool / evidence / review / rewrite / publication
→ 保证即使模型不支持 reasoning，系统行为仍然可解释

Model Reasoning Channel
→ provider reasoning field / Ollama message.thinking / <think>...</think>
→ 只透传模型真实产生的推理内容
→ 不允许后端用模板文案、摘要、reason 字段伪造“思维链”
```

因此：

```text
模型支持 reasoning
→ 必须实时流式展示真实 reasoning

模型不支持 reasoning
→ 明确显示“该调用未提供原始 reasoning”
→ 仍保留结构化 Execution Timeline
→ 不得生成伪思考文本填充空白
```

结构化事件与 raw reasoning 都是产品协议的一部分，但职责不同：前者提供稳定可观测性，后者提供真实模型推理透明性。

### 3.5 Agent 模式与 Pipeline 模式的可视化必须分开

传统 `status`：

```text
正在理解问题…
正在检索知识库…
正在生成答案…
正在审核答案…
```

本质上是为固定阶段的 Pipeline 设计的阶段播报。

在 Agent 模式中，真实执行过程已经由：

```text
Main Decision
→ Guard
→ Tool
→ Observation
→ Evidence Delta
→ Review / Rewrite
```

实时产生，因此不再额外叠加 Pipeline 式 `status` 文案。

最终模式约束：

```text
Agent Mode
→ 以真实 Agent Execution Transcript 为唯一主要过程展示
→ 不再显示“正在检索/正在审核/正在生成”这类人工阶段状态

Pipeline / Linear Mode
→ 保留 status / pipeline stage
→ 用于解释固定管线当前执行到哪一阶段
```

原则：

> **Agent 展示真实动作，不展示模拟阶段；Pipeline 没有自主动作轨迹，因此继续展示阶段状态。**

## 4. 目标体验（To-Be）

用户提出知识库问题后，前端应能实时看到类似：

```text
[理解]
已识别问题主体：StampWebRTC。
目标：查询 UDP 外网部署端口。

[Main]
问题主体明确，无需澄清，开始检索相关部署资料。

[Tool]
retrieve_kb 已启动。

[Evidence]
新增 3 条证据。
当前覆盖：PARTIAL。
仍缺：完整 UDP 外网部署端口清单。

[Main]
现有资料只能确认部分内容，针对完整端口清单执行一次定向补检。

[Tool]
retrieve_kb 第二次调用完成。

[Evidence]
NO_PROGRESS：没有发现新增证据。

[Main]
继续检索预计无法获得更多信息，将基于当前证据生成部分回答。

[Answer]
正在生成 Candidate V1。

[Reviewer]
正在审核 Candidate V1。

[Reviewer]
REVISE + PARTIAL。
发现 1 个未受当前证据支持的原子事实。

[Rewrite]
Candidate V1 未通过审核，正在执行 Atomic Claim Rewrite。

[Reviewer]
Candidate V2 审核通过：PASS + PARTIAL。

[Publish]
正在发布经过审核的部分回答。

[Final Answer]
当前资料可以确认……
```

## 5. SSE 事件协议重构

### 5.1 Agent 与 Pipeline 使用不同的过程事件面

#### Agent Mode

不再把所有过程塞进 `thinking`，也不再叠加 Pipeline 式 `status`。

Agent 主过程事件：

```text
understanding
decision
guard
tool_start
tool_result
evidence_update
evidence_gap
finalization_check
candidate_status
review_status
rewrite_status
publication
final_answer
sources
error
heartbeat
done
```

#### Pipeline / Linear Mode

保留：

```text
status
pipeline
heartbeat
token / final_answer
sources
error
done
```

其中 `status` 只服务于固定阶段流程，不应再被 Agent 模式消费为主执行展示。

### 5.2 `understanding`

用途：

```text
问题理解结果
主体识别
任务类型
是否需要澄清
```

示例：

```json
{
  "type": "understanding",
  "data": {
    "task_type": "knowledge_qa",
    "identity_status": "CONFIRMED_ENTITY",
    "entity": "StampWebRTC",
    "summary": "已识别为 StampWebRTC UDP 外网部署端口问题。"
  }
}
```

### 5.3 `decision`

Main 每一次 Controller Decision 都必须发事件。

```json
{
  "type": "decision",
  "data": {
    "step": 2,
    "action": "tool_call",
    "tool": "retrieve_kb",
    "reason": "当前证据只能覆盖部分问题，需要针对完整端口清单补检。",
    "gap": "完整 UDP 外网部署端口清单",
    "expected_gain": "找到明确的完整端口配置"
  }
}
```

### 5.4 `guard`

代码 Guard 的 allow/deny/fuse 透明展示。

```json
{
  "type": "guard",
  "data": {
    "allowed": false,
    "reason": "exploration_not_authorized",
    "message": "当前目标尚未获得实体探索授权，本次工具调用已拒绝。"
  }
}
```

### 5.5 `tool_start` / `tool_result`

保留当前工具生命周期，但增加：

```text
step
target
gap
expected_gain
progress
```

示例：

```json
{
  "type": "tool_result",
  "data": {
    "name": "retrieve_kb",
    "ok": true,
    "progress": "NO_PROGRESS",
    "summary": "未发现新的可引用证据。"
  }
}
```

### 5.6 `evidence_update`

统一承接 EvidenceDelta。

```json
{
  "type": "evidence_update",
  "data": {
    "new_chunks": 3,
    "new_entities": 0,
    "new_relations": 0,
    "evidence_version_before": 2,
    "evidence_version_after": 3,
    "coverage": "PARTIAL"
  }
}
```

### 5.7 `evidence_gap`

```json
{
  "type": "evidence_gap",
  "data": {
    "coverage": "PARTIAL",
    "missing_facts": ["完整 UDP 外网部署端口清单"],
    "missing_relations": []
  }
}
```

### 5.8 `finalization_check`

仅展示 Evidence Gate 状态，不包含自动 Recovery Action。

```json
{
  "type": "finalization_check",
  "data": {
    "coverage": "PARTIAL",
    "admissibility": "VALID",
    "message": "当前证据可以回答部分问题，但无法覆盖完整端口清单。"
  }
}
```

### 5.9 `candidate_status`

不发送未经审核 Candidate 正文，但展示 Candidate 生命周期。

```json
{
  "type": "candidate_status",
  "data": {
    "version": 1,
    "status": "generated",
    "message": "Candidate V1 已生成，正在进行 Grounding Review。"
  }
}
```

### 5.10 `review_status`

Helper Reviewer 的结构化结果应透明。

```json
{
  "type": "review_status",
  "data": {
    "review_count": 1,
    "verdict": "REVISE",
    "coverage": "PARTIAL",
    "message": "初始答案包含 1 个当前证据未支持的原子事实，需要修正。",
    "claim_reviews": [
      {
        "claim_id": "c2",
        "status": "unsupported",
        "evidence_ids": []
      }
    ]
  }
}
```

### 5.11 `rewrite_status`

```json
{
  "type": "rewrite_status",
  "data": {
    "status": "started",
    "mode": "atomic_claim_rewrite",
    "message": "Candidate V1 未通过审核，正在保留受支持事实并修正未受支持内容。"
  }
}
```

结束时：

```json
{
  "type": "rewrite_status",
  "data": {
    "status": "completed",
    "candidate_version": 2
  }
}
```

### 5.12 `publication`

```json
{
  "type": "publication",
  "data": {
    "final_mode": "grounded_partial",
    "review_verdict": "PASS",
    "coverage": "PARTIAL",
    "message": "答案已通过证据审核，正在发布。"
  }
}
```

### 5.13 `final_answer`

最终正式正文使用独立事件：

```json
{
  "type": "final_answer",
  "data": "当前资料可以确认……"
}
```

不再把审核后的整段正文伪装成普通 `token`。

## 6. Raw Model Reasoning / `<think>` 策略（V1.2 核心修订）

### 6.1 Raw Reasoning 是 Agent 模式正式可见协议，不再只是 Debug 信息

凡本轮在线 LLM 调用实际产生以下任一内容：

```text
Ollama message.thinking
provider reasoning / reasoning_content
<think>...</think>
```

都必须进入统一 reasoning 流，并实时通过 SSE 发送到前端。

禁止：

```text
模型已经产生 reasoning，但后端只存 Trace 不发 SSE
模型支持 thinking，但 Controller / Reviewer 强制 think=False
等模型调用结束后再一次性展示整段 thinking
用 decision.reason、固定模板或阶段摘要替代 raw reasoning
```

### 6.2 新增独立 LLM reasoning 生命周期事件

统一定义：

```text
llm_reasoning_start
llm_reasoning_delta
llm_reasoning_end
```

示例：

```json
{
  "type": "llm_reasoning_start",
  "data": {
    "call_id": "controller-2",
    "role": "main",
    "stage": "agent_controller",
    "model": "qwen3.5:9b"
  }
}
```

```json
{
  "type": "llm_reasoning_delta",
  "data": {
    "call_id": "controller-2",
    "role": "main",
    "stage": "agent_controller",
    "delta": "当前证据只覆盖了部署入口，但还缺少外网 UDP 端口范围……"
  }
}
```

```json
{
  "type": "llm_reasoning_end",
  "data": {
    "call_id": "controller-2",
    "role": "main",
    "stage": "agent_controller",
    "reasoning_available": true,
    "elapsed_ms": 1824
  }
}
```

若 provider 本次调用没有返回 reasoning：

```json
{
  "type": "llm_reasoning_end",
  "data": {
    "call_id": "controller-2",
    "role": "main",
    "stage": "agent_controller",
    "reasoning_available": false
  }
}
```

不得伪造 delta。

### 6.3 必须覆盖本轮所有关键 LLM 调用，而不是只覆盖 Answer Generator

至少包括：

```text
Helper / Stage-1 Understanding（若该步骤实际调用 LLM）
Main / Agent Controller 每一轮 decision
Main / Answer Generator Candidate V1
Helper / Grounding Review #1
Main / Atomic Claim Rewrite 或 grounded retry
Helper / Grounding Review #2
其他实际参与当前回答且会影响控制流或最终答案的在线 LLM 调用
```

每次调用必须有独立 `call_id`，前端不能把多个模型调用的 reasoning 拼成一个无法区分来源的大文本块。

### 6.4 Reasoning 与模型正式输出必须分通道处理

对于结构化调用，例如 Controller / Reviewer：

```text
reasoning stream
→ 实时发 llm_reasoning_delta

最终 JSON / structured content
→ 后端完整缓冲
→ Schema 校验 / parse
→ 再产生 decision / review_status 等结构化事件
```

不能为了获得流式 thinking 而牺牲现有 JSON Schema、协议校验和 fail-closed 行为。

对于 Answer Generator：

```text
reasoning
→ 实时发 llm_reasoning_delta

Candidate 正文
→ strict grounding 下继续仅在服务端缓冲
→ Review 通过前不得进入 final_answer
```

也就是说：

> **“思考过程全透明”不等于“未经审核的候选答案正文提前发布”。**

### 6.5 当前实现必须纠正的三处硬阻断

当前代码事实：

```text
Agent Controller
→ chat_role(... think=False)
→ 非流式调用

Answer Generator
→ 已解析 <think> / message.thinking
→ thinking_parts 只写 QA Trace
→ 不发 SSE

Helper Grounding Reviewer
→ chat_role(... think=False)
→ 非流式调用
```

V1.2 必须全部改造。

### 6.6 前端展示原则

Agent Timeline 中每次 LLM 调用显示为可持续增长的 reasoning block：

```text
[Main · Controller #2]
正在思考…
当前证据只覆盖……
需要判断继续检索是否还能提高覆盖……
……

随后：
[Decision]
调用 retrieve_kb，原因：……
```

Reviewer 同理：

```text
[Helper · Grounding Review #1]
逐步检查 claim-1……
claim-2 的端口范围没有证据……

[Reviewer]
REVISE + PARTIAL
```

用户看到的是“真实 reasoning + 最终结构化裁决”，而不是只有裁决摘要。

### 6.7 Trace 与 SSE 同源

`llm_reasoning_delta` 必须同时进入：

```text
SSE
QA Trace lifecycle events
```

禁止出现：

```text
Trace 有完整 thinking，但 SSE 没有
SSE 有 thinking，但 Trace 无法复盘
```

### 6.8 兼容与降级

如果某个 provider / model 不支持 reasoning：

```text
不报错
不阻断回答
不生成伪 reasoning
发送 reasoning_available=false
继续依赖结构化 Execution Event 保证过程可解释
```

因此 V1.2 的透明度定义是：

```text
真实模型推理：能拿到多少就实时展示多少
系统执行事实：必须 100% 结构化展示
```

## 7. 与第 4 点 Single Controller 的对齐

第 4 点定义：

```text
Main = Decide
Harness = Guard
Tool = Act
Gate = Observe
```

第 5 点直接把这四类对象变成前端透明事件：

```text
Main Decide
→ decision

Harness Guard
→ guard

Tool Act
→ tool_start / tool_result

Gate Observe
→ evidence_update / evidence_gap / finalization_check
```

因此第 5 点不得自己再创建新的隐藏控制路径。

## 8. 与 Grounding Reviewer PRD 的对齐

严格回答链：

```text
Candidate V1
→ Helper Review #1
→ PASS / REVISE / NO_SAFE_ANSWER
```

透明事件：

```text
candidate_status
review_status
```

若 REVISE：

```text
rewrite_status(started)
→ Atomic Claim Rewrite
→ rewrite_status(completed)
→ review_status(#2)
```

若：

```text
PASS + FULL
PASS + PARTIAL
```

则：

```text
publication
→ final_answer
```

若：

```text
NO_SAFE_ANSWER + NONE
```

则：

```text
review_status
→ publication(final_mode=review_blocked)
→ final_answer(受控无安全答案说明)
```

### 8.1 可以透明显示“刚刚的答案被拒绝了”

这是明确产品要求。

允许：

```text
“初始答案没有通过证据审核，正在重新组织。”
```

允许展示：

```text
REVISE
PARTIAL
unsupported claim 数量
claim_id
rewrite action 类型
```

无需隐藏失败。

## 9. 与澄清 / Identity PRD 的对齐

Main 判断需要澄清时：

```text
decision(action=clarify)
→ clarification candidate discovery
→ clarification event
```

用户选择后：

```text
understanding(identity_status=CONFIRMED_ENTITY / CONFIRMED_TOPIC)
```

## 10. 前端模式化展示设计

### 10.1 Agent Mode：Execution Timeline

Agent 模式下一条 Assistant Message 形成：

```text
Execution Timeline
↓
Final Answer
↓
Sources
```

Agent 模式不再额外显示 Pipeline `status` 条、阶段播报或“正在检索/正在生成”类重复文案。

### 10.2 Pipeline / Linear Mode：Stage Status

Pipeline 模式继续使用现有阶段式体验：

```text
status / pipeline stage
↓
正文流或最终答案
↓
Sources
```

例如：

```text
正在理解问题…
正在检索知识库…
正在生成答案…
正在审核答案…
```

这些状态只在 Pipeline / Linear 模式保留。

### 10.3 Agent Timeline Item 类型

```text
理解
Main 决策
Guard
工具调用
工具结果
Evidence 更新
Evidence Gap
Finalization
Candidate
Reviewer
Rewrite
Publish
Error
```

### 10.4 Agent 展示原则

默认展开当前执行项，历史项可折叠。

用户应能快速知道：

```text
现在做到哪一步
刚才为什么失败
为什么又调用工具
新增了什么
为什么不继续检索
答案为什么被重写
最终是否通过审核
```

### 10.5 不要重复刷屏

Agent 模式相同事件应合并：

```text
heartbeat
同一 tool progress 更新
重复 observation
```

并且 Agent 模式直接忽略用于 Pipeline 的重复 `status` / `pipeline` 阶段播报，不把它们渲染进 Timeline。

不能把 Timeline 变成日志控制台。

## 13. 典型 E2E 场景

```text

→ decision(finalize)
→ candidate_status
```

```text

→ review PASS+PARTIAL
```


```text
retrieve #1 → PROGRESS
→ gap
→ decision(retrieve #2)
→ NO_PROGRESS
→ decision(finalize partial)
```

用户看到：

```text
“第二次补检没有新增证据，不再重复搜索。”
```

### Case D：Main 工具选择被 Guard 拒绝

```text
Main → link_entities(target=pipelien)
→ Guard DENIED
→ decision(clarify)
```

全过程透明。

### Case E：Candidate 被 Reviewer 拒绝

```text
Candidate V1 generated
→ Reviewer REVISE + PARTIAL
→ unsupported c2
→ Rewrite started
→ Candidate V2
→ Reviewer PASS + PARTIAL
→ Publish
```

前端明确展示：

```text
“初始答案未通过审核，已重新组织。”
```

### Case F：Reviewer 二审仍失败

```text
Review #2 → NO_SAFE_ANSWER + NONE
→ publication(review_blocked)
```

用户看到：

```text
“修正后的答案仍无法在当前证据范围内安全发布。”
```

## 21. 最终架构

### 21.1 Agent Mode

```text
User Question
    │
    ▼
Understanding ───────────────→ SSE: understanding
    │
    ▼
Main Controller ─────────────→ SSE: decision
    │
    ▼
Harness Guard ───────────────→ SSE: guard
    │
    ▼
Tool Executor ───────────────→ SSE: tool_start / tool_result
    │
    ▼
Evidence Delta ──────────────→ SSE: evidence_update / evidence_gap
    │
    ▼
Main Controller ─────────────→ SSE: decision
    │
    ▼
Candidate V1 ────────────────→ SSE: candidate_status
    │
    ▼
Helper Reviewer ─────────────→ SSE: review_status
    │
    ├─ REVISE
    │    ▼
    │  Atomic Claim Rewrite ─→ SSE: rewrite_status
    │    ▼
    │  Helper Review #2 ─────→ SSE: review_status
    │
    ▼
Publication ─────────────────→ SSE: publication
    │
    ▼
Reviewed Final Answer ───────→ SSE: final_answer
    │
    ▼
Sources / Done
```

### 21.2 Pipeline / Linear Mode

```text
User Question
    │
    ▼
Fixed Pipeline Stage ─────────→ SSE: status / pipeline
    │
    ▼
Retrieve / Generate / Review ─→ SSE: status / pipeline
    │
    ▼
Reviewed Answer ──────────────→ SSE: token / final_answer
    │
    ▼
Sources / Done
```

Pipeline / Linear Mode 不伪装 Agent Decision/Tool Transcript；它只展示真实存在的固定阶段进度。

最终原则：

> **答案发布受控，执行过程透明。**

> **系统可以犯错、被拒绝、重试、重写，但这些过程不再隐藏。**
