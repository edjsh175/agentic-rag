## 0. 执行摘要与最终裁决

本 PRD 不是新增一套 Agent，也不是引入第三个普通对话模型，而是修正当前模型角色接线和回答阶段的控制语义。

最终架构裁决如下：

1. **Agent 模式由 Main LLM 负责两类调用**：
   - Agent Controller：决定是否继续调用工具、调用什么工具、何时结束探索；
   - Answer Generator：在证据冻结后生成最终回答。
2. **Controller 与 Answer Generator 使用两次独立 Main 调用**，使用不同的 system prompt、输入结构和工具权限。
3. 对 Controller 来说，回答能力以 `finalize_answer` 的形式暴露；对 Runtime 来说，它是**终止控制动作**，不是普通 `ToolRegistry` 业务工具。
4. 每个 request 的 Common Stage-1 Understanding 默认只执行一次，生成 immutable `UnderstandingResult`；如果需要 LLM 做追问还原、上下文化和指代消解，则使用 Helper，Agent Controller 仍然使用 Main。
5. `finalize_answer` 触发后，Runtime 先执行 Evidence Sufficiency Gate：
   - 证据不足且仍有预算：拒绝终止，把缺口反馈给 Controller，继续检索；
   - 证据足够：创建 immutable EvidenceSnapshot，进入 Answer Generator；
   - 达到预算仍不足：保留不足状态，进入受限回答，不伪造为充分。
6. **Answer Generator 不拥有工具定义，不接收原始 Thought/Action/Observation，不再回到 Controller 二次总结。**
7. **Linear 模式先执行 Common Stage-1 Contextualize/Resolve，再由 Helper 做意图判断、查询/图查询规划和改写；Main LLM 负责最终回答。**
8. Agent 的 `retrieve_kb` 内部必须 mode-aware：Linear Planner 可以规划，Agent Tool Planner 只能做 normalization/augmentation，不能覆盖 Controller 已明确给出的 query、实体、intent 和 scope。
9. Linear 的复杂任务、Helper 失败或结构化输出不合法时，允许按确定性规则升级到 Main；升级不是第三个模型角色，而是 Main 对复杂规划任务的兜底。
10. 安全检查、权限、预算、循环检测、确定性 Grounding 和引用合法性由 Runtime/确定性代码负责；Helper Semantic Verifier 只能在确定性 Grounding PASS 后做附加语义复核，不能复活确定性 FAIL。

一句话定义：

> **Common Stage-1 负责一次性把会话问题还原成稳定的 UnderstandingResult；Agent 再由 Main LLM 执行“行动阶段 + 回答阶段”，Linear 由 Helper 执行“理解/规划阶段”后接 Main 回答；Runtime 决定什么可以做、证据是否足够以及何时真正结束。**

## 1. 当前问题与根因

### 1.1 当前代码与目标模型分工相反

截至 2026-08-20，代码中已确认存在以下角色漂移：

| 场景 | 目标角色 | 当前实际角色 | 主要位置 |
|:---|:---|:---|:---|
| Agent 工具决策 | Main | **Helper** | `rag_knowledge/services/agent_orchestration/runtime.py` 的 `_decide_via_llm()` |
| Agent 最终回答 | Main | Main | `rag_knowledge/services/rag.py` 的最终生成路径 |
| Linear 意图判断 | Helper | **Main** | `query_planner.py` |
| Linear 历史上下文化/查询改写 | Helper | **Main** | `query_contextualizer.py` |
| Linear 澄清预检 | Helper | **Main** | `query_clarification.py` |
| Graph Query / Backbone 改写 | Helper | **Main** | `graph_query_rewrite.py` |
| 历史压缩 | Helper | **Main** | `history_compressor.py` |
| 知识库路由 | Helper | Helper | `rag.py` 的 `_route_query()` |
| 安全网语义验证 | Helper，可选 | `semantic_verifier`，默认关闭；未单独配置时复用 Helper | `rag.py` |

这不是“系统需要很多个主 LLM”，而是**调用角色接线错位**：Agent 最需要推理和工具编排能力的阶段用了 Helper；Linear 的轻量改写任务却消耗了 Main。

### 1.2 当前 `finish` 只有“结束检索”语义

当前 `AgentDecision` 主要是：

```text
tool_call → 执行工具
finish    → AgentLoop 结束
```

外层 Runtime 在 Loop 结束后再生成回答。这样虽然执行结果能够回答用户，但 Controller 没有显式表达：

> “我判断证据已经足够，现在请求回答阶段接管。”

结果是：

- `finish` 的含义混合了“证据充分”“预算耗尽”“循环熔断”“无结果”多种情况；
- 证据门禁与回答生成的边界不够清晰；
- Trace 难以区分“模型主动结束”和“Runtime 被迫停止”；
- 后续无法安全地把回答阶段建模为终止型能力。

### 1.3 不能用“有证据”替代“证据足够”

当前系统已经有生成后 Grounding，但仍需要生成前 Evidence Sufficiency Gate：

```text
EvidencePool 非空
≠
EvidencePool 已覆盖用户问题的必要事实
```

如果证据不足就直接生成，系统会频繁出现：

```text
证据不足
→ 模型自行补全
→ Grounding 失败
→ Retry / Fallback
```

正确闭环应为：

```text
证据缺口
→ 定向补检
→ 再次评估
→ 证据足够后回答
```

### 1.4 回答阶段不应继续携带 Agent 轨迹

回答模型需要知道：

- 用户到底问了什么；
- 当前会话中的指代和任务上下文是什么；
- 最终允许使用哪些证据；
- 证据是否存在缺口或冲突。

回答模型不需要知道：

- 所有原始 Thought；
- 每一次工具调用的完整参数和 Observation；
- 工具定义；
- 已经被淘汰的检索候选；
- Controller 的内部推理过程。

如果把这些内容全部继续塞入回答上下文，会增加上下文噪声、工具轨迹污染和二次推理风险。

### 1.5 Common Stage-1 Understanding 存在重复计算风险

当前公共入口可能先执行：

```text
DialogueUnderstanding.analyze(run_clarify=True)
        ↓
按 mode 分流
        ↓
Agent / Linear 再次 analyze(run_clarify=False)
```

这会造成同一 request 内重复上下文化、重复 LLM 调用和语义漂移。例如第一次把主体解析为 `PipelineWebGL`，第二次可能只保留为 `Pipeline`。

目标不是简单删除某一层，而是把 Common Stage-1 的结果变成不可变共享输入：

```text
用户问题 + History
        ↓
Common Stage-1 Contextualize / Resolve
        ↓
immutable UnderstandingResult
        ├─ Linear：复用后进入 Intent / Planner
        └─ Agent：复用后进入 Main Controller
```

只有以下情况允许重新计算：

- 用户完成了澄清；
- 用户明确发生 topic shift；
- 请求被 Runtime 重新构造成新的问题；
- 上一结果校验失败且进入显式恢复路径。

## 2. 目标与非目标

### 2.1 本 PRD 目标

| 编号 | 目标 |
|:---|:---|
| G1 | Agent Controller 和 Answer Generator 均使用 Main LLM |
| G2 | 以终止控制动作表达 `finalize_answer`，区分主动终止、证据不足、预算耗尽和循环熔断 |
| G3 | Answer 阶段使用干净、结构化、证据冻结的输入，不携带工具定义和原始轨迹 |
| G4 | Agent 在证据不足时能获得明确缺口并定向补检 |
| G5 | Linear 轻量理解/改写默认切换到 Helper，复杂场景可升级 Main |
| G6 | 维持当前权限、Scope、Grant、预算、循环检测、Grounding 和引用发布收口 |
| G7 | 维持流式状态、工具进度、主动澄清和多轮追问体验 |
| G8 | 通过统一路由审计，能够证明每次模型调用使用了正确角色 |
| G9 | 每个 request 的 Common Stage-1 Understanding 默认只计算一次，并由 Linear/Agent 下游复用 immutable 结果 |

### 2.2 非目标

本 PRD 不包含：

- 更换 Embedding 模型或重建正式 Chroma 知识库；
- 重写 Vector/BM25/Hybrid/Reranker 的检索算法；
- 将 `retrieve_kb` 拆成多个新的业务 Tool；
- 引入多 Agent 互相 handoff 的新架构；
- 将原始思维链展示给用户；
- 默认新增第三个普通对话 LLM；
- 修改 Graph Extraction、Vision、Embedding 的业务实现；
- 把所有模型调用都强行归入 Main/Helper 两个角色。

说明：项目全局仍然可以存在 `embedding`、`vision`、`compression`、`graph_extraction` 等**横切或旁路模型角色**。本 PRD 收敛的是普通文本问答主链，不否认这些业务支路的存在。

## 3. 目标总体架构

### 3.1 双模式总览

```text
用户请求
  │
  ├─ 确定性短路：空问题 / 敏感 / greeting / 请求策略
  │
  └─ Common Stage 1：Contextualize / Resolve（必要时 Helper）
       ↓
     immutable UnderstandingResult
       │
       └─ 按 mode 分流
       │
       ├─ Linear
       │    ├─ Helper：意图判断 / Query Plan / 查询改写
       │    ├─ 确定性检索流水线
       │    ├─ Main：最终回答
       │    └─ Grounding / 引用发布收口
       │
       └─ Agent
            ├─ 复用 UnderstandingResult / IdentityScope / Grant
            ├─ Main Controller：自主工具循环
            │    ├─ retrieve_kb
            │    ├─ link_entities
            │    ├─ reuse_evidence
            │    ├─ clarify
            │    └─ finalize_answer（终止控制动作）
            ├─ Runtime Evidence Gate
            ├─ 创建 immutable EvidenceSnapshot
            ├─ Main Answer Generator：无工具回答
            └─ Grounding / 引用发布收口
```

### 3.2 Agent 两阶段主链

```text
Stage 0：确定性公共门禁
  ↓
Stage 1：Common Contextualize / Resolve
  ├─ deterministic 解析与校验
  ├─ 必要时 Helper 还原追问、指代和 resolved_question
  └─ 生成 immutable UnderstandingResult（本 request 默认一次）
  ↓
Stage 2A：Main Controller
  ├─ 读取 UnderstandingResult、会话上下文、EvidencePool 摘要和可用工具
  ├─ 选择工具或请求澄清
  ├─ 多轮收集证据
  └─ 触发 finalize_answer
  ↓
Runtime Finalization Gate
  ├─ Reject：证据缺口反馈给 Controller，继续检索
  ├─ Forced：预算耗尽，进入受限回答
  └─ Accept：创建 immutable EvidenceSnapshot
  ↓
Stage 2B：Main Answer Generator
  ├─ 新 system prompt
  ├─ 无工具定义
  ├─ 无原始 Thought/Action/Observation
  ├─ 使用结构化会话上下文 + EvidencePool
  └─ 生成带引用的 Candidate
  ↓
AnswerFinalizer
  ├─ Deterministic Grounding
  ├─ 必要时 Main Grounded Retry
  ├─ Deterministic recheck PASS 后才允许 Helper Semantic Verifier
  └─ Deterministic Fallback / Publish
```

### 3.3 “同一个 Main”不等于“同一次调用”

目标不是让一个 Main 调用同时完成工具决策和最终回答，而是：

```text
同一模型角色 / 同一 endpoint
        ≠
同一上下文 / 同一 prompt / 同一次调用
```

这样既保留 Main 的推理能力，又避免回答模型继续受 Agent 工具轨迹影响。

## 4. Agent `finalize_answer` 终止控制动作

### 4.1 设计原则

对模型来说，`finalize_answer` 看起来像 Controller 可以主动调用的能力；对 Runtime 来说，它必须是独立的控制分支：

```text
tool_call → 普通工具执行并回传 Observation
clarify   → 暂停本轮并请求用户补充
finalize  → 进入证据门禁和回答流水线
```

不得将 `finalize_answer` 作为普通 `ToolRegistry` 工具执行后，再把最终答案回传给 Controller 二次改写。

### 4.2 推荐决策协议

推荐将 `finalize` 作为新的规范动作，兼容旧 `finish` 输入：

```json
{
  "action": "finalize",
  "focus_evidence_ids": ["e12", "e18"]
}
```

Prompt 层可以把该动作描述为 `finalize_answer` 能力，但数据协议层只保留 `action="finalize"`。`finalize` 不得同时携带 `tool` 字段，避免出现 `action="finalize"` 与 `tool="retrieve_kb"` 之类的无意义组合。

兼容期内：

```text
旧 action=finish → 解析为 finalize 的兼容别名
Runtime 被迫停止 → 记录 terminal_reason，不伪装成模型主动 finalize
```

### 4.3 参数最小化

Controller 不应通过 `finalize_answer` 改变安全策略、回答权限或证据资格。

唯一允许的可选参数：

```json
{
  "focus_evidence_ids": ["e12", "e18"]
}
```

约束：

- `focus_evidence_ids` 只表示回答重点偏好；
- Runtime 必须执行 `focus_evidence_ids ∩ authorized EvidencePool`；
- 空数组或非法 ID 不得导致证据越权；
- Controller 不提交自由文本 `reason`；Runtime 根据 Evidence Verdict 和执行状态生成 Trace 原因；
- `answer_mode`、`allow_general_knowledge`、`strict_kb` 等策略不能由 Controller 自由修改；
- 最终回答默认看到本轮所有合法、未淘汰、已进入 `EvidenceSnapshot` 的证据。

### 4.4 Finalization Gate

Controller 调用 `finalize_answer` 后，Runtime 按以下顺序处理：

```text
1. 检查当前请求策略和回答类型
2. 计算/读取 AnswerContract
3. 评估 Evidence Sufficiency
4. 检查 IdentityScope / ExplorationGrant / provenance
5. 检查 required fact 的冲突和未解决缺口
6. 通过后创建 `EvidenceSnapshot`
7. 构造 AnswerGenerationContext
8. 调用 Main Answer Generator
```

其中，纯会话释疑、历史回顾和元对话先归类为 `answer_type=direct_chat`：

```text
direct_chat → evidence_not_required → controller_finalize → Direct Answer Context
knowledge   → Evidence Sufficiency Gate → EvidenceSnapshot → AnswerGenerationContext
```

`direct_chat` 仍然必须经过 `finalize` 终止协议，但不调用 Evidence Sufficiency Gate，
也不创建空的 `EvidenceSnapshot`；“无需证据”和“证据不足”必须保持不同的 verdict/reason。

如果证据不足：

```json
{
  "status": "finalization_rejected",
  "reason": "missing_evidence",
  "gaps": [
    "缺少 StampWebGL 与 StampWebRTC 的产品关系证据"
  ],
  "next_action": "continue_tool_loop"
}
```

该结果作为结构化 Observation 交回 Controller，Controller 可以继续调用 `retrieve_kb` 或 `link_entities`。

如果证据足够：

```json
{
  "status": "accepted",
  "evidence_snapshot_id": "evs_...",
  "next_action": "answer_generation"
}
```

### 4.5 预算耗尽与循环熔断

以下情况必须与主动 finalize 区分：

| 情况 | terminal reason | 后续行为 |
|:---|:---|:---|
| Controller 主动调用 finalize 且证据足够 | `controller_finalize` | 正常回答 |
| Controller 主动 finalize 但证据不足、仍有预算 | `finalization_rejected` | 回 Controller 继续检索 |
| 检索预算耗尽 | `retrieve_budget_exhausted` | 受限回答，保留不足状态 |
| Step 预算耗尽 | `step_budget_exhausted` | 受限回答，保留不足状态 |
| 检测到重复工具循环 | `tool_cycle_detected` | 受限回答或确定性 fallback |
| 工具权限/参数拒绝 | `tool_rejected` | Controller 可修正；达到预算后受限回答 |
| 用户主动澄清 | `clarify_pause` | 暂停，不进入 Answer Generator |

预算耗尽不能把 `PARTIAL/INSUFFICIENT` 改写成 `SUFFICIENT`。

### 4.6 Forced Answer 状态矩阵

达到预算上限后，Runtime 根据最后一次 Evidence Verdict 决定回答边界：

| Evidence Verdict | 预算耗尽后的处理 |
|:---|:---|
| `SUFFICIENT` | 正常 Answer；仍需经过 Grounding 和引用发布收口 |
| `PARTIAL` | Main 只回答已覆盖部分，并明确列出未覆盖缺口 |
| `INSUFFICIENT` 且存在部分证据 | 极受限回答，只陈述已确认事实，并说明核心问题证据不足 |
| `INSUFFICIENT` 且无证据 | 确定性 no-knowledge 响应，不调用模型生成知识事实 |
| `CONFLICT` | 展示冲突事实及各自证据，不替用户强行裁决 |

## 5. Answer Generator 上下文契约

### 5.1 输入结构

Answer Generator 接收一个独立的 `AnswerGenerationContext`：

```python
@dataclass(frozen=True)
class AnswerGenerationContext:
    original_question: str
    resolved_question: str
    conversation_context: str
    answer_contract: dict
    evidence_snapshot_id: str
    evidence_items: tuple[dict, ...]
    evidence_verdict: dict
    answer_policy: dict
    execution_summary: str | None = None
```

### 5.2 EvidencePool 与 EvidenceSnapshot

`EvidencePool` 是本轮 Agent 探索期间的 live 状态；`EvidenceSnapshot` 是某次 Finalization Gate 通过后生成的不可变回答输入。

```text
Live EvidencePool
        ↓ Finalization Accept
EvidenceSnapshot.freeze()
        ↓
Answer Generator
```

约束：

- Answer Generator 只能读取 `EvidenceSnapshot`，不能读取正在变化的 Live EvidencePool；
- Snapshot 必须包含 provenance、Scope/Grant 校验结果、Evidence Verdict 和创建时的证据版本；
- Snapshot 创建后不得追加、删除或覆盖 Evidence；
- 下一轮用户追问创建新的 Live EvidencePool，可按复用策略 seed 上一轮仍合法的 cited evidence，但不得把旧 Snapshot 当成可变池继续写入；
- `evidence_snapshot_id` 是回答、Grounding、引用和 Trace 的共同关联键。

### 5.3 必须保留的信息

- 原始用户问题；
- 已解析的问题；
- 结构化会话上下文：历史摘要、最近对话、指代主体、任务类型、澄清结果；
- AnswerContract / RequiredFacts；
- 冻结后的 EvidencePool；
- 每条证据的 `evidence_id`、`chunk_id`、来源和引用位置；
- Evidence Sufficiency 状态；
- 请求级回答策略，例如是否允许通用知识、是否必须严格知识库回答；
- 可选的简短执行摘要，例如“本轮进行了 2 次知识库检索”。

### 5.4 必须排除的信息

- 工具定义和工具 schema；
- 原始 Thought；
- 原始 Action/Observation 全量日志；
- 已被淘汰的候选证据；
- 任何未通过 Scope/Grant 的内容；
- Controller 的内部 rationale / Trace 摘要作为事实依据；
- 未进入 EvidencePool 的检索结果。

### 5.5 会话灵活性不通过原始轨迹实现

多轮交互所需的灵活性来自：

```text
结构化 ConversationContext
+ 当前 resolved_question
+ 历史摘要
+ 最近若干轮用户/助手消息
+ 当前主体与任务状态
+ 可复用 EvidencePool
```

而不是把上一轮完整 ReAct 轨迹原样复制到下一轮 prompt。

### 5.6 Answer Prompt 基本约束

Answer Generator 的 system prompt 必须明确：

1. 只能基于提供的 Evidence 回答知识事实；
2. 每个关键事实必须绑定引用；
3. Evidence 不足时明确说明缺口；
4. 不得自行调用工具；
5. 不得把会话上下文当成知识库证据；
6. 不得把 Controller 的执行理由当成事实；
7. 允许基于多个证据进行有限归纳，但不能引入未被支持的外部事实。

## 6. Evidence Sufficiency 与 Grounding 的双门禁

### 6.1 两个门禁的职责

```text
Gate A：Evidence Sufficiency
回答前：当前证据够不够？

Gate B：Grounding Firewall
回答后：生成文本有没有超出证据？
```

二者不能合并为一个“大模型 Judge”。

### 6.2 Gate A 接入方式

本 PRD复用 [Evidence Sufficiency Gate 与定向补检闭环 PRD](2026-08-20-Evidence-Sufficiency-Gate与定向补检闭环PRD.md) 的数据模型和判定原则：

```text
AnswerContract
  ↓
RequiredFacts
  ↓
EvidencePool Coverage
  ↓
SUFFICIENT / PARTIAL / INSUFFICIENT / CONFLICT
```

首期要求：

- 结构化 Evidence 引用才可以把 fact 标为 `COVERED`；
- 证据不足必须能输出具体 missing fact；
- Agent 负责决定如何补检，Gate A 不直接生成最终 Query；
- Graph 负责导航，最终回答事实仍需可追溯 Evidence；
- Judge 故障时 fail-safe，不得自动判定为 `SUFFICIENT`。

### 6.3 Grounding 失败处理

回答阶段必须严格执行以下顺序：

```text
Main Candidate
      ↓
Deterministic Grounding
      │
      ├─ FAIL
      │    ↓
      │  Main grounded retry
      │    ↓
      │  Deterministic Grounding recheck
      │    │
      │    ├─ FAIL → deterministic fallback
      │    └─ PASS ──┐
      │               │
      └─ PASS ────────┤
                      ↓
          semantic_verifier_enabled?
                      │
             no ─────→ Publish
                      │
                      ↓
                Helper Semantic Verifier
                      │
                 PASS / reject
```

硬约束：

- Deterministic Grounding 的硬失败不得被 Helper Semantic Verifier 覆盖或“复活”；
- Helper Semantic Verifier 只能检查已经通过 Deterministic Grounding 的 Candidate；
- Helper 返回 `reject`、超时或格式错误时，不得升级为 PASS；
- Semantic Verifier reject 后进入确定性 fallback，或进入预先定义的受限发布路径，不重新唤醒 Controller；
- Grounded Retry 最多一次，避免 Answer Pipeline 无界循环。

不要轻易重新唤醒 Controller，否则会形成：

```text
Controller → finalize → Answer → Grounding FAIL
→ Controller → retrieve → finalize → Answer → ...
```

“证据不足”属于 Controller / 检索问题；“答案写坏”属于 Answer Pipeline 问题；“语义复核不通过”属于发布收口问题，三者必须分责。

## 7. 模型角色与路由调整

### 7.1 普通文本问答的目标角色表

| 逻辑阶段 | 默认角色 | 主要职责 | 是否允许工具 |
|:---|:---|:---|:---:|
| Common Stage-1 Contextualize / Resolve | **Helper LLM（必要时）+ 确定性代码** | 追问还原、指代消解、`resolved_question`、基础语义校验；每个 request 默认只执行一次 | 否 |
| Agent Controller | **Main LLM** | 工具选择、参数生成、证据探索、主动 finalize | 是 |
| Agent Answer Generator | **Main LLM** | 根据冻结证据生成最终答案 | 否 |
| Linear 意图判断 / Planner | **Helper LLM** | 基于已解析的 `UnderstandingResult` 判断任务类型、检索意图和 Query Plan | 否 |
| Linear 查询改写 | **Helper LLM** | 基于 `resolved_question` 生成有限 query variants | 否 |
| Linear Graph Query 改写 | **Helper LLM** | 轻量 canonical query / anchor 改写 | 否 |
| Linear 历史压缩 | **Helper LLM** | 非实时关键路径的摘要压缩 | 否 |
| 安全网语义复核 | **Helper LLM** | 仅在确定性门禁无法判断时复核 | 否 |
| 权限、Scope、Grant、预算、循环检测 | **确定性代码** | 约束和治理 | 不适用 |
| Grounding、引用合法性、fallback | **确定性代码 + 条件模型** | 发布前收口 | 不适用 |

### 7.2 当前调用的切换清单

| 模块/调用 | 当前 | 改造目标 | 优先级 |
|:---|:---|:---|:---:|
| Common Stage-1 `DialogueUnderstanding` / Contextualizer | 入口与分支可能重复；部分路径使用 `llm` | 每个 request 一次；必要的 LLM contextualize/resolve 使用 `helper_llm`，下游复用 immutable `UnderstandingResult` | P0 |
| `AgentLoop._decide_via_llm()` | `helper_llm` | `llm` | P0 |
| `QueryPlanner._classify_via_llm()` | `llm` | `helper_llm`；输入来自已解析的 `UnderstandingResult` | P0 |
| `QueryContextualizer._contextualize_via_llm()` | `llm` | `helper_llm`；只在 Common Stage-1 调用一次 | P0 |
| Common Stage-1 Semantic Clarification | `llm` | `helper_llm` 或确定性规则；负责主体/语义绑定，不等同 Agent clarify | P1 |
| `GraphQueryRewriter` 两条改写路径 | `llm` | `helper_llm` | P1 |
| `HistoryCompressor` | `llm` | `helper_llm` | P1 |
| `RagChain._route_query()` | `helper_llm` | 保持 | — |
| 最终回答与 grounded retry | `llm` | 保持 | — |
| `semantic_verifier` | 可选 Helper 复用 | 保持逻辑角色；默认关闭 | — |
| Vision / Embedding / Graph Extraction | 独立旁路角色 | 不纳入本轮切换 | — |

### 7.3 Agent 路由硬约束

Agent Controller 不得因为 Helper 已配置就自动改用 Helper：

```python
# 禁止以“helper 是否存在”决定 Agent Controller 角色
role = "helper_llm" if helper_configured else "llm"
```

目标应为：

```python
role = ModelRoutePolicy.agent_controller_role()
# 固定返回 llm
```

如果 Main provider 不可用：

- 优先使用确定性 fallback 或明确服务降级；
- 不得静默把 Agent Controller 降级成 Helper，除非经过专门评测并明确配置；
- Trace 必须记录 `model_route_fallback`。

原因：Helper 降级会改变工具选择和证据探索质量，不是普通的同义模型替换。

### 7.4 Linear 默认路由与 Main 升级

Linear 默认流程：

```text
Common Stage-1 Contextualize / Resolve
→ immutable UnderstandingResult
→ Helper 意图判断 / Query Planner
→ Helper 查询改写 / query variants
→ 确定性检索
→ Main 最终回答
```

以下情况允许升级到 Main 处理规划/改写：

- Helper 输出为空、JSON 非法或不满足 schema；
- Helper 调用超时或 provider 错误；
- 查询包含多个显式实体并要求比较、关系判断或跨实体归纳；
- 存在未解决的核心指代/实体歧义；
- Query Planner 发现多步任务或多个互相依赖的检索子问题；
- Helper 产生的 query 与用户原意、IdentityScope 或 RetrievalScope 冲突。

升级规则首期采用确定性条件，不以一个未经评测的“模型 confidence”直接决定。

### 7.5 Agent Tool 内部 Planner 必须 mode-aware

`retrieve_kb` 当前内部仍可能调用 Query Planner、Graph Plan 和 Graph Query Rewriter。实施时不能只把这些调用从 `llm` 改成 `helper_llm`，而必须根据调用来源区分权限。

Agent Controller 发出的 Tool 参数是 authoritative input：

```text
Main Controller
  ↓
retrieve_kb(
  query,
  target_entity,
  intent,
  scope / grant
)
```

Agent Tool 内部规则：

- 不重新判断 `target_entity`；
- 不重新解释或覆盖 `intent`；
- 不删除或替换 Controller 的原始 `query`；
- 不扩大 `scope` 或伪造 Grant；
- 允许 deterministic normalization，例如格式清理、同义词补充和安全参数默认值；
- 如果启用 LLM augmentation，只能新增 query variant，不能删除或替换 Controller query；
- 所有新增 variant 必须通过 IdentityScope、RetrievalScope 和实体一致性检查；
- 检索结果仍必须经过现有 Evidence admission、Graph/Chunk 约束和后处理。

因此同一个 Planner 实现需要有明确的 mode-aware 语义：

| 调用来源 | Planner 权限 |
|:---|:---|
| Linear | 可以基于 `UnderstandingResult` 规划、改写和生成 query variants |
| Agent `retrieve_kb` | 只能 normalization / augmentation；Controller 参数优先 |
| Agent `link_entities` | 只能在当前 IdentityScope 与 ExplorationGrant 内导航 |

Agent Controller 已经决定工具参数后，不应再经过 Helper 做一轮无条件 query rewrite。

原因：

- 容易造成实体漂移；
- 破坏 Controller 对 `target_entity` 和 intent 的判断；
- 增加延迟和不可解释的中间决策；
- 与 Agent 的自主工具参数生成职责重复。

`retrieve_kb` 内部可以继续使用现有 Query Planner、Graph Plan 和检索后处理，但必须携带调用 mode，并在 Agent mode 下遵守上述增强器权限。

### 7.6 Common Clarification 与 Agent Runtime Clarify

两种澄清不是同一个动作：

| 层级 | 负责问题 | 示例 | 结果 |
|:---|:---|:---|:---|
| Common Stage-1 Semantic Clarification | 用户到底指的是谁/哪个实体 | “pipeline”是 `PipelineBuilder`、`PipelineWebGL` 还是发布服务？ | 修复 `UnderstandingResult` 或返回澄清卡片 |
| Agent Runtime `clarify` | 主体已知，但完成任务还缺什么信息 | 要排查客户端还是服务端？需要哪个部署环境？ | 暂停 Agent Loop，等待用户补充 |

Common Clarification 在 mode 分流前执行；Agent Runtime `clarify` 只在 Main Controller 已经进入工具循环后执行。两层都触发时，优先完成 Common Stage-1，再进入 Agent。

## 8. 配置与模型切换方案

### 8.1 配置原则

遵循项目现有优先级：

```text
环境变量 > config.ini > 代码默认值
```

本 PRD 的第一阶段优先切换**角色路由**，不直接改变模型名称。

### 8.2 当前本地配置与目标用途

当前 `config-local.ini` 已配置：

```ini
[model.llm]
provider = ollama
model = qwen3.5:9b

[model.helper_llm]
provider = ollama
model = qwen3.5:4b
```

目标用途：

| 模型 | Agent | Linear | 安全/复核 |
|:---|:---|:---|:---|
| `qwen3.5:9b` Main | Controller + Answer | 最终回答；复杂规划升级 | 不作为默认复核 |
| `qwen3.5:4b` Helper | 不进入核心 Controller | 意图、改写、历史压缩 | 条件式语义复核 |

本地环境第一阶段不需要因为本 PRD 重建向量库：LLM 角色切换不改变 Embedding。但如果同时更换 Embedding，必须按照项目规则受控重建知识库并重新生成相关评测集。

### 8.3 生产/混合配置

生产或混合配置继续以实际 ini 为准：

- `[model.llm]` 指向主回答/Agent Controller 模型；
- `[model.helper_llm]` 指向轻量辅助模型；
- `[model.semantic_verifier]` 如未单独配置，可复用 Helper endpoint；
- Graph Extraction、Vision、Compression 使用各自既有配置，不因本 PRD 自动并入 Main/Helper 主链。

不允许在 PRD 实施时未经评测直接替换生产模型名称。模型名称变更必须单独记录：provider、模型版本、上下文长度、工具调用能力、显存/延迟、质量评测结果和回滚配置。

### 8.4 建议新增的最小路由配置

不建议为每一个函数增加独立配置。只增加阶段级策略：

```ini
[model_routing]
common_stage1_role = helper_llm
agent_controller_role = llm
agent_answer_role = llm
linear_preprocess_role = helper_llm
linear_escalation_enabled = true
semantic_verifier_role = helper_llm
```

约束：

- `common_stage1_role` 只用于低风险 Contextualize/Resolve；确定性路径可以不调用模型；
- `agent_controller_role` 和 `agent_answer_role` 生产默认固定为 `llm`；
- 允许测试环境覆盖，但 Trace 必须显示实际角色；
- `linear_preprocess_role` 默认 `helper_llm`；
- `semantic_verifier_role` 是逻辑角色，不代表必须新增模型 endpoint；
- 配置项只控制角色选择，不赋予模型新的工具权限。

### 8.5 模型切换验收前置条件

任何 Main/Helper 模型替换必须先通过：

1. 结构化输出 schema 测试；
2. Agent 工具调用参数测试；
3. 中文多轮指代测试；
4. Evidence 引用和 Grounding 回归测试；
5. 本地显存/启动/超时测试；
6. 至少一轮固定题集 A/B；
7. 与当前基线的成本、延迟和 fallback 对比。

## 9. Linear 模式改善方案

### 9.1 目标流程

```text
用户问题
  ↓
确定性短路与请求策略
  ↓
Common Stage-1：Contextualize / Resolve
  ↓
immutable UnderstandingResult
  ↓
Helper：意图判断 / Query Planner
  ↓
Helper：查询改写 / query variants
  ↓
确定性 RetrievalScope / Query Plan
  ↓
Hybrid / Graph / Rerank / EvidencePack
  ↓
Main：最终回答
  ↓
Grounding / Citation / Publish
```

### 9.2 轻量任务边界

Helper 可以负责：

- 将追问补全为可检索问题；
- 判断 `exact_parameter`、`conceptual_overview`、`troubleshooting` 等检索意图；
- 生成有限数量的 query variants；
- 图谱 canonical query 的表层改写；
- 历史摘要压缩。

Helper 不得负责：

- 最终事实回答；
- 改变用户主体身份；
- 越过 RetrievalScope / IdentityScope；
- 将没有证据支持的关系写入 EvidencePool；
- 决定是否允许通用知识输出。

### 9.3 Linear 复杂任务升级

复杂任务升级到 Main 只发生在规划/改写阶段，且仍然回到固定 Linear 检索流水线：

```text
Helper 失败或确定性复杂条件命中
  ↓
Main 生成一次结构化 Query Plan
  ↓
确定性检索
  ↓
Main 最终回答
```

Linear 升级不改成 Agent，也不允许 Main 直接绕过 Scope 调用任意工具。

### 9.4 Common Stage-1 与 Linear 的调用顺序

Linear 不应在原始追问尚未还原前判断意图：

```text
用户问题 + History
  ↓
Contextualize / Resolve
  ↓
resolved_question + SemanticTaskContext
  ↓
Intent / Query Planner
  ↓
Query variants
  ↓
Retrieval
```

例如“那前者呢？”必须先恢复为带有主体和任务的 `resolved_question`，再判断是参数查询、比较、故障排查还是概念说明。

Common Stage-1 的结果由 request 级上下文持有，Linear 各下游只读复用，不重新调用 Contextualizer。用户完成澄清或明确发生 topic shift 后，才创建新的 UnderstandingResult。

### 9.5 迁移期间的兼容策略

在角色切换初期，保留原函数接口，改变 `chat_role` 的 role 参数；不要同时重写 planner、contextualizer 和 retrieval 数据结构。

每个改动必须有一条路由断言：

```text
调用 stage = linear_query_contextualization
实际 role = helper_llm
```

避免出现“属性名写着 helper，但调用实际仍是 Main”的假一致。

## 10. 交互体验与流式协议

### 10.1 用户不感知内部阶段拆分

用户看到的是：

```text
正在分析问题
→ 正在检索相关资料
→ 正在补充缺失信息（如有）
→ 正在组织回答
→ 回答与引用
```

用户不需要看到：

- Controller 的原始 Thought；
- 内部 `finalize_answer` JSON；
- Helper/Main 的角色名称；
- 未采用的工具参数候选。

### 10.2 推荐事件序列

保持现有 SSE 兼容，同时补充结构化事件：

```text
agent_started
  ↓
agent_status / tool_start / tool_end
  ↓
clarify_requested（如需用户补充）
  或
finalization_requested
  ↓
finalization_rejected（证据不足，继续 Agent）
  或
evidence_snapshot_created
  ↓
answer_generation_started
  ↓
token / answer_delta
  ↓
grounding_checked
  ↓
final_answer
```

### 10.3 澄清行为

`clarify` 仍然是暂停动作，不得误处理为 `finalize`：

- 前端显示澄清卡片；
- 本轮不生成知识回答；
- 用户补充后恢复同一会话状态；
- 保留已经合法收集的 EvidencePool，但重新评估 AnswerContract；
- 不把澄清前的未冻结候选直接作为最终证据。

### 10.4 取消与超时

用户取消请求时：

- 停止后续工具调用和回答生成；
- Trace 记录 `cancelled_by_user`；
- 不发布半成品 Candidate；
- 不把取消视为证据充分或回答成功。

Provider 超时时：

- Helper 超时：按 Linear 升级/确定性 fallback；
- Main Controller 超时：按 Agent 降级策略停止，不静默用 Helper 接管；
- Main Answer 超时：沿用现有 fallback；
- 所有降级都写入模型角色和阶段信息。

| `rag_knowledge/services/query_clarification.py` | Linear 预检切换 Helper；Agent 主动澄清不依赖该路径替代 Controller |
| `rag_knowledge/services/graph_query_rewrite.py` | 改写路径切换 Helper；保持 Scope/实体约束 |
| `rag_knowledge/services/history_compressor.py` | 压缩调用切换 Helper；保留非阻塞和 cache 语义 |
| `config*.ini` | 增加最小阶段路由配置或明确默认路由；不改 Embedding |
| `tests/` | 增加角色、终止动作、冻结证据、流式事件和回归测试 |

### 12.2 建议新增的最小抽象

只新增必要的职责边界；其中 request 级 Understanding 可以复用现有请求上下文，不要求为了命名强行新增类：

```text
ModelRoutePolicy
  负责：根据 mode/stage 返回逻辑模型角色

Request Understanding Coordinator / request context
  负责：一次性生成并共享 immutable UnderstandingResult

FinalizationHandler
  负责：验证 finalize、冻结证据、调用 Answer Generator、接 Grounding
```

不要为每个 Helper 调用增加一个新的包装类，也不要把所有既有服务重构成通用 Agent。`retrieve_kb` 内部 mode-aware 权限可以通过现有参数和运行时上下文实现，不要求拆出第二套检索系统。

### 12.3 不应做的改法

- 不要把 `finalize_answer` 注册为普通检索 Tool 后再回传答案给 Controller；
- 不要把 Agent Controller 改成 Helper 以节省一次调用；
- 不要将所有 `role="llm"` 全局替换成 `helper_llm`；必须按阶段审核；
- 不要由模型决定 `allow_general_knowledge` 或 Evidence 合法性；
- 不要让 Answer Generator 继续拥有 Tool schema；
- 不要用一次额外的 Helper rewrite 覆盖 Agent Controller 明确给出的实体和范围；
- 不要在没有固定题集和 Trace 证据的情况下切换生产模型名称；
- 不要为本次 LLM 路由改造手动清空或重建正式 `chroma_db`。

- 能检测“Agent 用 Helper”“Linear 改写用 Main”等漂移；
- 原有测试全部通过。

### Phase 1：模型角色纠偏（P0）

目标：先完成最小模型切换。

交付：

- Agent Controller 切换到 Main；
- Linear Planner/Contextualizer 切换到 Helper；
- 消除入口与分支内部的重复 Contextualize / Resolve 调用；
- 明确 Linear 与 Agent 的 Planner 权限差异；
- History Compressor、Graph Query Rewrite 按表切换；
- Main Answer 保持不变；
- Helper 不作为 Agent Controller 的隐式 fallback。

验收：

- Agent Controller 100% 记录 `role=llm`；
- Agent Answer 100% 记录 `role=llm`；
- Linear 轻量预处理默认记录 `role=helper_llm`；
- 失败升级有明确 Trace。

### Phase 2：`finalize_answer` 与两阶段回答（P0）

目标：把 `finish` 升级为真正的终止回答控制语义。

交付：

- 增加 `finalize` 规范动作和旧 `finish` 兼容解析；
- 实现 `FinalizationHandler`；
- Finalization Gate 拒绝不足证据并反馈缺口；
- 证据通过后创建 immutable `EvidenceSnapshot`；
- Answer Generator 使用新上下文；
- Answer 阶段不携带工具定义和原始轨迹；
- Answer 结果不回 Controller 二次总结；
- Deterministic Grounding FAIL 不得被 Semantic Verifier 覆盖。

验收：

- 主链顺序为 `Main Controller → finalize → Main Answer`；
- `finalize` 被拒绝时 Agent 能继续检索；
- Grounding 失败不重新唤醒 Controller；
- 证据冻结后不会被后续工具修改；
- 回答引用仍能映射到合法 Evidence。

### Phase 3：Evidence Gate 与定向补检闭环（P0/P1）

目标：让 Agent 不是“有证据就回答”，而是“必要事实覆盖后回答”。

交付：

- 接入 AnswerContract / RequiredFacts；
- 生成 `missing_fact` 和 `FollowUpTarget`；
- Controller 使用缺口执行定向补检；
- 预算耗尽时保留不足状态并进入受限回答；
- 与现有 Grounding Firewall 分责。

验收：

- 对比类、多实体、关系类问题能够识别缺口；
- 不再无意义重复原 query；
- 不因 budget exhaustion 伪造 `SUFFICIENT`；
- missing evidence Trace 可审计。

### Phase 4：Linear 复杂任务升级（P1）

目标：低风险任务用 Helper，复杂任务不牺牲质量。

交付：

- Helper 失败/复杂确定性条件触发 Main 规划升级；
- 复杂任务仍走 Linear 固定检索，不升级为 Agent；
- 建立 Helper/Main A/B 题集。

验收：

- 简单查询没有不必要 Main 规划调用；
- 多实体关系、跨主题、多步查询的质量不低于当前基线；
- 升级原因可从 Trace 解释。

### Phase 5：交互与发布收口（P1）

目标：将内部阶段变化映射成稳定用户体验。

交付：

- `finalization_requested`、`evidence_snapshot_created`、`answer_generation_started` 等事件；
- 澄清暂停/恢复；
- 取消、超时、fallback 状态；
- 不展示原始 Thought，展示可读状态摘要。

验收：

- 前端不需要感知模型角色即可完成问答；
- Agent 多轮工具进度仍可见；
- 澄清后能恢复同一会话；
- 不出现半成品回答或重复最终回答。

### Phase 6：删除兼容语义（P2）

在 Phase 2–5 稳定并完成全量验收后：

- 删除 `finish` 的长期兼容路径；
- 删除散落的硬编码模型 role；
- 删除临时 feature flag；
- 将当前 PRD 的已实现部分更新为阶段完成记录；
- 不保留双轨长期实现。

## 15. 质量、成本与延迟评估

### 15.1 调用次数预期

本改造不应无条件增加回答阶段调用次数：当前 Agent 外层已经存在最终回答调用；改造重点是把它从“Loop 结束后的隐式步骤”变为“finalize 后的显式步骤”。

允许增加的调用仅包括：

- 证据不足时的定向补检 Controller 轮次；
- Grounding 失败时的一次 Main retry；
- Linear 复杂任务的 Main 规划升级；
- 条件式 Helper semantic verifier。

禁止：

```text
Main Controller 生成答案
→ Main Answer 再总结一次
→ Helper 再改写一次
```

### 15.2 质量指标

至少记录：

- AnswerContract required fact 覆盖率；
- `finalization_rejected` 比例；
- 定向补检成功率；
- Grounding PASS 比例；
- Grounded Retry 比例；
- Deterministic Fallback 比例；
- 引用完整性；
- 多轮指代正确率；
- Agent 工具循环率；
- Helper→Main 升级率。

### 15.3 延迟与资源指标

至少记录分阶段耗时：

```text
public_gate_ms
linear_preprocess_ms
agent_controller_ms
tool_execution_ms
finalization_gate_ms
answer_generation_ms
grounding_ms
retry_ms
```

本地 Ollama 环境还需记录：

- Main 模型加载时间；

- OOM / VRAM Guard 触发次数；

不要为了降低一次 Agent Controller 的延迟把它换成 Helper；应综合比较工具轮次减少、最终正确率和总耗时。

## 16. 风险与处理

| 风险 | 原因 | 处理 |
|:---|:---|:---|
| Main Controller 调用更慢 | Main 模型更大或远端 provider | 保留现有 step/retrieve budget；按阶段测量；必要时调整工具循环，不降级为 Helper |
| Main 工具 JSON 不稳定 | 模型/provider 工具调用能力差异 | 增加 schema、解析和重试测试；provider 不满足时阻断上线 |
| Helper 改写丢失实体 | 轻量模型上下文能力有限 | Query 改写必须经过 IdentityScope/Scope 校验；冲突升级 Main |
| Finalization 过早 | Controller 判断错误 | Evidence Gate 硬拒绝；输出 missing fact；不依赖模型自报充分 |
| Finalization 反复被拒绝 | AnswerContract 过细或检索能力不足 | Contract 首期保持粗粒度；引入预算和结构化缺口；避免无限循环 |
| 回答阶段丢失会话灵活性 | 过度清理上下文 | 保留结构化 ConversationContext、历史摘要和最近轮次，不保留原始轨迹 |
| Grounding 失败形成循环 | 重新唤醒 Controller | Answer Pipeline 内完成一次 retry/fallback；禁止回 Controller |
| 角色配置与实际调用不一致 | 散落硬编码 `chat_role` | 集中 `ModelRoutePolicy`，每次调用 Trace 记录实际角色 |
| 配置切换影响正式环境 | provider/model 不兼容 | 本地/隔离测试、A/B 和回滚配置先行；不直接操作正式库 |
| 第三类逻辑角色被误认为第三个模型 | `semantic_verifier`、compression 等命名 | 文档区分逻辑角色与 endpoint；未配置时复用已有 Helper |

### 18.1 本次实施记录（2026-08-21）

本 PRD 的核心实现已落地，关键行为如下：

- `Agent Controller` 和 `Answer Generator` 均经 `ModelRoutePolicy` 使用 Main 角色；Linear/Common Stage-1 默认使用 Helper，复杂规划和 Helper 失败按固定规则升级 Main。
- `finalize_answer` 仅作为 Controller 协议动作，Runtime 统一规范为 `action="finalize"`；Evidence Sufficiency Gate 拒绝不足证据，足够后创建 immutable `EvidenceSnapshot` 和 `AnswerGenerationContext`。
- V2 下 Runtime 自己产生的 heuristic/harness `finish` 也会先归一化为 `finalize`，不能绕过 Gate；旧的外部程序化 `finish` 仅在灰度开关关闭或兼容调用路径中保留。
- Answer Generator 使用无工具、无原始 Thought/Action/Observation 的独立 prompt；Grounding retry/fallback 留在回答流水线内，不重新唤醒 Controller。
- Grounding 已拆成 deterministic 检查、deterministic FAIL 的一次 Main retry、再次 deterministic 检查和条件式 semantic veto；semantic reject 直接 fallback/受限发布，不再触发 Main retry。
- Agent `retrieve_kb` 在 agent mode 下保留 Controller 的 query/entity/intent/scope，Planner 只做确定性增强；Common Understanding 在同一 request 内复用，不重复执行。
- `UnderstandingResult` 的嵌套 list/dict 已深冻结；EvidencePool、EvidenceSnapshot 与 AnswerGenerationContext 均记录 `evidence_version`，非流式 Agent request 也按 request-level mode 记录 `agent_answer` 路由。
- Finalization Gate 已先识别 `answer_type`：Direct Chat 返回 `evidence_not_required` 并只执行一次终止，不消耗循环预算、不创建空 Snapshot；知识型请求仍严格执行 Evidence Gate。SSE 事件顺序固定为 `finalization_requested → evidence_snapshot_created`（仅知识型成功终止产生 Snapshot 事件）。
- Agent V2 对相同且已成功的 `retrieve_kb` 请求不再执行第二次相同检索，而是优先将当前 EvidencePool 交给 Finalization Gate；`conceptual_overview` 仅通过确定性检索变体补充“概述/功能/架构”词，不重新调用 Helper 改写。
- 前端澄清回调完成后会清理旧歧义卡片；SSE 非正常 EOF 也会幂等收口 loading 状态；知识库问答默认关闭通用知识兜底，用户可在高级参数中显式开启。
- Trace 已记录阶段、逻辑角色、provider/model、调用耗时、终止原因、finalization 次数、snapshot/verdict；SSE 与前端时间线已接入 finalization、snapshot、answer-generation 事件。
- 保留旧 `finish` 作为短期协议兼容层，以便已有程序化调用平滑过渡；新 Controller 路径统一输出 `finalize`。临时灰度 flag 和兼容层的删除属于发布稳定后的清理动作，不能在本地回归前提前删除。
