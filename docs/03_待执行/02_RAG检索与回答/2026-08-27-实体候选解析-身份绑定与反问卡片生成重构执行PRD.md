> **重构“实体身份解析 + 反问卡片候选生成”链路。**

不顺手重构 Evidence、Grounding、回答生成等其他链路，避免再次把一个 PRD 做得过宽。

# 实体候选解析、身份绑定与反问卡片生成重构执行 PRD

**建议文件名：**

`2026-08-27-实体候选解析-身份绑定与反问卡片生成重构执行PRD.md`

**状态：** 待实施
**优先级：** P0
**影响范围：** Stage-1 理解、实体身份解析、Main Controller、Clarify 工具、反问卡片、Clarification Callback
**不涉及：** Evidence Admission、Grounding Reviewer、Answer Generator、Chunk 证据排序算法

---

# 1. 背景

当前系统已经具备：

```text
用户问题
→ Stage-1 理解
→ Main Controller
→ clarify / retrieve / graph / finalize
```

以及：

```text
identity_status
entity_binding_required
confirmed_entity
```

等身份状态。

但当前反问卡片的**候选生成逻辑存在结构性问题**。

以：

```text
pipeline
```

为例，当前系统候选并非真正通过通用实体解析得到，而主要经过：

```text
读取 product_relation_backbone.json
→ canonical / alias 字符串匹配
→ pipeline / 管线专属 family expansion
→ 扫描所有 Product / Tool / Service / Module
→ different_from 扩充
→ 转成反问选项
```

并且 Main Controller 还可以通过：

```text
model_suggested_options
```

额外创建实体选项。

因此曾实际出现：

```text
PipelineManager
PipelineCLI
PipelineServer
StampPipeline
```

等知识库中不存在、但被展示为可选实体的候选。

与此同时，当前 Backbone 候选生成也存在明显泛化问题。

实际行为包括：

```text
pipeline
→ 11 个 Backbone 候选

webgl
→ 3 个

webrtc
→ 5 个

stamp
→ 0 个

server
→ 0 个

builder
→ 0 个
```

而一个已经非常明确的：

```text
StampServer
```

反而可能因为 CamelCase family expansion：

```text
StampServer
→ Stamp
→ 扫描整个 Stamp family
```

扩展成十余个候选。

因此当前问题不是：

> `PipelineManager` 一个错误选项。

而是：

> **实体候选召回、实体相关性排序、身份判断、反问展示四种职责没有真正分层。**

---

# 2. 本 PRD 的核心问题定义

反问卡片本质上不应该负责：

> “猜用户可能说的是哪些东西。”

反问卡片只是**实体身份解析失败后的用户交互界面**。

真正的问题应该拆成：

```text
用户表达
↓
实体候选召回
↓
候选排序
↓
身份置信判断
↓
是否需要用户澄清
↓
反问卡片
```

因此本 PRD 的核心目标是：

> **建立统一的实体候选解析链路，使反问卡片只展示系统中真实存在、经过验证并与当前表达相关的实体候选。**

---

# 3. 第一性原则

## 3.1 实体存在性与模型推测必须分离

模型可以判断：

```text
现在是否存在歧义
问题应该怎么问
哪些已知候选更值得优先关注
```

但模型不能决定：

```text
知识库里存在哪些实体
```

因此：

```text
LLM output
不能扩大
Verified Entity Universe
```

即：

> **大模型不能创造实体身份事实。**

---

## 3.2 身份先于证据

整个链路必须保持：

```text
Identity
→ Candidate Scope
→ Evidence
→ Answer
```

不能：

```text
先检索 Chunk
→ 根据 Chunk 猜实体
→ 再决定用户问的是谁
```

证据不能反过来决定身份。

---

## 3.3 实体存在不等于当前相关

必须明确：

```text
实体真实存在
≠
当前问题相关
≠
应该成为候选
≠
应该展示给用户
```

因此必须把：

```text
候选召回
```

与：

```text
候选展示
```

分离。

---

## 3.4 图谱关系是相关性信号，不是候选授权

例如：

```text
StampWebGL
different_from
PipelineWebGL
```

表达的是：

> 二者不是同一个实体。

不能解释成：

> PipelineWebGL 是候选，所以 StampWebGL 也自动成为候选。

因此：

```text
Graph Relation
→ Ranking / Disambiguation Signal
```

而不是：

```text
Graph Relation
→ Candidate Admission
```

---

## 3.5 Main Controller 仍然是唯一控制器

本 PRD 不新增第二个决策模型。

实体候选解析器负责提供状态：

```text
有哪些候选
各候选可信度如何
身份是否已经可以确定
```

Main Controller 仍然负责决定：

```text
clarify
retrieve
graph
finalize
```

也就是说：

```text
实体解析器 = 感知/判断事实
Main Controller = 行动决策
```

---

# 4. 目标架构

改造后链路：

```text
用户问题
   ↓

   ↓
判断是否需要实体身份绑定
   ↓
EntityCandidateResolver
   ↓
候选召回
   ↓
候选融合与排序
   ↓
IdentityResolution
   ↓
Main Controller
   ↓
┌───────────────────────────────┐

└───────────────────────────────┘
   ↓

   ↓

   ↓

   ↓

   ↓
正常 Evidence Retrieval
```

# 5. 新增核心领域对象

## 5.1 `EntityCandidate`

建议定义统一候选对象：

```python
@dataclass(frozen=True)
class EntityCandidate:
    entity_id: str
    canonical_name: str
    display_name: str
    entity_type: str

    matched_surface: str | None
    match_sources: tuple[str, ...]

    lexical_score: float
    semantic_score: float | None
    context_score: float
    graph_score: float

    final_score: float
```

注意：

这里的 `score` 必须开始成为真实含义，而不是当前 `CandidateDTO.score=None` 的占位字段。

---

# 6. 身份解析结果

新增统一：

```python
@dataclass(frozen=True)
class IdentityResolution:
    status: str
    surface: str | None
    confirmed_entity_id: str | None
    confirmed_entity_name: str | None
    candidates: tuple[EntityCandidate, ...]
    confidence: float | None
    margin: float | None
    reason: str
```

`status` 只允许四种：

```text
confirmed
ambiguous
unresolved
not_required
```

对应中文语义：

```text
已确认
有歧义
未解析
无需绑定
```

---

# 7. EntityCandidateResolver 职责

新增统一模块，例如：

```text
rag_knowledge/services/entity_candidate_resolver.py
```

其职责只能是：

```text
输入：
用户 surface
对话上下文
知识库约束

输出：
排序后的真实实体候选
```

不得执行：

```text
clarify
retrieve_kb
graph_explore
finalize
```

不得直接控制 Agent。

---

# 8. 第一阶段：候选实体数据源

候选实体来源必须全部是**系统可验证实体**。

当前可以继续利用：

```text
product_relation_backbone.json
domain_catalog
```

现阶段没有必要立刻依赖完整 Graph DB。

首先把现有 Backbone 变成一个真正的：

> **实体注册表 / Entity Registry**

至少包含：

```text
entity_id
canonical_name
aliases
entity_type
description
doc_category
parent / ownership
```

当前没有稳定 `entity_id` 时，可以第一阶段使用 deterministic ID，例如由 canonical identity 产生稳定 ID。

但长期不应依赖展示名称作为唯一身份键。

---

# 9. 候选召回设计

候选召回应以：

> **高召回**

为目标。

但禁止使用当前这种：

```text
命中一个实体
→ 自动扩展整个 CamelCase prefix family
```

的无条件逻辑。

至少支持以下几路通用召回。

## 9.1 完整名称匹配

例如：

```text
StampServer
```

命中：

```text
StampServer
```

应赋予最高优先级。

并且如果：

```text
exact canonical match
+
没有明确主体切换歧义
```

不应该继续扩展整个：

```text
Stamp*
```

家族。

---

## 9.2 别名匹配

例如：

```text
Pipeline WebGL
管线 WebGL
```

统一解析到：

```text
PipelineWebGL
```

Alias 必须来自 Entity Registry。

不能由模型生成。

---

# 10. 词法候选召回

当前：

```text
server
builder
stamp
```

基本无法得到候选。

应增加通用的实体名词法召回。

例如：

```text
server
```

应该可以召回：

```text
StampServer
StampNodeServer
...
```

但只是进入内部 CandidateSet。

并不意味着全部展示。

建议使用轻量词法评分：

```text
完整匹配
前缀/后缀匹配
token 匹配
规范化字符串匹配
编辑距离 / 拼写相似
```

而不是继续建立：

```text
SERVER_FAMILY_TOKENS
BUILDER_FAMILY_TOKENS
STAMP_FAMILY_TOKENS
```

---

# 11. 语义召回

如果当前依赖允许，可以增加实体级向量召回。

索引内容可以是：

```text
canonical_name
aliases
entity_type
description
parent product
```

例如：

```text
服务器
```

可语义关联：

```text
StampServer
StampNodeServer
```

但语义召回只是一个来源。

不允许：

```text
向量相似
→ 自动认为实体就是目标
```

仍需后续排序。

如果当前实现成本较高，可以将其列为 P1，不阻塞 P0 结构修复。

---

# 12. 候选融合

各召回来源产生实体 ID 后统一合并：

```text
Exact
Alias
Lexical
Semantic
```

例如：

```text
E100 StampServer
来源：
canonical_exact
lexical
semantic
```

只保留一个候选对象。

禁止通过 label 字符串简单去重。

应按：

```text
entity_id
```

去重。

---

# 13. Graph 的正确作用

Graph 只参与：

```text
候选排序
上下文消歧
```

不直接创建实体候选。

例如对话当前已绑定：

```text
PipelineWebGL
```

用户：

```text
那三维管线呢？
```

候选召回可能得到：

```text
三维管线管理
PipelineWebGL
PipelineWebRTC
```

图谱存在：

```text
三维管线管理
belongs_to
PipelineWebGL
```

因此：

```text
三维管线管理 graph_score ↑
```

这是正确使用。

---

## 13.1 `different_from` 修改

当前：

```text
A 命中
→ A different_from B
→ B 自动加入
```

必须停止。

改成：

```text
如果 A、B 都已通过候选召回进入 CandidateSet
→ different_from 用来防止 canonical collapse
→ 必要时提高消歧价值
```

不能凭 `different_from` 创建 B。

---

# 14. 候选排序

新增统一排序。

概念公式可以是：

```text
最终分数 =
词法匹配
+ 别名匹配
+ 语义相关
+ 对话上下文
+ 图谱上下文
+ 实体类型适配
```

第一阶段不要求构建复杂机器学习模型。

重点是：

> **必须存在排序，而不是所有候选平级。**

---

# 15. 精确实体必须优先

例如：

```text
StampServer
```

如果完整 canonical 匹配：

```text
StampServer
```

则正常情况下：

```text
StampServer score ≫ 其他实体
```

不能再次因为：

```text
Stamp
```

前缀而把：

```text
StampTools
StampWebGL
StampWebRTC
StampManager
...
```

全部扩出来。

因此删除当前这种隐含规则：

```text
CamelCase 首词
→ family token
→ 全家族扩展
```

至少不能在 exact match 已成立后触发。

---

# 16. 删除 Pipeline 专属候选扩展

以下逻辑应退出实体候选主链：

```python
WIDE_SURFACE_TERMS = (
    "pipeline",
    "Pipeline",
    ...
)

_PIPELINE_FAMILY_TOKENS = {
    "pipeline",
    "管线",
}
```

注意：

不是简单把这些常量删掉以后让 `pipeline` 失效。

必须先用新的通用候选召回覆盖：

```text
pipeline
→ PipelineWebGL
→ PipelineBuilder
→ PipelineWebRTC
→ ...
```

之后再删除特判。

验收标准是：

> 不依赖 `pipeline` 特判仍能正确得到合理的 Pipeline 候选。

---

# 17. 身份状态判断

候选排序以后，不能再使用：

```text
候选 >= 2
→ 必须反问
```

改成根据：

```text
Top1 置信度
Top1 与 Top2 差值
```

判断。

---

## 17.1 已确认

例如：

```text
StampServer       0.98
StampNodeServer   0.28
```

则：

```text
status = confirmed
```

直接绑定。

---

## 17.2 有歧义

例如：

```text
PipelineWebGL      0.84
PipelineBuilder    0.82
PipelineWebRTC     0.78
```

则：

```text
status = ambiguous
```

Main 可以决定 clarify。

---

## 17.3 未解析

例如：

```text
top1 = 0.28
top2 = 0.25
```

说明系统根本没有可靠候选。

不能展示一堆低质量实体。

应该：

```text
status = unresolved
```

如果实体绑定是必须的：

> 请求用户输入更完整的名称。

---

# 18. 阈值原则

第一阶段允许使用可配置阈值。

例如概念上：

```text
CONFIRMED_MIN_SCORE
CONFIRMED_MIN_MARGIN
AMBIGUOUS_MIN_SCORE
```

但必须满足：

> 阈值是通用身份判定规则，不是针对 Pipeline、StampServer 等实体的特殊阈值。

禁止：

```python
if query == "pipeline":
    threshold = ...
```

---

# 19. 与 Stage-1 Understanding 的关系

Stage-1 负责：

```text
提取 surface
理解当前意图
判断是否需要具体实体身份
理解指代
结合历史实体
```

例如：

```text
什么是三维GIS？
```

Stage-1 可判断：

```text
entity_binding_required = false
```

则无需运行强制身份绑定。

---

用户：

```text
Pipeline怎么部署？
```

则：

```text
entity_binding_required = true
surface = pipeline
```

进入 EntityCandidateResolver。

# 20. 与 Main Controller 的融合

Main Controller 输入增加完整：

```text
IdentityResolution
```

例如：

```text
实体身份状态：有歧义

候选：
PipelineWebGL / 0.84
PipelineBuilder / 0.82
PipelineWebRTC / 0.78
```

Main 决定：

```text
clarify
```

但是 clarify 工具不得再接受：

```text
options
model_suggested_options
```

作为实体创建来源。

# 21. Clarify 工具协议重构

当前类似：

```json
{
  "question": "...",
  "model_suggested_options": [...]
}
```

应改成：

```json
{
  "question": "您说的 pipeline 具体指哪个实体？",
  "reason": "entity_identity_ambiguous"
}
```

选项不再由模型提交。

执行框架自动读取：

```text
当前 IdentityResolution.candidates
```

生成卡片。

---

# 22. Main 不允许扩大 CandidateSet

即使 Main 输出类似：

```text
我认为可能还有 PipelineManager
```

也不能变成系统候选。

代码层必须满足：

```text
Clarification Options
⊆
Verified CandidateSet
```

这是硬性不变量。

---

# 23. 反问卡片展示逻辑

内部召回可以：

```text
10
20
甚至更多
```

但前端展示必须独立。

默认建议：

```text
Top 3~5
+
以上都不是
```

不再执行：

```text
找到几个就全部展示几个
```

---

# 24. 删除“无数量上限”的旧设计

当前测试：

```text
test_clarify_no_max_options_cap
```

所体现的：

> 所有 family candidate 全部展示。

应废弃。

新原则：

```text
内部候选高召回
前端候选低认知负担
```

两者职责不同。

---

# 25. “以上都不是”

系统固定只保留一个：

```text
以上都不是
```

它是：

```text
UI Action
```

不是实体。

因此不进入：

```text
CandidateSet
```

也不参与：

```text
candidate count
score
identity confidence
```

Main 不允许生成：

```text
其他
其他（请说明）
以上都不是
```

等重复选项。

---

# 26. Clarification Candidate Snapshot

卡片创建时冻结当次候选：

```python
ClarificationCandidateSnapshot
```

至少包含：

```text
clarification_id
created_at
surface
candidate entity_ids
display order
identity resolution metadata
```

用户点击后：

```text
selected_entity_id
```

必须满足：

```text
selected_entity_id
∈
当前 clarification snapshot
```

不能重新跑一次候选解析后再凭 label 猜实体。

---

# 27. Callback 身份绑定

当前后续链路应该收敛成：

```text
用户点击选项
↓
返回 entity_id
↓
服务端校验 entity_id 属于当前候选快照
↓
confirmed_entity_id = entity_id
↓
confirmed_entity_name = canonical_name
↓
继续 Agent
```

禁止：

```text
用户点击 "PipelineWebGL"
↓
重新拿字符串 PipelineWebGL 做一次实体推断
```

---

# 28. 对话实体锁定

用户确认实体以后：

```text
confirmed_entity_id
```

成为后续身份来源。

例如：

```text
用户选择 PipelineWebGL
↓
下一句：
“它支持什么？”
↓
继续绑定 PipelineWebGL
```

不能因为：

```text
它
pipeline
这个产品
```

这些表述短，就再次触发全局候选澄清。

只有：

```text
明确主体切换
明确新实体
上下文证据显示当前 binding 已失效
```

才重新解析身份。

---

# 29. 当前 `QueryClarificationService` 的职责调整

当前它同时承担：

```text
候选发现
候选扩展
模型歧义判断
选项合并
UI 数据生成
```

职责过多。

重构以后：

```text
EntityCandidateResolver
→ 候选发现 + 排序

IdentityResolver
→ 身份状态

QueryClarificationService / Presenter
→ 只负责把 ambiguous candidate snapshot
   转成反问卡片
```

如果现有类名保留，也必须内部职责明显收缩。

---

# 30. 旧逻辑清理

完成迁移后应删除或退出主链：

```text
_PIPELINE_FAMILY_TOKENS
Pipeline 专属 family expansion
无条件 CamelCase family expansion
different_from 自动追加候选
model_suggested_options 创建实体
options 创建未知实体
unresolved model candidate
所有候选直接展示
```

禁止为了兼容旧测试长期双轨运行：

```text
legacy_candidate_discovery
new_candidate_discovery
```

正式链路只能保留一个权威实现。

# 31. Entity Type 约束

当前：

```python
_ALLOWED_ENTITY_TYPES = {
    "Product",
    "Tool",
    "Service",
    "Module",
}
```

短期可以继续使用。

但是必须明确：

# 42. DoD

本 PRD 只有同时满足以下条件才能标记完成：

1. Main 不再拥有创建未知实体候选的能力。
2. `PipelineManager` 等未注册实体无法进入卡片。
3. `pipeline` 不依赖 Pipeline 专属 family 特判也能召回合理真实候选。
4. `server / builder / stamp` 等非 Pipeline 模糊词具备通用候选召回能力。
5. `StampServer / PipelineWebGL` 等明确实体不再扩成整个 family。
6. `different_from` 不再直接扩大候选集。
7. 候选具有实际排序分数。
8. 系统可以输出 `confirmed / ambiguous / unresolved / not_required`。
9. Main 根据身份状态决定是否 clarify。
10. 前端只展示 Top-K verified candidates。
11. “以上都不是”只有一个，并且不属于实体 CandidateSet。
12. 用户选择通过 `entity_id` 绑定。
13. 反问候选创建时存在冻结 Snapshot。
14. 已绑定实体不会因为短指代重新反问。
15. Trace 可以解释每个候选为什么出现。
16. 新 Gold Set 和单元测试全部通过。
17. Agent 集成链路通过。
18. 至少完成 `pipeline / server / StampServer / PipelineWebGL` 真实模型验证。
19. 不保留 legacy/new 双轨候选实现。
20. `git diff` 中不存在针对单一实体名的补丁式判断。

# 45. 本 PRD 最核心的一句话

整个重构可以压缩为：

> **反问卡片不负责发现世界里有哪些实体；实体系统先完成真实候选召回和排序，只有身份确实无法可靠确定时，Main 才调用反问，并且反问只能展示已经验证过的候选。**

这份 PRD 的重点不是“修好 `pipeline`”，而是让 `pipeline`、`server`、`builder`、`stamp`、中文模糊词以及以后出现的新实体表达，都走同一个可泛化的身份解析机制。
