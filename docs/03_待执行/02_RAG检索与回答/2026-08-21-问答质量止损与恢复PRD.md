## 1. 背景与问题

2026-08-21 的真实 QA Trace 显示，问答主链已发生可观测退化：当天 42 条请求中，29 条进入 Agent 模式，29 条均以 `deterministic_fallback` 发布。失败答案通常是原始 Chunk 摘录，而不是面向问题的可读回答。

这不是模型能力问题。本 PRD 不更换、降级或回退 Main / Helper 模型；问题在于新控制规则叠加后，把合理的生成答案过度判定为不合格，并允许不充分的检索结果进入兜底发布。

已确认的事故模式：

1. UI 默认将 `allow_general_knowledge` 发送为 `false`，覆盖配置值，使所有普通问答进入严格发布分支。
2. 用户请求 `mode=agent` 时会绕过 `agent_orchestration.enabled=false`；`terminal_finalization_v2=true` 因而实际作用于生产请求。
3. Agent 对未授权或拼写不明实体反复调用工具；最终无范围检索召回低信息 Chunk。
4. Grounding 对“现有证据不足”“不同于”等解释性语句产生 false reject，候选答案重试后仍被替换成摘录。
5. 流式心跳任务与 QA Trace 的 `ContextVar` 不在同一上下文提交，导致请求在最终 `done` 前抛错；前端会把它视为流式失败并再次发起非流式请求。
6. `pipelien` 这类专有实体疑似拼写错误在 Stage-1 被判为 `unbound` 后仍返回 `mode=retrieve`，没有进入澄清前置环节；后续 Agent 只能围绕错误词做无效检索和授权请求。

## 2. 产品目标

恢复“先理解问题、再检索、基于证据作答”的主体验，同时保留来源、权限、事实约束和可追溯 Trace。

成功不是降低事实要求，而是让规则只拦截真正无依据的事实，不把正常的归纳、范围声明或证据不足说明误杀。

## 3. 非目标

- 不调整 Main / Helper / Embedding 模型及其 provider。
- 不重建 Chroma、重分块或修改正式知识库数据。
- 不删除 IdentityScope、ExplorationGrant、引用校验或 AnswerFinalizer。
- 不引入新的 Agent、模型角色或完整 Claim Graph。
- 不把“允许通用知识”作为规避知识库引用要求的默认手段。

## 4. 根因与设计裁决

### 4.1 默认策略必须与配置一致

`allow_general_knowledge` 是请求级覆盖项，而不是前端的硬编码默认值。

裁决：前端未被用户显式选择时不得发送 `false`，应传 `undefined`，由后端配置决定。用户显式关闭后，仍可进入 strict KB，但必须知道这是受限回答模式。

### 4.2 Agent 是灰度能力，不是配置关闭后仍可隐式启用的默认路径

裁决：后端总开关关闭时，普通聊天入口必须以 Linear 运行；只有明确的内部试验入口可携带 `mode=agent` 覆盖，并在 Trace 标识 `agent_override=true`。前端不保存或自动恢复已失效的 Agent 模式。

### 4.3 澄清必须在检索前处理未知实体和疑似拼写

Stage-1 对单一专有词必须区分以下状态：

| 状态 | 示例 | 后续动作 |
| --- | --- | --- |
| 已精确解析 | `PipelineWebGL` | 进入带实体约束的检索 |
| 高置信别名 | 合法目录别名 | 归一化后检索 |
| 疑似拼写 | `pipelien` | 返回候选澄清，不得带该词作为 `target_entity` 调工具 |
| 完全未知 | 随机字符串 | 明确无匹配或请求补充上下文 |

候选生成可使用确定性编辑距离、已有 domain catalog 和检索候选标题，但“疑似”不是自动改写。系统必须将候选展示给用户确认；确认前不得触发 ExplorationGrant 或图谱关系检索。

### 4.4 Finalization Gate 只负责“是否继续检索”

Gate A 与 Gate B 分工如下：

```text
Gate A（回答前）: 当前证据是否足够继续检索，或以 PARTIAL 回答？
Gate B（发布前）: Candidate 是否包含证据不支持的知识事实？
```

Gate A 不得把预算耗尽、检索未命中或授权失败伪装成 `SUFFICIENT`；但也不得要求“概述”“区别”等问题必须命中固定关键词或两条以上特定类型 Chunk 才可回答。

### 4.5 Fallback 不是低质量检索的发布通道

只有同时满足以下条件时才允许摘录式 fallback：

```text
存在与问题主体直接相关的、可引用的有效证据
且候选答案确实无法通过 Gate B
```

空表格、低信息 Excel 行、无主体匹配的泛召回不得进入 fallback。此时应返回受控的“未找到可确认资料”或澄清请求，而非拼接四段原文。

### 4.6 流式完成必须可靠

一次用户请求只能产生一次最终回答。Trace 记录失败不得破坏已完成的生成，更不得触发前端隐式二次查询。

## 5. 目标流程

```text
请求
  ↓
配置默认值（用户未显式覆盖时）
  ↓
Linear 默认 / Agent 灰度
  ↓
Stage-1 理解与实体解析
  ├─ 拼写不明 → 澄清候选，等待用户确认
  ├─ 完全未知 → 请求补充上下文或返回无匹配
  └─ 已解析 → 受 Scope / Grant 约束的检索
  ↓
Evidence Quality Filter
  ↓
Gate A：继续检索 / PARTIAL / 可生成
  ↓
Candidate（带引用）
  ↓
Gate B：仅拦截不受支持的知识事实
  ↓
正常答案 / 受限部分答案 / no-knowledge
  ↓
先完成 SSE，再异步落 Trace
```

## 6. 实施范围与验收

### Phase 0：止损开关与真实样本基线

**实施**

- 将 `terminal_finalization_v2` 改为显式灰度开关，默认关闭；不改模型配置。
- 后端总开关关闭时拒绝普通入口的 Agent 覆盖，前端默认 Linear。
- 前端不再默认提交 `allow_general_knowledge=false`。
- 建立当天 Trace 的 10 个真实问题回归集，至少覆盖：实体概述、比较、端口配置、模糊拼写、无结果、多轮澄清。

**验收**

- 默认请求的 Trace 中 `effective_agent_orchestration_enabled=false`。
- 请求未显式设置通用知识策略时，`requested_allow_general_knowledge=null`。
- 基线集每条请求都记录最终模式、检索证据、模型调用、Gate A/B 原因。

### Phase 1：修复发布收口的 false reject

**实施**

- 将 Grounding 校验单位从“包含关系词的整句”改为“可发布的知识事实”。
- 对范围声明和不确定性说明建立白名单语义：例如“当前证据未覆盖”“无法确认”，它们不要求反向事实引用。
- 关系断言只在确有关系事实时校验主客体与关系；不得把排版、标题或解释语误判成关系事实。
- 保留生成后一次 grounded retry；retry 成功即发布，失败才进入 fallback。

**验收**

- `PipelineWebGL 和 PipelineBuilder 有什么区别？` 不因“区别/不同于”解释文本被误杀。
- `StampWebRTC UDP 外网部署需要配置哪些关键端口？` 能清晰区分已确认端口与未确认 UDP 要求，不被替换为原文堆叠。
- 真实回归集的 `deterministic_fallback` 比例不高于 20%，且每次 fallback 都有结构化失败原因。

### Phase 2：收敛 Agent 的失败恢复

**实施**

- 未授权 target 只记录一次失败；后续要么去掉 target 执行宽松检索，要么进入澄清，禁止同目标重复调用。
- 拼写不明、单词式问题由 Stage-1 先走实体候选或澄清，不得直接把未识别词写入 `target_entity`；Agent 不得承担该前置消歧职责。
- Gate A 输出结构化缺口；Runtime 只在检索有新证据时重试 finalization。
- `PARTIAL` 允许受限回答，不为追求 `SUFFICIENT` 消耗全部 Step 预算。

**验收**

- `pipelien` 不出现重复的 `exploration_not_authorized`。
- `pipelien` 必须在第一次检索前返回澄清候选（例如 `PipelineWebGL`、`PipelineBuilder`）；若无可靠候选，返回“未识别实体”而非检索。
- 无主体检索只保留主体/问题相关的有效 Chunk；低信息表格不进入答案或 fallback。
- 单个 Agent 请求最多一次“同一 target 被拒绝后”的重试。

### Phase 3：流式完成与 Trace 解耦

**实施**

- Trace 的 ContextVar 在创建它的 task/context 内 finish，或改为显式传递诊断快照；禁止跨 context reset token。
- SSE 已发送最终答案时，无论 Trace 写入成功与否都必须发送 `done`。
- 前端只在未收到任何最终答案且请求确实异常时才允许非流式降级；降级请求必须带 `retry_of_request_id`。

**验收**

- `logs/rag_error.log` 不再出现 `Token ... was created in a different Context`。
- 一次用户发送只产生一个 QA Trace 或一条带明确关联 ID 的重试 Trace。
- 连续 20 次流式请求均收到一次且仅一次 `done`。

### Phase 4：灰度恢复 Agent V2

**前置条件**

- Phase 0–3 的验收全部通过。
- Agent 真实回归集 fallback 比率、无效工具调用、平均时延均不劣于 Linear 基线。

**实施**

- 仅对带内部灰度标志的请求开启 `terminal_finalization_v2`。
- Trace 按 `linear`、`agent_v1`、`agent_v2` 分桶统计。
- 任何指标回退均能独立关闭 V2，不影响模型、检索和引用链路。

## 7. 指标

| 指标 | 当前观察 | Phase 4 门槛 |
| --- | ---: | ---: |
| Agent deterministic fallback rate | 29/29（100%） | ≤ 20% |
| 未授权工具重复调用 | 存在 | 0 |
| 流式跨 Context 异常 | 存在 | 0 |
| 低信息 Chunk 进入最终答案 | 存在 | 0 |
| 同问题重复请求 | 存在风险 | 0（除用户主动重试） |
| 每条最终答案的来源可追溯性 | 应保留 | 100% |

## 8. 测试与交付要求

- 测试先覆盖事故样本，再做抽象单测；不得只以 mock 数据证明 Gate 正确。
- 每个样本保存：输入、模式、检索证据、Agent steps、Grounding verdict、最终答案和 Trace ID。
- 不操作正式 `chroma_db`、`data/` 或关系数据库；正式评测在停止后端和评测进程后执行。
- 变更必须按 Phase 单独提交，允许独立回滚；禁止把配置、前端默认、Agent Runtime 与 Grounding 大改混在同一次上线。

## 9. Definition of Done

- [ ] 默认 Web 问答不再被前端硬编码成 strict KB。
- [ ] Agent 总开关可真实关闭普通入口的 Agent 路径。
- [ ] Gate A、Gate B、Fallback 各自有唯一职责与 Trace 字段。
- [ ] 事故样本不再输出无关原文或空表格摘录。
- [ ] 流式完成不受 Trace 写入异常影响。
- [ ] Agent V2 仅在灰度开关下运行。
- [ ] 达到指标后，才允许把 V2 设为默认路径。

## 10. 最终原则

问答质量不是通过增加更多拒绝规则得到的。正确顺序是：

```text
先保证请求走对模式、检索到对证据、正常回答能正常发布，
再用最小且可解释的规则阻止无依据事实。
```

任何无法降低真实 fallback、无效工具调用或流式异常的改动，都不得进入默认问答主链。
