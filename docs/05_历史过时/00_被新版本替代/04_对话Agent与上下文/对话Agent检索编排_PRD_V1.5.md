## 一、 架构总原则与第一性原理

### 1.1 核心架构定义
```text
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                            V1.5 终态两阶段架构 (Two-Stage Architecture)                   │
├──────────────────────────────────────────────────────────────────────────────────────────┤
│ Stage 1：Dialogue Gate (固定语义入口)                                                    │
│ 流程固定经过，决策由 LLM 驱动。每一个请求必经语义理解门禁，由 LLM 结合图谱事实空间判断。   │
│ ├─ 需要澄清 ──► 输出 Clarify Card 选项卡片，暂停请求等待用户选择                          │
│ └─ 主体明确 ──► 提取规范化问题与主体，放行进入 Stage 2                                    │
├──────────────────────────────────────────────────────────────────────────────────────────┤
│ Stage 2：Agent Execution Loop (自主执行循环)                                             │
│ 纯粹按需调用，动态自主收敛。LLM 自由规划 retrieve_kb / link_entities / reuse_evidence。   │
│ ├─ 证据充分 ──► LLM 自主决策 action="finish" ──► 单步直接生成回答（低延迟）              │
│ └─ 缺少特定事实 ──► LLM 自主生成精准 Query 发起补检 ──► 严禁系统套用机械正则篡改         │
├──────────────────────────────────────────────────────────────────────────────────────────┤
│ Safety Harness (系统级安全边界)                                                          │
│ 纯物理安全网：参数 Schema 校验、工具存在性校验、总步数熔断、异常循环检测。不干预合法业务。 │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 架构第一性原则（Core Principles）

| 编号 | 原则 | 详细说明 |
|:---|:---|:---|
| **P1** | **流程固定 $\neq$ 规则硬编码** | 系统固定每个请求必经 Stage 1 语义理解门禁；但**是否需要澄清、澄清什么、候选有哪些，完全由 LLM 结合图谱结构化事实裁决**，禁止在代码中写死的业务语义判断（如 `if "pipeline" in q: clarify()`）。 |
| **P2** | **Stage 2 工具调用完全按需** | Agent 内部的检索次数、工具组合、补检时机与结束节点由 LLM 根据每一步的 Observation 自主裁决。系统不设“默认搜两轮”的窄幅轨道。 |
| **P3** | **Harness 退出业务编排，回归系统底线** | Harness 仅负责拦截非法参数、未知工具、总步数熔断（`max_steps`）与死循环防护。**Harness 严禁拦截合法的 `finish` 决策，严禁替 LLM 自动补检。** |
| **P4** | **禁止硬编码业务语义，保留系统技术约束** | 禁止硬编码任何业务判断逻辑；但明确保留系统级约束、协议约束、数据结构 Schema、图谱拓扑依赖与安全配额。 |
| **P5** | **体验层只呈现自然高层行为** | 前端只呈现 Agent 正在采取的自然业务动作（如“正在检索相关资料”），彻底废除内部算法策略名（如 `strip_modifiers`）对用户的暴露。 |

## 二、 详细设计：Stage 1 对话门禁（Dialogue Gate）

### 2.1 职责与定位
* **核心职责**：解决**“我们到底在谈什么”**（指代消解、主体锁定、跨模块/跨产品歧义识别）。
* **工序特征**：每一个用户提问都固定经过 Stage 1 语义判定。

### 2.2 运行控制流与数据流
```text
                     [用户输入 Question + 对话历史 History]
                                       │
                                       ▼
                       ┌───────────────────────────────┐
                       │  LLM Dialogue Understanding   │
                       │   (输入包含：知识图谱顶级概念)    │
                       └───────────────┬───────────────┘
                                       │
                        ┌──────────────┴──────────────┐
                        ▼                             ▼
                【判定存在多义/宽泛】            【判定主体明确或已消歧】
                        │                             │
                输出 Clarify Card                     │ 提取 resolved_question 与 head_entity
             {"question": "请确认模块",                │
              "options": ["A", "B"]}                  │
                        │                             │
                        ▼                             ▼
                  [暂停并等待选择]               【进入 Stage 2: Agent Loop】
```

### 2.3 图谱在 Stage 1 的角色
知识图谱是 **LLM 做判断时所使用的结构化事实来源**（为 LLM 提供受控的候选概念空间），而非直接通过硬编码逻辑代替 LLM：
* 例如用户输入“*Pipeline 怎么发布*”，图谱提供 `[PipelineBuilder, PipelineWebGL, StampServer 管线服务]` 作为背景事实；
* LLM 理解后判定：“Pipeline 在当前知识库存在 3 个合理实体，当前上下文不足以消歧”，从而主动输出 Clarify Card。

## 三、 详细设计：Stage 2 自主执行循环（Agent Execution Loop）

### 3.1 职责与定位
* **核心职责**：解决**“主体确定后，如何最精准、最低开销地获取知识并组织答案”**。
* **执行模型**：标准流式 ReAct（Think $\to$ Act $\to$ Observe）。

### 3.2 极简决策契约（LLM Output Schema）
彻底废除与旧 Evidence Gate 耦合的 `gate` 字段，LLM 核心决策仅包含动作、工具、参数与思维推导：

```json
{
  "thought": "用户询问 StampServer 默认端口，主体明确。改写为精准查询'StampServer 默认端口'，调用 retrieve_kb 检索知识库。",
  "action": "tool_call",
  "tool": "retrieve_kb",
  "arguments": {
    "query": "StampServer 默认端口",
    "mode": "hybrid",
    "intent": "exact_parameter"
  }
}
```
* **当 LLM 评估证据充分时**：
```json
{
  "thought": "召回片段中已明确包含 StampServer 默认端口为 8080 的配置事实，证据完备，结束检索开始生成回答。",
  "action": "finish"
}
```

### 3.3 工具注册表规范（Tool Registry）

| 工具名称 | 职责定位 | 参数规范 | 输出与副作用约束 |
| :--- | :--- | :--- | :--- |
| `retrieve_kb` | 知识库检索 | `query` (必须非空)<br>`mode` (hybrid/vector/bm25)<br>`intent` (可选意图标记) | 将召回 chunk 写入 `EvidencePool`，返回摘要。<br>**只读无副作用**。 |
| `link_entities` | 图谱实体与拓扑检索 | `query` (实体/关系词) | 返回实体规范名、置信度及拓扑一跳关系。<br>**只读无副作用**（严禁在工具内篡改全局状态）。 |
| `reuse_evidence` | 复用前序有效证据 | 无（或 `group_id`） | 连续追问且主体一致时激活前序已引用证据。 |
| `environment.*` | 系统状态感知 | 按需 | 读取服务与运行时状态。 |

### 3.4 知识获取的完全自主化
1. **单步直接即答（One-Shot Finish）**：
   * 简单或明确问题，第 1 次 `retrieve_kb` 后 LLM 观察到证据充足，输出 `action="finish"`；
   * 系统**无条件放行**进入生成阶段，消除一切伪补检，响应延迟缩短 50% 以上。
2. **按需多步定向补检（Multi-step by Need）**：
   * 复杂问题（如故障排查、跨模块依赖），LLM 观察到缺少关键事实，自主输出第 2 次或第 3 次 `retrieve_kb`（带上 LLM 自己生成的精准 query）；
   * 系统严禁使用静态正则篡改模型生成的 Query。

## 四、 详细设计：Safety Harness 系统级安全边界

Harness 彻底退出业务路径决策，仅保留以下 5 项纯技术级物理安全防护：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Harness 系统安全边界                            │
├────────────────────────────────────────────────────────────────────────┤
│ 1. 参数合法性校验    ──► 校验入参非空、校验 JSON Schema、拦截未知工具    │
│ 2. 总步数预算熔断    ──► steps_used >= max_steps (默认 8 步) 强行熔断   │
│ 3. 异常死循环检测    ──► 相同 query + 相同 tool 连续重复调用时熔断      │
│ 4. 技术级调用硬上限  ──► hard_retrieve_cap = 8 (仅防程序死锁，非业务约束)│
│ 5. 证据失效隔离      ──► reuse_blocked_reason 拦截实体冲突的历史证据    │
└────────────────────────────────────────────────────────────────────────┘
```

> **严格红线**：Harness 严禁在 LLM 决策 `action="finish"` 且证据池存在相关文档时强行打回；严禁由 Harness 替模型生成补检 query。

## 五、 体验层展示规范（全链路语义化）

前端面向终端用户呈现清晰、专业的自然技术语言，彻底清除策略名残留：

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                           前端高层状态展示规范                           │
├─────────────────────────────────────────────────────────────────────────┤
│ 首次检索时     ──► "正在检索相关资料..."                                  │
│ 首次不足补检   ──► "发现当前资料缺少关键信息，正在进一步深入查询..."      │
│ 多轮深入核实   ──► "正在从相关资料中进一步核实关键事实..."                │
│ 检索探索收敛   ──► "证据组织完成，正在生成回答..."                        │
│ 触发澄清时     ──► 出示清晰的选项卡片 (Clarify Card)，提供明确指代分支     │
└─────────────────────────────────────────────────────────────────────────┘
```

## 六、 验收指标与测试标准

| 验收维度 | 考核指标 | 测量与验证方法 |
|:---|:---|:---|
| **首轮充分放行率** | $\ge \mathbf{95\%}$ | 在单一事实/明确参数测试集中，首轮召回有效证据时，Agent 直接 `finish` 放行的比例。 |
| **过度/非必要补检率** | $\le \mathbf{5\%}$ | 在证据已足以回答问题的情况下，系统仍继续发起检索的比例。 |
| **多轮复杂问题覆盖** | $\mathbf{100\%}$ 支持 2~4 次按需调用 | 构造跨组件依赖与故障排查复合题集，验证 Agent 可按需执行多步检索而不被狭隘配额拦截。 |
| **歧义识别准确率** | $\ge \mathbf{95\%}$ | 针对宽泛多义词（如“Stamp”、“管线”）准确出示 Clarify Card，明确指向问题 0 误杀。 |
| **端到端响应时延** | 简单问题时延降低 $\mathbf{40\% \sim 50\%}$ | 统计 SSE 首 Token 与生成完毕总耗时。 |
| **代码洁净度** | **零硬编码业务语义决策** | 代码审查确认彻底清除 `resolve_anchor_binding` 静态拦截与 `strip_modifiers` 正则。 |
