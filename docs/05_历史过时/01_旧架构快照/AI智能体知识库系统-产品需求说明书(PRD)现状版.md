## 一、项目概述

### 1.1 项目背景

当前系统已从早期的 Open WebUI + Ollama 基础 RAG，演进为 **自研 Vue3 前端 + FastAPI 单体后端** 的本地知识库问答系统（多 provider 模型、Hybrid 检索、可选 GraphRAG）。原版 PRD 中列出的核心问题，落地情况如下：

| 问题编号 | 原问题描述 | 现状（2026-08-10） |
|---------|-----------|-------------------|
| P1 | 多份手册中相同名词含义不同，AI回答混乱 | 部分缓解：检索前歧义预检（反问卡片）+ Graph Intent（alias / `different_from`）+ 回答侧实体消歧提示；**无**用户偏好记忆表 |
| P2 | 知识块按字数硬切分，丢失章节结构语义 | **已解决**：章节硬边界 + embedding 语义切块；表格/代码结构保护；异常时滑窗降级 |
| P3 | 文档无分类、无关联关系 | **部分解决**：chunk 带 `doc_category`（9 类枚举）+ SQLite 图谱（实体/关系/实体-chunk 链接）；分类**不是**原版树形分类表 |
| P4 | 系统不会反问 | **已有**：`POST /query/clarify` + 前端选项卡片；规则 JSON 种子 + LLM 主判；**无** 30 秒超时 / 偏好跳过 |
| P5 | 业务人员无法干预和修正知识数据 | **部分解决**：审核台可改章节标题/分类、通过/驳回；**无**块内文本编辑、合并/拆分、审核台内关联实体 |
| P6 | 无空间数据对接能力 | **仍预留**：仅 `geo_wkt` 字段（恒为 None），无地图功能 |

### 1.2 项目目标

原版目标与达成情况：

| 目标编号 | 目标描述 | 原量化指标 | 现状 |
|---------|---------|-----------|------|
| G1 | 回答准确率提升至85%以上 | 人工抽检100题 | 黄金集 FR-10 v4：**39/45 = 86.67%**（live 约 2537 chunks） |
| G2 | 支持知识块人工审核与修正 | 业务员可独立操作 | ✅ 审核台通过/驳回/改标题与分类；❌ 无合并拆分与块文本编辑 |
| G3 | 建立文档分类与知识图谱关系 | 复杂问题能跨文档关联 | ✅ 分类元数据 + 图谱建设/审批；运行时图扩召回辅助找块（生产模板默认关图） |
| G4 | 系统具备主动反问能力 | 歧义时弹出选项卡片 | ✅ 提问前反问卡片（2~4 选项） |
| G5 | 预留地图展示对接接口 | 空间字段存在、渲染暂不实现 | 仅保留 `geo_wkt`；`geo_bbox` / `place_name` **未落地** |

### 1.3 系统角色定义

系统当前**无登录与权限体系**，页面均开放。按使用方式对应原版角色：

| 角色 | 职责（现状） | 使用频率 |
|------|-------------|---------|
| **普通用户** | 提问、追问、查看来源/证据、反馈有用/无用、可选联网搜索、切换知识库/分类/模型 | 高频 |
| **业务审核员** | 审核知识块（通过/驳回、改标题/分类）；图谱候选审批与应用；画布查看/主干预览编辑 | 中频 |
| **系统管理员** | 配置/CLI、受控重建、知识库一致性、Docker 部署、质量仪表盘；**无**分类树管理页与版本切换页 | 低频 |
| **后台系统** | 定时扫描入库、清洗分块向量化、BM25 重建、图谱抽取候选（规则±LLM）、反馈统计 | 持续运行 |


## 二、总体架构

└─────────────────────────────────────────────────────────────────────────────────────┘
                                        │ HTTP / SSE
┌─────────────────────────────────────────────────────────────────────────────────────┐
│                         智能体核心层（现状 = FastAPI 问答管线）                        │

**检索与图谱在架构中的位置（对应原版「工具调用」）**：

| 能力 | 作用 | 是否写入答案事实 |
|------|------|------------------|
| Hybrid 文本检索 | 主召回通道：向量 Similarity ∥ BM25 → RRF；只取 `review_status=approved` | 是（chunk 原文进 context） |
| 图谱扩召回+融合 | 实体链接 → 关系扩展 → `entity_chunk_links` 取块 → 与文本路加权融合（席位控噪） | 否（仍用块原文） |
| 图辅助改写 query | 中量图摘要 → helper LLM 产出额外检索 query | 否 |
| Graph Intent 评分 | alias↑ / `different_from`↓ 等，改已召回块排序（可不依赖开图开关） | 否 |
| 回答侧实体提示 | prompt 消歧提示，声明非事实来源 | 否 |

> 现行契约：**业务事实只来自检索到的 chunk 原文**（联网结果须显式开启并标「外部来源」）。关系边 / `evidence_text` 不作为独立事实通道。

### 2.2 数据流转总览

| 阶段 | 触发动作 | 数据流转（现状） |
|------|---------|------------------|
| **入库** | 放入 `watch_directory` / 上传 / 博客爬取或同步；定时扫描或 `POST /scan` | 文档 → 清洗 → 章节/语义分块 → 向量化入 Chroma（`pending`）→ 更新 `file_index` + BM25；图谱抽取为**独立** extract→候选→审批→apply，不与扫描同步写正式库 |
| **审核** | 打开知识块审核台 | 筛选 pending → 改标题/分类 → 通过/驳回（批量或「通过全部筛选」）；**无**合并/拆分/块内改文/审核台关联实体 |
| **检索** | 对话页提问 | 问题 →（可选反问）→ 上下文化/多 query → Planner → Hybrid →（可选图扩召回融合/改写）→（可选 Rerank）→ Intent 等后处理 → LLM 生成 + 引用/证据 |
| **反馈** | 用户点「有用/无用」 | 写入 `user_feedbacks` → 质量仪表盘统计；差评可重置对应 chunk 待审 |


## 三、数据层详细设计

### 3.1 向量数据库（ChromaDB）

**原版问题「固定字数硬切」**：现状已改为章节硬边界 + embedding 语义边界；表格/代码不切断；embedding 异常时滑窗降级。

每个 Chunk 入库时携带的主要字段（与运行时 metadata 对齐）：

| 字段名 | 类型 | 必填 | 说明 | 示例/备注 |
|--------|------|------|------|-----------|
| `chunk_id` | String | 是 | 全局唯一知识块 ID | 由入库流程生成 |
| `text` | Text | 是 | 知识块正文 | — |
| `embedding` | Vector | 是 | 文本向量 | 由配置的 embedding 模型生成 |
| `metadata.source` / `file_path` | String | 是 | 来源文件 | 如手册路径 |
| `metadata.doc_category` | String | 是 | 文档分类（9 类枚举，非树表） | StampServer / StampTools / … |
| `metadata.section_title` | String | 是 | 章节标题 | — |
| `metadata.section_path` | String | 是 | 章节完整路径 | — |
| `metadata.section_index` / `chunk_in_section` | Integer | 是 | 章节序 / 块在章节内序号 | — |
| `metadata.page` | Integer/空 | 否 | 页码；无页码类型显示「无页码」 | TXT/MD/图片/视频等 |
| `metadata.kb_name` | String | 是 | 「已发布文章」或「文章附件」 | 按目录规则 |
| `metadata.review_status` | Enum | 是 | `pending` / `approved` / `rejected` | 检索默认只返回 approved |
| `metadata.geo_wkt` | String | 否 | **预留**空间字段 | 恒为 None；无 bbox/place_name |

知识库约定：`watch_directory/已发布文章/` → kb_name=「已发布文章」；其余 →「文章附件」。

### 3.2 关系数据库（SQLite，`data/rag_relational.db`）

原版规划 **6 张表**（含分类树、歧义规则表、用户偏好表）。  
**现状**为图谱 schema（约 9 张业务表 + 反馈等），**没有** `doc_categories` / `disambiguation_rules` / `user_preferences` SQL 表。

#### 表：实体 `entities`

| 字段名 | 说明（现状） |
|--------|-------------|
| `name` / `canonical_name` | 名称 / 规范名（唯一约束按实现） |
| `entity_type` | 如 Product / Service / Section / Field / Error 等（以正式库与主干为准） |
| `doc_category` | 可选归属分类 |
| `confidence` / `review_status` / `properties_json` / `created_by` | 置信度、审核态、扩展属性、来源（如 `seed:product_backbone`） |

别名不在实体行内逗号拼接，而在独立表 **`aliases`**（`alias` → `entity_id`，可带 `source_chunk_id` / `evidence_text`）。

#### 表：关系边 `relations`（对应原版 `entity_relations`）

| 字段名 | 说明（现状） |
|--------|-------------|
| `source_entity_id` / `target_entity_id` | 两端实体 |
| `relation_type` | 如 `belongs_to`、`different_from`、`defined_in`、`has_field` 等 |
| `confidence` / `evidence_text` / `source_chunk_id` / `review_status` | 置信度、证据、血缘 chunk、审核态 |
| 唯一约束 | `(source, target, type)` |

> 运行时扩召回取证据块主要靠 **`entity_chunk_links`**，不是靠把 `evidence_text` 直接塞进答案。

#### 表：实体-知识块关联 `entity_chunk_links`（核心关联，同原版定位）

| 字段名 | 说明（现状） |
|--------|-------------|
| `entity_id` / `chunk_id` | 实体 ↔ 向量库 chunk |
| `link_type` / `section_path` / `page_label` / `evidence_text` / `source` | 链接类型与展示/血缘信息 |

**作用**：图扩召回（模式 2）经此表加载图侧 Document，再与 Hybrid 结果融合。

#### 表：字段 / 流程（原版无，现状新增）

| 表 | 用途 |
|----|------|
| `fields` | 限定名 Field（如 `管线点表.管点编号`），Task 8.2 |
| `procedures` / `procedure_steps` | 操作流程与步骤 |

#### 表：抽取 staging（原版无，现状建设主路径）

| 表 | 用途 |
|----|------|
| `extraction_batches` | 抽取/同步批次（mode、快照哈希、统计） |
| `extraction_candidates` | 候选（kind、fingerprint 去重、payload、status：pending/approved/rejected/applied） |

#### 原版表5/表6 的替代形态

| 原版表 | 现状 |
|--------|------|
| `disambiguation_rules` | `data/disambiguation_rules.json` 种子；LLM 主判是否反问 |
| `user_preferences` | **未实现** |
| `doc_categories` 树表 | chunk `doc_category` 枚举 + `data/domain_catalog.json` |

#### 反馈表 `user_feedbacks`

记录对话反馈（有用/无用），供质量仪表盘与差评回审。

### 3.3 数据淘汰与版本管理机制

| 机制 | 原版设计 | 现状 |
|------|---------|------|
| **软删除** | `is_active=false` | 用 `review_status=rejected`（或重建剔除）；检索不返回非 approved |
| **版本标记** | 同文件多版本共存 + 切换界面 | **无**版本切换页；变更靠重新入库/受控重建（备份→清空→重扫→一致性断言→BM25） |
| **定期清理** | 180 天物理删 | 无该定时策略；图谱侧有 Stale 链接清理、审计等运维命令 |


## 四、智能体核心功能设计

### 4.1 智能体工作流程

原版为 12 步 Agent（预检得分阈值 → 反问 → 正式检索 → 图谱扩展 → 重排 → 生成 → 偏好记忆）。  
**现状**按下列管线执行（实现入口：`rag.py` 等服务模块）：

| 步骤 | 阶段 | 动作 | 决策点 |
|------|------|------|--------|
| 1 | **感知** | 接收用户问题 + 对话历史（前端/可选后端聊天记录） | 闲聊正则 → 直接 LLM，跳过检索；敏感 → 拒答 |
| 2 | **歧义预检** | `POST /query/clarify`：LLM 主判 + 规则种子降级 | **命中** → 前端反问卡片，用户带过滤条件再问；**否则**继续 |
| 3 | **上下文化** | 历史改写独立问题 + 多 query + 来源锚点；失败启发式 | — |
| 4 | **意图/计划** | QueryPlanner：流程/部署/排错/对比等 → top_k、是否 rerank 等 | — |
| 5 | **图谱准备**（可选） | `graph_retrieval.enabled=true` 时：实体链接 → 关系扩展 → 经 `entity_chunk_links` 取图侧 chunk；可选图辅助改写 query | 失败 → fallback 纯文本路 |
| 6 | **正式检索** | Hybrid：向量 Similarity ∥ BM25 → RRF；过滤 approved；可选 kb/分类/实体锚定 | — |
| 7 | **图谱融合**（可选） | 文本路与图侧块加权融合；`max_graph_only_slots` + `protect_text_top1` 控噪 | 关图则跳过 |
| 8 | **重排序**（可选） | Cross-Encoder Rerank；生产 CPU 默认关，本地可开 | 全局 `reranker.enabled` 三层门控 |
| 9 | **后处理评分** | 结构化加权（表格/章节等）+ **Graph Intent**（alias / `different_from` / field / section） | Intent **不依赖**开图开关 |
| 10 | **上下文组装** | Token 预算裁剪 + 历史摘要；可选联网搜索（显式开启） | — |
| 11 | **生成答案** | chunk 原文（编号）进 prompt；若已链实体可附加**消歧提示（非事实）** → LLM（同步/SSE） | 无依据先输出未命中提示；可选通用知识补充 |
| 12 | **溯源与证据** | 确定性来源引用 + 证据包；可选 QA trace 全流程记录 | — |
| 13 | **反馈** | 有用/无用 → `user_feedbacks` | **无** `user_preferences` 记忆跳过反问 |

与原版步骤 7–9 的对应关系：

- **正式检索** = 现状 Hybrid（主路径）。  
- **图谱扩展** = 现状「先链实体再取块再融合」，不是「仅用已命中 chunk 反查 links 扩 1 跳」这一种写法；并增加图改写 query、Intent 加减分、回答侧消歧提示。  
- **答案依据**始终是 Top 上下文中的 **chunk 文本**，不是关系句子。

### 4.2 反问工具的行为规范

| 规范项 | 原版要求 | 现状 |
|--------|---------|------|
| **反问触发条件** | 预检得分＜0.75 / 命中规则表 / 缺上下文 | 提问前 clarify：LLM 主判模糊/实体不确定；规则 JSON 作种子与降级 |
| **反问格式** | 可点击选项，非开放式 | ✅ 选项按钮 |
| **选项数量** | 2~4，可加「其他」 | ✅ 2~4 |
| **选项内容** | 显示文本 + 过滤条件 JSON | ✅ 可带 `doc_category` / `entity_name` 等继续检索 |
| **超时处理** | 30 秒自动「综合回答」 | ❌ 未实现 |
| **记忆应用** | `user_preferences` 跳过反问 | ❌ 未实现 |

## 六、业务流程详细说明

### 6.1 文档入库流程

```
【开始】
   ↓
① 文档进入 watch_directory / 上传接口 / 博客爬取或发布同步
   ↓
② 系统自动（定时约 30 分钟或 POST /scan）：
   a. SHA-256 哈希去重（移动/重命名可追踪）
   b. 解析（md/docx/txt 优先章节切片；pdf/doc；Excel→Markdown 表；图片/视频→视觉描述）
   c. 清洗（Word 域代码、纯目录/纯链接/噪声）
   d. 分块（章节硬边界 + 语义边界；表格/代码结构保护）
   e. 向量化写入 Chroma，review_status=pending
   f. 更新 file_index；重建 BM25；清查询缓存
   （图谱抽取不在本步自动 apply 进正式库）
   ↓
③ 业务员在【知识块审核工作台】处理 pending：
   - 通过 → approved（可被检索）
   - 驳回 → rejected
   - 可改章节标题、doc_category
   - 无合并/拆分/块内改文 → 切错则驳回后由开发侧重切
   ↓
④ approved 后进入检索集合
   ↓
【结束】
```

### 6.2 用户问答流程（含反问场景）

```
【开始】
   ↓
① 用户在【智能对话页面】输入问题
   ↓
② 闲聊/敏感分流；否则进入问答管线
   ↓
③ 提问前歧义预检（/query/clarify）
   ├─ 命中 → 反问卡片 → 用户选择过滤条件 → 继续
   └─ 未命中 → 继续
   ↓
④ 上下文化 + QueryPlanner
   ↓
⑤ [可选] 图谱准备：链接实体 / 扩召回取块 / 改写检索 query
   ↓
⑥ Hybrid 正式检索（approved + 可选分类/知识库过滤）
   ↓
⑦ [可选] 图侧与文本路融合（席位控噪 + 保护文本 top1）
   ↓
⑧ [可选] Rerank → 后处理（结构化加权 + Graph Intent）
   ↓
⑨ 组装 context（仅 chunk 原文 + 可选实体消歧提示）→ LLM 生成（SSE）
   ↓
⑩ 展示来源/证据；用户反馈有用/无用
   ↓
【结束】
```

### 6.3 图谱维护流程

```
【开始】
   ↓
① 方式一：规则管线 ± LLM 抽取 → extraction_candidates
   - SectionPath / TableField / ConfigBlock 等确定性抽取
   - 可选 LLM 语义补实（配置开关）
   - 指纹去重进批次
   ↓
② 方式二：产品主干 / domain_catalog / Profile 等 JSON 同步进 staging
   ↓
③ 审批：【图谱候选审批台】或 CLI（run_graph_build.py）
   - 分拆审批；禁止对敏感 mode 滥用 --approve-all
   - apply 需三重确认（DB 路径 / 批次 / 备份）
   ↓
④ 写入正式表：entities / aliases / relations / entity_chunk_links / fields / …
   ↓
⑤ 画布：查看、过滤、展开邻居；主干预览改 JSON（不直接当正式写）
   ↓
⑥ 审计 / Stale 清理 / 质量 / Task8.1 Gate 等运维命令
   ↓
⑦ 运行时：仅按配置介入检索管线（Intent / 扩召回融合 / 改写 / 消歧提示）
   ↓
【结束】
```

## 八、非功能性需求

### 8.1 性能要求 / 实测

| 指标 | 原版要求 | 现状参考 |
|------|---------|---------|
| 普通问答响应 | ≤ 5 秒 | 视模型与是否 Rerank/开图；检索段 Hybrid 历史约 ~200ms 量级（不含生成） |

| 检索质量 | — | Hybrid+Rerank：标准集 Recall@3 **88.89%**；难例集 **90.97%**；黄金集 **86.67%** |
| GraphRAG | — | 第 4 轮 A/B **PASS**；融合控噪已落地；**生产默认仍关图** |
| 图谱画布 | ≥500 节点 30fps | 渐进展开/过滤为主，未按原版指标单独验收 |

### 8.2 可用性要求

| 指标 | 原版 | 现状 |
|------|------|------|

| 要求 | 原版 | 现状 |
